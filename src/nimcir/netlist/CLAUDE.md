# `netlist` submodule

`src/nimcir/netlist/` models an electronic circuit netlist in memory and reads/writes it to netlist file formats.

- **`types.nim`** — the core, format-agnostic data model: `Netlist`, `Net`, `Component`, `Pin`, all `ref object`s. The graph is deliberately built with *direct object references* in both directions (`Pin.component`/`Pin.net`, `Net.pins`, `Component.pins`, `Netlist.parent`/`Netlist.children`) so it is fully walkable from any starting point — not just reachable through the name-keyed `OrderedTable` dictionaries (`Netlist.nets` by net name, `Netlist.components` by reference designator). Nim 2.x's default ORC GC collects the resulting reference cycles automatically. Every entity has an open-ended `attrs: OrderedTable[string, string]` bag for format-specific extras, keeping the core schema format-agnostic.
- **`graph.nim`** — the only place allowed to mutate the graph's back-references (`addComponent`, `addNet`, `addPin`, `connect`/`disconnect`, `removeComponent`, `addChild`, `addPort`, `renameNet`, `clone`, `instantiate`). `renameNet` rekeys `nets` and sets `Net.name`, leaving `ports` *keys* alone (a port name is the published interface, independent of the net behind it); it exists because `spice/isolate` has to promote some rail to SPICE node `"0"`, which means nothing until the net is actually named `"0"`. Code elsewhere must go through these procs rather than hand-setting `.net`/`.pins`/`.component`/`.parent` directly, or the bidirectional links will get out of sync.

  It also owns **hierarchical naming**: `hierSep` is `'.'`, `hierName` joins with it, and `findNet`/`findComponent`/`findPin` resolve a `hierSep`-separated path — **flat key first, then descending into `children`**. That ordering is what lets one call serve an authored hierarchy and a flattened one alike, so nothing holding such a name has to know which it is looking at. `findPin` searches split points **right to left**, longest component prefix winning, because both halves may contain a dot (XSPICE names a differential port's pins `name.p`/`name.n`). `adoptNet`/`adoptComponent` re-home an existing object under a new name rather than copying it — every `Pin.net` back-reference and every `attrs` entry, including the `role.*` tags that must outlive a transform, comes along untouched. `mergeNets` folds one net into another, which is what a subcircuit port *is* once the hierarchy is gone. `registerGlobalNet` exists for the same reason `setModel` does: `global = true` expanded to a bare `globals[name] = net`, which forced every design using it to `import std/tables` — and that went unnoticed until the first design with a subcircuit, because the statement is only worth making when there is a child to share a net with.
- **Hierarchy model**: a "sub-netlist" is a child `Netlist` hung off a `Component` whose `subNetlist` field points at it (e.g. a SPICE `X`/subcircuit instance). `instantiate()` deep-clones a template `Netlist` per instance via `clone()`, so each instantiation gets independent `Net`/`Component`/`Pin` objects rather than sharing one template — except nets registered in the `globalNets` table passed to `clone`/`instantiate` (e.g. SPICE node `"0"`), which are reused as the *same* object across every hierarchy level to match real ground/global-net semantics. A hierarchical instance's pins connect normally to nets in the *parent* scope; each such pin's `hierNet` additionally points straight at the matching port `Net` inside `component.subNetlist`, so hierarchy boundaries can be walked in either direction without name lookups.
- **`issue.nim`** — the shared `Issue` result type (`kind`/`severity`/`message`/`net`/`pins`/`components`/`attrs`). It lives here rather than in `analysis`, where it started, for the same reason `kinds.nim` does: `netlist/annotations` validates the vocabulary and must report what it finds, `pcb` will want to report design-rule findings, and `analysis` already depends on `spice` — a type all three need has to sit below all three. `analysis/issue.nim` re-exports it unchanged, so every existing import still means what it did.
- **`annotations.nim`** — the *vocabulary*: which `attrs` keys mean something, what type and unit each carries, and where each value came from. `attrs` is open-ended so a format never extends the core schema; the price is that **a typo in a key is indistinguishable from an absent key** — write `ESL` for `esl` and `spice/models` silently uses a package default *and reports it as an assumption*, so it looks like it worked. `AnnDef` declares key/kind/unit/scopes/doc/aliases, `validateAnnotations` reports misspelled bare keys, wrong-scope keys and unparseable values, and `setAnnotation` overloads check the unit (`esr = 20.nF` is rejected). **Naming rule: bare means registered, dotted means owned** — `value`/`voltage`/`esr`/`esl`/`package`/`tolerance`/`zin`/`rout`/`lout`/`gain`/`gbw`/`t_ambient_min`/`t_ambient_max`/`delta_t`, plus the switch and magnetics keys `ron`/`roff`/`vt`/`vh`/`k_coupling`/`turns`/`lpri`/`lsec`, are the shared vocabulary; `xspice.*`, `parasitics.*`, `role.*`, `ann.src.*`, `kicad.*`, `switch.*` (mux topology hints — `select_pins`, `off_termination`, `enable_active_low`) and anything a user invents are namespaced and never validated. The registry is a **runtime table seeded from a `const`**: the `const` is what the DSL macro reads to reject a bad key at compile time, and the table is what keeps runtime registration possible. `parseAnnFloat` **rejects SPICE magnitude suffixes** rather than interpreting them — `"20m"` is 20 milli in a deck and 20 units read naively, and picking either silently is the failure the whole module exists to prevent. Provenance is in the accessor's *return type* (`AnnValue[T]{source, value}`), which is why it could not be added later without touching every call site; accessors are **pure and never default**, because inventing a stand-in is a policy decision belonging to whichever consumer knows what a sensible stand-in is. `Assumption` lives here too, next to `AnnSource`, since `spice` produces assumptions and cannot import `analysis`.
- **`kinds.nim`** — electrical classification of the open-ended `Component.kind` string (`classifyConductivity` -> `condConductive`/`condBlocking`/`condAmbiguous`, `isPassive`) and of a net's rail role (`isRail`, `isGround`). Its own module, not a helper inside its first consumer, because two independent subsystems must agree on the answer: `analysis/io_check` walks DC paths and `spice/isolate` decides what to absorb and where to stop, and a net that terminates one walk must not be traversed by the other. `analysis` already depends on `spice`, so the shared answer can live in neither. `behaviouralKinds` (`vcvs`/`vccs`/`cccs`/`ccvs`) is the one thing `isPassive` accepts that `classifyConductivity` still calls ambiguous, and the split is deliberate: a controlled source is **not** a DC path in the conduction sense — its output *is* a source, not a connection to its input — so `io_check` must keep refusing to walk through one; but its behaviour genuinely is fully described by its value, which is the question `isPassive` is actually asked. Without that, a controlled source synthesized by `spice/models` to preserve a signal path would be discarded by the very isolation meant to keep it. `couplingKinds` (`mutual_inductance`) is the same shape for a different reason: a SPICE `K` card has *no terminals*, so `classifyConductivity` calling it ambiguous is not a hedge — a transformer's two windings genuinely share no DC node, and that *is* the isolation barrier `io_check` must not cross — while `isPassive` accepts it so `spice/isolate` keeps the coupling rather than dropping it. It is synthesized only, by `spice/models/magnetics`. `builtinDesignatorPrefixes`/`designatorPrefixFor` map a `kind` to its **reference-designator** prefix (`ferrite_bead` -> `FB`, `opamp` -> `U`, fallback `U`), a runtime table extensible with `registerDesignatorPrefix` like every other registry here. **Deliberately separate from `formats/spice.prefixByDeviceKind`, and it must stay separate**: a ferrite bead is `FB` on a schematic and needs `L` in a deck, a battery is `BT` and `V`. They answer different questions -- a naming convention for people versus how SPICE decides what device it is reading -- and deriving either from the other is how `FB1` came to be simulated as a current-controlled current source. A wrong designator prefix is cosmetic where a wrong device letter is a wrong answer, which is why `U` is an acceptable fallback here and nothing is guessed there. `isRail`/`isGround` accept *either* signal (`Net.kind` OR a connected `Pin.kind`) because the two are populated inconsistently by netlist origin — requiring both would make every partially-annotated netlist look railless.
- **`environment.nim`** — where the board lives, and how hot each part runs in it. Two numbers stand between the netlist and any temperature-dependent answer, and neither is electrical: the **board's** ambient range (`t_ambient_min`/`t_ambient_max`, netlist-scope, from an enclosure spec and the same for every part) and a **part's** rise above it (`delta_t`, component-scope). They are stated separately on purpose — the range is fixed when the product is specified, while a rise is a per-part consequence of a circuit that does not exist yet at that point, so folding them into one absolute temperature per part would mean restating the enclosure spec on every component with a copy to drift at each one. **It wires the two together and models nothing**: there is no tempco here, no capacitance- or ESR-versus-temperature curve, and the figures are deliberately **not** passed to the deck as `.options temp`, which would change how every semiconductor in the design behaves and would silently move every number this repo has measured. What it provides is the input such a model needs — `partTemperatureRange(c, env)` shifts the ambient range by the part's rise at **both** ends, since a dissipating part is above the air whatever the air is doing, and a board specified to -40 does not have to hold a self-heating regulator's ratings at -40 while everything that does *not* dissipate still does. Storage is `attrs` rather than fields on `types.nim` for the reason annotations always are, and here it is load-bearing: `clone` copies them, so the range and every rise survive `materializeSimNetlist`, `flatten`, `extractSubcircuit` and `isolate` — and a fragment cut out for simulation is precisely where a model pass will read them. `environmentOf` reads the **root**, so a child netlist gets the same answer as the board (a subcircuit has no weather of its own). **A part's rise defaults to 0 and says that it did**: `temperatureRise` returns `annDefaulted`, which is the one place a default is applied by an accessor rather than by a consumer, and it does not generalise — an unstated ESR and a zero ESR are different claims about a part, whereas an unstated rise and a zero rise agree for every part that is not dissipating. `deltaT` is still the pure accessor for anything that wants to see the absence, and `riseAssumption` phrases the default once for every consumer. `validateEnvironment` reports what was *stated* and cannot work — an inverted range, half a range, or a `delta_t` with no range to be a rise above — and never nags a design that stated nothing, since nothing consumes the range yet. Authored via the DSL's `environment:` block; `setOperatingTemperature`/`setDeltaT` are the runtime path a file reader takes.
- **`packages.nim`** — one physical package, several channels that may live on different sheets. A dual op-amp is one chip, one footprint, one BoM line, one silkscreen designator; the netlist models it as N `Component`s (often two instances of one `subckt`, so `XL.U1` and `XR.U1` are separate objects in separate child netlists) that share only a `partNumber`. This module adds the statement *these sections are the same die*. Like `environment.nim` and `contract/design.nim` it **stores membership in namespaced `attrs`** (`package.ref`/`package.section`/`package.def`) rather than `types.nim` or a root registry: `graph.clone` copies `attrs` at every level, so membership survives `clone`/`instantiate`/`flatten`/`extractSubcircuit`/`isolate` with no new code — and a root registry of direct `Component`/`Pin` references would need remapping written and tested across all of those, with `extractInstance` (which clones a child alone) stranding it. A package **definition** (`PackageDef`: sections, per-section logical pins, global pins, a package-pin-id → `PackagePin` map) *is* a registry, keyed by part number, because only a full pinout lets `pcb/graph.addLand` resolve pad `"7"` on an NE5532 to section B's `OUT` and lets `pcb/bom` fall back to a shared part number when `Placement.component` is nil. Definitions hold **no procs** (a package computes nothing) so they could later be read from a file, and there are **no built-ins** — every multi-channel package is a specific part number, so `designs/lib/` owns the catalogue (`designs/lib/opamps.nim`), the line `parts/policy.nim` already draws. `assignSection` is the one writer; `packageInstance(defName, ref)` raises at the `let` for an unregistered definition; `pkg.section("A", "U1")` returns a `proc (Netlist)` for `instance ..., with =` (the cross-sheet path), `pkg.assign(nl, "A", "U1A")` is the flat path. **The global-pin check is by object identity, not by name**: in a stereo board both channels' `V+` nets are distinct `Net` objects sharing the name `VP` (clones of one template net), so `validatePackages` resolves each through `Pin.hierNet`/ports to the outermost net (`outermostNet`) and compares those — a name comparison passes a genuinely miswired board. `validatePackages` returns `Issue`s (kinds prefixed `package_`), wired into `verify.readiness` after `validateEnvironment`. **A SPICE round trip intentionally loses package metadata** — `attrs` never reach a deck, no synthetic device encodes package identity, and a reparsed netlist carries no `package.*` keys; a consumer that needs the packaging keeps the Nim source (`test_netlist_spice.nim` pins this).
- **`interfaces.nim`** — scalar-net views for buses and declared interfaces. `bus.*` and `iface.*` attrs are the source of truth, so `findBus`/`findInterface` reconstruct after clone and hierarchy; in particular recovery takes a member bus's recorded width rather than assuming a parameterized definition's registry default. `promotePortDirections` copies child port direction and parent interface identity to instance pins, keeping shared-bus ERC valid across hierarchy. A shared signal may be genuinely released by all participants: it suppresses both multi-inout conflict and undriven findings, but never two `ptOutput` drivers. `interfaces/std.nim`'s SPI MISO uses that shape (`ptInOut` at a peripheral); map a wide signal with individual `signal_0` keys rather than one pin name. `narrow(i, signal, k)` / `narrow(i, signal, s)` return `i` with one wide signal cut to a single member (or a re-indexed slice) as a width-1/width-N bus — a **pure value-space** copy that touches neither the netlist nor the registry, so it survives `clone` and cannot rewrite `bus.index` the way `busOf` would; `{"spi": spi1.narrow("cs", k)}` in an `instance` block is how a child owning one member of a shared select bus is wired without per-signal `spi1.bus("cs")[k]` boilerplate, and `[](i, signal, k)` is the same member as a scalar. `wiringOf` and `addPorts` agree on child-side naming: a width-1 group is the bare `label`, a wider one is `label_0 … label_(N-1)`; `wiringOf(InterfaceView)` is built off `def.signals` directly (an earlier version recovered the signal by substring and silently dropped every wide-signal entry once the plain-interface overload member-suffixed).
- **`formats/`** — pluggable file-format readers/writers. Every format module implements the same contract: `readNetlist(s: Stream, name = ""): Netlist`, `writeNetlist(nl: Netlist, s: Stream)`, plus `readNetlistFile`/`writeNetlistFile` path wrappers. Format modules only depend on the core types/graph API — the core never depends on a format. `formats/spice.nim` is the only format implemented so far (SPICE `.cir`/`.net` decks); a `formats/kicad.nim` can be added later using the same contract. `formats/common.nim` holds the shared `NetlistFormatError`.
- **SPICE specifics** (`formats/spice.nim`): parses positionally per SPICE's reference-designator-prefix convention (R/C/L/D/Q/M/V/I map to fixed pin-name templates via `deviceKindByPrefix`/`pinTemplates`, and the inverse `designatorPrefix(kind): char` derives the letter back from a `kind` string; `X`/`U` resolve against `.SUBCKT`/`.ENDS` blocks, supporting forward references and nested subcircuit-instantiates-subcircuit). `.MODEL` cards are stored verbatim in `Netlist.models` (passthrough, not structurally parsed); other simulation-control directives (`.OPTIONS`, `.TRAN`, `.PARAM`, ...) are topology-irrelevant and are skipped on read. Unrecognized device-designator prefixes fall back to generic `pin1..pinN` pins rather than erroring. Because raw SPICE has no native concept of pin *type* (power/ground/input/output), `Pin.kind` fidelity through a SPICE round-trip is best-effort only — this is an inherent format limitation, not a bug. `spiceValue(x: float)` is the one correct way to format a synthesized device value (always scientific with an explicit exponent — any format that could end in a letter is a silent-misread hazard, since SPICE reads a trailing letter as a unit multiplier). `parseSpiceMagnitude` is its partial inverse and the counterpart to `annotations.parseAnnFloat`, which *rejects* suffixes because an annotation is in SI base units — here a trailing letter genuinely is a multiplier, because this is what goes into a deck. It refuses two things rather than guessing: anything that is not purely a magnitude (`attrs["value"]` may hold a whole source spec like `"DC 0 AC 1"`, which is why the annotation registry documents that key as never parsed as a number, so only a caller that knows the kind makes the value a bare magnitude should ask), and **RKM notation, where a digit follows the multiplier** — `"2k2"`, `"4u7"`. An EDA tool means 2200 and 4.7 µ by those; **ngspice reads the multiplier and discards the trailing digits, giving 2000 and 4 µ — verified against ngspice-46, not assumed.** Since `value` reaches the deck verbatim, the simulator's reading is the one that gets simulated, so a static check that quietly picked the other would disagree with the simulation about the same part by 10%. `prefixByDeviceKind`/`pinTemplates` also carry `"vcvs" -> 'E'` and `"vccs" -> 'G'` **write-side only**, for `spice/models.idealOpAmp`; unlike `'A'`, an `E`/`G` line genuinely *is* positional and reads back correctly through the generic `pin1..pinN` fallback, so they are kept out of `deviceKindByPrefix` only because nothing yet needs to recover the named `IN+`/`IN-` roles from a deck. `spice/models` added three more write-side letters: `"vswitch" -> 'S'` (a positional four-node line, so a `pinTemplates` entry `1/2/C+/C-` and nothing else is needed), `"iswitch" -> 'W'` (the letter only — a `W` line's third token names a voltage source, like `F`/`H`), and `"mutual_inductance" -> 'K'`. A **`K` card carries no nodes at all** — it names two inductors and a coefficient — so `formatDeviceLine` has a dedicated branch for it keyed on `attrs["spice.couples"]` (the coupled inductors' graph designators), resolving each to its `deckDesignator` spelling at write time; the same verbatim-escape shape as `xspice.ports`, and baking the names instead would go stale the moment `flatten` or a rename touched a winding. **`deckDesignator(comp)` is what actually reaches a deck line, and the letter comes from `Component.kind` rather than from the designator the design wrote.** SPICE infers device type from that first letter and from nothing else, so a part whose designator disagrees with its `kind` is silently simulated as a different device — and the colliding designators are all ordinary ones: `FB` (ferrite bead) reads as a current-controlled current source, `BT` (battery) as a behavioural source, `J` (connector) as a JFET, `VR` (pot) as a voltage source, `TP` as a transmission line. Those fail loudly; the dangerous pair does not, since an inductor filed as `C12` reads as a *capacitor* and a resistor filed as `L7` as an *inductor*, both of which parse and simulate. This was not hypothetical — `designs/ts808_drive.nim` had `VR1` for its drive pot, and 250 kohm of feedback network was being emitted as a 250 kV source, so the stage measured a gain of 12 instead of 65 with nothing reported anywhere. The correct letter is **prepended, not substituted** (`FB1` -> `LFB1`, never `L1`): designators are unique as a set and a truncated one need not be, so substituting would merge `FB1` and `L1` into one device on a board carrying both. A `kind` with no known letter is left alone, since there is nothing to correct it against. `deckInstanceDesignator` does the same for a hierarchical instance, always spelling it `X` — the reader accepts `U` too because other tools emit it, but ngspice reads `U` as a uniformly-distributed RC line. Note the invariant was already enforced for parts the tool *synthesizes* (`transform.replaceComponent` derives its prefix, `probes` validates one) and only the authored path was unguarded. `writeNetlist` calls **`checkDeckDesignators`** on each level first, because graph uniqueness does not imply deck uniqueness: prepending the device letter is not injective, so a resistor designated `XA.R1` and one designated `RXA.R1` are two components in the graph and one line in the deck, which ngspice reads as a device defined twice. That was unreachable while designators were hand-written and short; `spice/flatten` makes generated dotted designators ordinary. Checked per level, since SPICE scopes designators inside a `.SUBCKT`, and it raises rather than renaming — there is no safe way to guess which one was meant. `writeNetlist`/`writeNetlistFile` take an optional `cards: seq[string]` (raw control/analysis lines, e.g. `@[".op"]`) written just before `.END`; empty by default, so plain topology output is unaffected. This is what `nimcir/spice/ngspice` uses to attach an analysis card without duplicating device-line formatting.
**A `component` may omit its label entirely** (`component kind = "capacitor", value = "100n":`), in which case `graph.addGenerated` picks the designator from `kind` at construction -- at construction rather than at macro expansion because `kind` is an expression and because a `for` loop's iteration count is not knowable to the macro. Numbering is **per netlist, not per design**, which is the property that makes it tolerable: a subcircuit gets its own `C1`, `C2`, so adding a part to one module cannot renumber another, and flattening prefixes with the instance path anyway. Hand-authored designators are respected (a netlist already carrying `R1`/`R2` generates `R3`), an explicit `designator =` still wins, and omitting both a label and `kind` is a compile error rather than a guess. Generated ones are marked `attrs["designator.generated"]` and listed by `graph.generatedDesignators`, because a designator is the join key to a board (`pcb/graph.bindComponent` raises on a mismatch), a BoM line and silkscreen text -- and a generated one is **positional**, so inserting a part earlier renumbers everything after it. Safe for a part nothing names and nothing places; wrong for anything already laid out. That is self-selecting: needing to refer to a part is the signal to write its designator.

  **`instance` takes `with = <proc (Netlist)>`**, run against that instance's own clone immediately after `instantiate` and before anything else sees it. It is what makes omitted designators safe rather than merely convenient: post-hoc override is the only thing that *forces* stable identifiers, and injecting the variation at construction removes the need to address an individual anonymous part at all. Inside the proc the only names in play are the module's own **local** designators -- few, author-controlled, and never leaving the module -- rather than a name that must be unique across the whole design and stable against edits. It composes with `for` and with closures, so a per-channel trim table is ordinary code — and it now also carries **section assignment** for a multi-channel package: `with = u10.section("A", "U1")` tags this instance's `U1` as section A of package `U10` (see `packages.nim`), the only way to say two `subckt` instances share one physical chip. It is a *construction* step, not a mutation of something already built, which is the same line `Component.simReplace` draws: a post-hoc hook adding a simulation view is fine, one that changes what the board *is* afterwards is not.

- **`dsl.nim`** — an opt-in Nim-macro DSL (`import nimcir/netlist/dsl`) for authoring a `Netlist` directly in `.nim` source instead of hand-calling `graph.nim` or parsing a file format. `netlist("name"): ...` builds a flat netlist from `net`/`component` (with nested `pin`) statements, optionally repeated or selected by a `for`/`if`/`case`/`when`; `subckt("name", [ports]): ...` builds a free-standing template `Netlist` (never registered into any parent), instantiated later via `instance designator, templateIdent, [portNets]`, which expands straight to `graph.instantiate`. Net/component names given as bare identifiers are bound as real Nim `let`s so later statements can reference them (a typo is a compile error); `kind`/`name`/`partNumber` are the only typed "known fields" and get direct field assignment, while any other `key = value` pair lands in that entity's `attrs` bag. The DSL only ever expands into calls on the `graph.nim` API — like everywhere else in this submodule, back-references are never hand-set outside `graph.nim` itself. A top-level **`environment:`** block states the board-level operating conditions (today the ambient temperature range); it is `spec:` at netlist scope and is spelled differently only because that is what it says — a range read off an enclosure specification is not a property of the netlist the way a net's rail voltage is, and the name is what keeps a design file legible when humidity or altitude is added beside it. A `net` or `component` block may contain a `spec:` block, whose keys are validated against `netlist/annotations` **at compile time** — an unknown or wrong-scope key is a compile error naming the registered keys, and a `nimcir/units` literal inside it cannot be misread. This is the opposite of the permissive head-of-statement fallback, and deliberately so: the strictness boundary is syntactic, because inside `spec:` there is no open-ended bag for an unknown key to mean anything, exactly the reasoning that makes `xspice/dsl.nim` strict while this module is not. A `model "<name>", "<card>"` statement registers a `.MODEL` card (through `graph.setModel`, not a bare table assignment — `Netlist.models` is state `graph.nim` owns, and expanding to `nl.models[k] = v` would force every design file to `import std/tables` for a statement that has nothing to do with tables). The card body is **never parsed**: tracking every parameter of every device type in every SPICE dialect would mean getting one wrong silently simulates a different part, whereas passing it through means the simulator reads exactly what the datasheet said. What *does* read it is `kinds.hasDeviceModel`, which only asks whether the name is present — and that is what makes the statement matter beyond reaching the deck, because `isPassive` accepts a part with a model, so `spice/models` stops standing it in and `spice/isolate` will traverse it. Matched case-insensitively, as SPICE is. The TS808's clipping diodes are the case: without a card each became two 1 Mohm resistors to ground, and the pair shunted the inverting node with 500k — a second gain leg that lifted the stage's gain at the bottom of the sweep from unity to 4.2 dB, which is where a reported 31.6 dB of peaking came from against a real 35.3. **Parameterized circuits work, and the mechanism is that a `subckt` block is ordinary runtime code inside a `block` expression**: put it in a `proc`, compute values from the arguments before it, and reference them — `value =`, `designator =` and `name =` all take arbitrary expressions rather than literals, and `spec:` keys are validated at compile time while their *values* are expressions. `designs/lib/filters.nim` is the worked example. The block additionally admits **`for`, `if`, `case` and `when`**, and admits them as *control flow over DSL statements* rather than as an opening to arbitrary code: the loop header passes through untouched and the body is expanded by the same dispatcher, so everything inside is still a `net`/`component`/`instance`/`model`. A decoupling bank or a channel per lane is otherwise N nearly-identical lines, which is where a value gets corrected in one copy and not the others; build variants are otherwise two files that drift apart, or one file with the unused half commented out. A bare `discard` is an empty branch, since `if`/`case` need a body and "this variant adds no parts" is ordinary — `discard <expr>` is refused as arbitrary code wearing a keyword. Nothing is weakened by it — `spec:` keys are still validated at compile time and an identifier typo is still a compile error, because neither depends on whether the branch runs, and `addComponent` always raised on a duplicate designator at runtime anyway. Two things do not fit inside one: the `let` a `net`/`component` binds is scoped to the **branch or iteration**, so address anything generated there by name through `graph.findComponent`/`findNet` afterwards; and `role`/`require` are **rejected with a message**, because `design` hoists claims to after the netlist is built and a nested one would attach to a netlist that does not exist yet. `buildNetlistBody*` is exported as an extension point for a higher-level DSL that wants these statements plus its own (see `contract/dsl.nim`). A `component` block may additionally contain one or more `simReplace kind = "...", name = "...", suits = ...: pin ..., ...` statements (see `src/nimcir/spice/CLAUDE.md`) — each only ever *adds* to `Component.simModels`, so none of them mutates the component it's attached to, and a component-level `simDefault = "..."` names which one is used when nothing states a purpose. Several are told apart by `name`, and `suits` (a bare string or a bracketed list) is what says which question each answers; a duplicate `name` raises.
