# `netlist` submodule

`src/verax/netlist/` models an electronic circuit netlist in memory and reads/writes it to netlist file formats.

- **`types.nim`** — the core, format-agnostic data model: `Netlist`, `Net`, `Component`, `Pin`, all `ref object`s. The graph is deliberately built with *direct object references* in both directions (`Pin.component`/`Pin.net`, `Net.pins`, `Component.pins`, `Netlist.parent`/`Netlist.children`) so it is fully walkable from any starting point — not just reachable through the name-keyed `OrderedTable` dictionaries (`Netlist.nets` by net name, `Netlist.components` by reference designator). Nim 2.x's default ORC GC collects the resulting reference cycles automatically. Every entity has an open-ended `attrs: OrderedTable[string, string]` bag for format-specific extras, keeping the core schema format-agnostic.
- **`graph.nim`** — the only place allowed to mutate the graph's back-references (`addComponent`, `addNet`, `addPin`, `connect`/`disconnect`, `removeComponent`, `addChild`, `addPort`, `renameNet`, `clone`, `instantiate`). `renameNet` rekeys `nets` and sets `Net.name`, leaving `ports` *keys* alone (a port name is the published interface, independent of the net behind it); it exists because `spice/isolate` has to promote some rail to SPICE node `"0"`, which means nothing until the net is actually named `"0"`. Code elsewhere must go through these procs rather than hand-setting `.net`/`.pins`/`.component`/`.parent` directly, or the bidirectional links will get out of sync.

  It also owns **hierarchical naming**: `hierSep` is `'.'`, `hierName` joins with it, and `findNet`/`findComponent`/`findPin` resolve a `hierSep`-separated path — **flat key first, then descending into `children`**. That ordering is what lets one call serve an authored hierarchy and a flattened one alike, so nothing holding such a name has to know which it is looking at. `findPin` searches split points **right to left**, longest component prefix winning, because both halves may contain a dot (XSPICE names a differential port's pins `name.p`/`name.n`). `adoptNet`/`adoptComponent` re-home an existing object under a new name rather than copying it — every `Pin.net` back-reference and every `attrs` entry, including the `role.*` tags that must outlive a transform, comes along untouched. `mergeNets` folds one net into another, which is what a subcircuit port *is* once the hierarchy is gone. `registerGlobalNet` exists for the same reason `setModel` does: `global = true` expanded to a bare `globals[name] = net`, which forced every design using it to `import std/tables` — and that went unnoticed until the first design with a subcircuit, because the statement is only worth making when there is a child to share a net with.
- **Hierarchy model**: a "sub-netlist" is a child `Netlist` hung off a `Component` whose `subNetlist` field points at it (e.g. a SPICE `X`/subcircuit instance). `instantiate()` deep-clones a template `Netlist` per instance via `clone()`, so each instantiation gets independent `Net`/`Component`/`Pin` objects rather than sharing one template — except nets registered in the `globalNets` table passed to `clone`/`instantiate` (e.g. SPICE node `"0"`), which are reused as the *same* object across every hierarchy level to match real ground/global-net semantics. A hierarchical instance's pins connect normally to nets in the *parent* scope; each such pin's `hierNet` additionally points straight at the matching port `Net` inside `component.subNetlist`, so hierarchy boundaries can be walked in either direction without name lookups.
- **`issue.nim`** — the shared `Issue` result type (`kind`/`severity`/`message`/`net`/`pins`/`components`/`attrs`). It lives here rather than in `analysis`, where it started, for the same reason `kinds.nim` does: `netlist/annotations` validates the vocabulary and must report what it finds, `pcb` will want to report design-rule findings, and `analysis` already depends on `spice` — a type all three need has to sit below all three. `analysis/issue.nim` re-exports it unchanged, so every existing import still means what it did.
- **`annotations.nim`** — the *vocabulary*: which `attrs` keys mean something, what type and unit each carries, and where each value came from. `attrs` is open-ended so a format never extends the core schema; the price is that **a typo in a key is indistinguishable from an absent key** — write `ESL` for `esl` and `spice/models` silently uses a package default *and reports it as an assumption*, so it looks like it worked. `AnnDef` declares key/kind/unit/scopes/doc/aliases, `validateAnnotations` reports misspelled bare keys, wrong-scope keys and unparseable values, and `setAnnotation` overloads check the unit (`esr = 20.nF` is rejected). **Naming rule: bare means registered, dotted means owned** — `value`/`voltage`/`esr`/`esl`/`package`/`footprint`/`tolerance`/`zin`/`rout`/`lout`/`gain`/`gbw`/`t_ambient_min`/`t_ambient_max`/`delta_t`/`mpn`/`manufacturer`/`part_use`/`dnp`/`bom_exclude`, plus the switch and magnetics keys `ron`/`roff`/`vt`/`vh`/`k_coupling`/`turns`/`lpri`/`lsec`, are the shared vocabulary — `part_use` (`akEnum`, `allowed: timing/coupling/decoupling/bulk/precision/general/power/filter`, the union of `parts.CapUse`/`ResUse`/`IndUse` spelled without their enum prefix) is this registry's first `akEnum` builtin, and `setAnnotation`'s string overload checks `allowed` **at the setter**, not only in `validateAnnotations` at `readiness` — `parts/annotate.applyChoice` writes it far more often than a design is re-checked, so a typo from a runtime-built policy is caught at the point it happens rather than surfacing however much later `readiness` next runs; `mpn`/`manufacturer` are deliberately distinct from `Component.partNumber`, which may be a real MPN or an internal/house part number; the free-text descriptive labels that once overloaded it (~40 design sites, `docs/bom_compiler_plan.md` fact 2) moved to the **`description`** key on 2026-10-06, so `partNumber` now means a part number — the BOM falls back to it as an MPN, unverified and said so — `dnp`/`bom_exclude` are the registry's first `akBool` builtins: a `setAnnotation(e, key, v: bool)` overload stores `"true"`/`"false"` (so `spec: dnp = true` works), the string overload and `validateAnnotations` both refuse anything else, and `annotationBool` reads it back; `dnp` keeps the BOM line, `bom_exclude` drops it — `footprint` (component-scope, `akString`, accessor `footprint(c: Component): AnnValue[string]`) is deliberately separate from `package`: `package` is a case size keying `spice/models`' parasitics table (`"0402"`, `"tantalum"`), while `footprint` names the land pattern (`"Resistor_SMD:R_0402_1005Metric"`) `pcb/assemble.nim` resolves through `pcb/footprint.findFootprint`, and two parts can share a case size while needing different land patterns (hand-solder vs. reflow); `xspice.*`, `parasitics.*`, `role.*`, `ann.src.*`, `kicad.*`, `switch.*` (mux topology hints — `select_pins`, `off_termination`, `enable_active_low`) and anything a user invents are namespaced and never validated. The registry is a **runtime table seeded from a `const`**: the `const` is what the DSL macro reads to reject a bad key at compile time, and the table is what keeps runtime registration possible. `parseAnnFloat` **rejects SPICE magnitude suffixes** rather than interpreting them — `"20m"` is 20 milli in a deck and 20 units read naively, and picking either silently is the failure the whole module exists to prevent. Provenance is in the accessor's *return type* (`AnnValue[T]{source, value}`), which is why it could not be added later without touching every call site; accessors are **pure and never default**, because inventing a stand-in is a policy decision belonging to whichever consumer knows what a sensible stand-in is. `Assumption` lives here too, next to `AnnSource`, since `spice` produces assumptions and cannot import `analysis`.
- **`kinds.nim`** — electrical classification of the open-ended `Component.kind` string (`classifyConductivity` -> `condConductive`/`condBlocking`/`condAmbiguous`, `isPassive`) and of a net's rail role (`isRail`, `isGround`). Its own module, not a helper inside its first consumer, because two independent subsystems must agree on the answer: `analysis/io_check` walks DC paths and `spice/isolate` decides what to absorb and where to stop, and a net that terminates one walk must not be traversed by the other. `analysis` already depends on `spice`, so the shared answer can live in neither. **`classifyConductivity` keeps its whole-component meaning and body, unchanged, on purpose**: `isPassive` (below) and `schematic/placement.portDrives` both still ask it that question, and widening it to answer *per pin pair* would silently move both. `conductivityBetween(c, a, b)`/`conductiveExits(c, fromPin)` sit beside it and answer the pin-pair question instead, imported from `./traversal` for the fallback ladder's first rung: (1) `c` states a `traversal.TraversalSpec` (`statesTraversal`) -> that answers exclusively -- `tmNone` blocks every pair, `tmAll` is `classifyConductivity(c)` for every pair, a declared edge answers by its own `conducts` flag, and an undeclared pair on a part that declared *some* edges is `condBlocking` (a declaration is exhaustive: the point of writing one is to say what *does* connect); (2) nothing stated and exactly two connected pins -> `classifyConductivity(c)`, today's answer; (3) nothing stated and more than two connected pins -> `condAmbiguous`, never guessed -- and this is not a behavioural change for any undeclared part today, since no member of `conductiveKinds` has more than two terminals. `analysis/io_check.dcReachable` and `contract/evaluators/static.dcConnected` both walk per-pin through `conductiveExits` now, in place of the whole-component `case classifyConductivity(comp)` either used to run once per component -- see `traversal.nim`'s own bullet for why the split between storage/grammar (there) and resolution (here) exists. `behaviouralKinds` (`vcvs`/`vccs`/`cccs`/`ccvs`) is the one thing `isPassive` accepts that `classifyConductivity` still calls ambiguous, and the split is deliberate: a controlled source is **not** a DC path in the conduction sense — its output *is* a source, not a connection to its input — so `io_check` must keep refusing to walk through one; but its behaviour genuinely is fully described by its value, which is the question `isPassive` is actually asked. Without that, a controlled source synthesized by `spice/models` to preserve a signal path would be discarded by the very isolation meant to keep it. `couplingKinds` (`mutual_inductance`) is the same shape for a different reason: a SPICE `K` card has *no terminals*, so `classifyConductivity` calling it ambiguous is not a hedge — a transformer's two windings genuinely share no DC node, and that *is* the isolation barrier `io_check` must not cross — while `isPassive` accepts it so `spice/isolate` keeps the coupling rather than dropping it. It is synthesized only, by `spice/models/magnetics`. `builtinDesignatorPrefixes`/`designatorPrefixFor` map a `kind` to its **reference-designator** prefix (`ferrite_bead` -> `FB`, `opamp` -> `U`, fallback `U`), a runtime table extensible with `registerDesignatorPrefix` like every other registry here. **Deliberately separate from `formats/spice.prefixByDeviceKind`, and it must stay separate**: a ferrite bead is `FB` on a schematic and needs `L` in a deck, a battery is `BT` and `V`. They answer different questions -- a naming convention for people versus how SPICE decides what device it is reading -- and deriving either from the other is how `FB1` came to be simulated as a current-controlled current source. A wrong designator prefix is cosmetic where a wrong device letter is a wrong answer, which is why `U` is an acceptable fallback here and nothing is guessed there. `isRail`/`isGround` accept *either* signal (`Net.kind` OR a connected `Pin.kind`) because the two are populated inconsistently by netlist origin — requiring both would make every partially-annotated netlist look railless.
- **`layouthints.nim`** — authored hints for where the schematic layout heuristic should put a component, not electrical facts, so they never join `esr`/`package`/`t_ambient_max` in `annotations.builtinAnnotations`. Storage is a namespaced `attrs` key (`layout.side`), the trade every sibling attrs-based module here makes (`environment.nim`, `packages.nim`, `pinmux.nim`, `traversal.nim`): `graph.clone` copies `attrs` at every level, so a hint survives `clone`/`instantiate`/`flatten`/`extractSubcircuit`/`isolate` for free, and a SPICE round trip is expected to lose it exactly as it loses `package.*`. Compile-time strictness comes from the DSL's `layout:` block (`netlist/dsl.handleLayout`), not from `netlist/annotations` — permissive in the open-ended `attrs` bag underneath, strict at the syntax boundary where an unknown key can only be a mistake. Four hints exist: `side` (`left`/`right`, forcing a component to the schematic's leftmost/rightmost placement column), `mirror` (`true`/`false`, reflecting a box symbol about its own vertical centre axis), `power` (`true`/`false`, forcing a component's whole placement unit into, or out of, the schematic's separated power/decoupling band regardless of what `schematic.unitExternallyPurePower` would infer from its nets), and `variant` (`layout.variant`, a free-text name — the one hint that is a *board*-side statement rather than a schematic-rendering one: "this instance uses `pcb/variant.LayoutVariant` X"). `variant` does not share `side`/`mirror`/`power`'s closed-enum shape (`parseLayoutVariant`/`layoutVariant`/`setLayoutVariant` work in plain strings, `""` meaning no override) because a variant name is whatever `pcb/variant.registerLayoutVariant` was given and this module cannot enumerate a registry it must not import — `pcb/` depends on `netlist/`, never the reverse, so the binding is authored here and resolved there. `layoutHintKeys` is a `const seq` rather than inlined into the DSL, so a future key (rotation, a pin-level placement, an absolute position) has one place to be added on both sides — the parser here and the dispatcher there — the same shape `traversal.traversalSpecKeys` copies for its own (currently unused) extension point; `variant` is the first hint to actually use that extension point. `LayoutSide`'s `sideAuto` (and `LayoutMirror`'s `mirrorAuto`, `LayoutPower`'s `powerAuto`) is both the zero value and "no override stated", so absence and the explicit default coincide; `parseLayoutSide`/`$` (and its `parseLayoutMirror`/`parseLayoutPower` siblings) are one parse point shared by the accessor and `validateLayoutHints`, so an unrecognised value is reported once rather than divergently — the same discipline `traversal.parseTraversalEdges` copies for a three-key, edge-list vocabulary instead of one enum. `power`'s consumer (`schematic/power.poolPower`) resolves it the identical deterministic first-wins way `side` already does for a multi-member composite: the first non-`powerAuto` member in canonical order wins for the whole placement unit.
- **`traversal.nim`** — author-stated pin-to-pin conduction for a component whose `kind` alone cannot say it: an 8-pin RF switch (`designs/xbar_rf.nim`'s ADG904, `kind = "rf_switch"`) conducts `RFC` to whichever `RFn` is selected and nothing else, and neither of the two hard-coded walks that ask "can a graph walk pass through this component" — `kinds.classifyConductivity` (kind lookup in two fixed tables, anything else ambiguous) nor `schematic/composites/composite.isTwoTerminal` (true only for a flat two-connected-pin part) — has anywhere to hear that. A `traverse:` block in the component DSL (`netlist/dsl.handleTraverse`) is the third, explicit answer, and it **overrides** the other two rather than replacing them: a component that declares nothing takes its exact pre-feature path through both walks, which is what makes every design with no `traverse:` block behave bit-for-bit as it did before this module existed. Modelled directly on `layouthints.nim` — the accessor/validator split (`traversal`/`statesTraversal` are pure and total, absent-or-unparseable both reading as a zero spec; `validateTraversal` is the only place a bad value is ever reported) and the storage trade (namespaced `attrs` keys, so `clone`/`instantiate`/`flatten`/`extractSubcircuit`/`isolate` carry a spec for free and a SPICE round trip is expected to lose it). **Owns storage, grammar and validation only, deliberately not resolution**: `Conductivity` stays in `kinds.nim`, which already imports only `./types` while `schematic/layout.nim` imports `./kinds` — putting the fallback-ladder procs here would need `kinds` to import `traversal` and `traversal` to need `Conductivity` from `kinds`, a cycle. This module states conduction as a plain `bool` (`TraversalEdge.conducts`) instead, so it needs nothing from `kinds`; `kinds.conductivityBetween`/`conductiveExits` import `./traversal` and do the resolving (see that module's bullet for the fallback ladder). Three homogeneous `;`/`,`-delimited keys (`traverse.mode`/`traverse.paths`/`traverse.blocked`) rather than one key with a per-edge marker, so each stays a flat list the shape `switch.select_pins`/`spice.couples` already use; `-` is deliberately not the pin separator since `IN-`/`IN+` are real pin names in `spice/models/common.nim`. `TraversalMode.tmDefault` is the zero value and "nothing stated" at once, the `sideAuto` shape. An unknown *pin name* is `sevError` in `validateTraversal`, unlike `layouthints`' `sevWarning`: a bad rendering hint only draws the sheet worse, but a bad traversal spec silently changes what `dcReachable`/`dc_path_exists` conclude about the board. **The schematic side additionally splits `isTwoTerminal` from a widened `isTraversable`** (`schematic/composites/composite.nim`): every composite recognizer (`parallel`/`pi`/`tee`/`series`) keeps calling `isTwoTerminal` because each assumes a *unique* other net via `twoTermOtherNet`, which a declared multi-exit part would break, while only `constrained.pathsFrom`'s own semantic walk calls the widened `isTraversable` and its per-exit `traversalExits(c, nl, fromNet): seq[Net]` (declared edges from whichever pin sits on `fromNet` when `c` states a spec, otherwise `twoTermOtherNet` wrapped in a one-element `seq` — today's answer, unchanged).
- **`environment.nim`** — where the board lives, and how hot each part runs in it. Two numbers stand between the netlist and any temperature-dependent answer, and neither is electrical: the **board's** ambient range (`t_ambient_min`/`t_ambient_max`, netlist-scope, from an enclosure spec and the same for every part) and a **part's** rise above it (`delta_t`, component-scope). They are stated separately on purpose — the range is fixed when the product is specified, while a rise is a per-part consequence of a circuit that does not exist yet at that point, so folding them into one absolute temperature per part would mean restating the enclosure spec on every component with a copy to drift at each one. **It wires the two together and models nothing**: there is no tempco here, no capacitance- or ESR-versus-temperature curve, and the figures are deliberately **not** passed to the deck as `.options temp`, which would change how every semiconductor in the design behaves and would silently move every number this repo has measured. What it provides is the input such a model needs — `partTemperatureRange(c, env)` shifts the ambient range by the part's rise at **both** ends, since a dissipating part is above the air whatever the air is doing, and a board specified to -40 does not have to hold a self-heating regulator's ratings at -40 while everything that does *not* dissipate still does. Storage is `attrs` rather than fields on `types.nim` for the reason annotations always are, and here it is load-bearing: `clone` copies them, so the range and every rise survive `materializeSimNetlist`, `flatten`, `extractSubcircuit` and `isolate` — and a fragment cut out for simulation is precisely where a model pass will read them. `environmentOf` reads the **root**, so a child netlist gets the same answer as the board (a subcircuit has no weather of its own). **A part's rise defaults to 0 and says that it did**: `temperatureRise` returns `annDefaulted`, which is the one place a default is applied by an accessor rather than by a consumer, and it does not generalise — an unstated ESR and a zero ESR are different claims about a part, whereas an unstated rise and a zero rise agree for every part that is not dissipating. `deltaT` is still the pure accessor for anything that wants to see the absence, and `riseAssumption` phrases the default once for every consumer. `validateEnvironment` reports what was *stated* and cannot work — an inverted range, half a range, or a `delta_t` with no range to be a rise above — and never nags a design that stated nothing, since nothing consumes the range yet. Authored via the DSL's `environment:` block; `setOperatingTemperature`/`setDeltaT` are the runtime path a file reader takes.
- **`bomdefaults.nim`** — board-level procurement defaults for the parametric BOM compiler `docs/bom_compiler_plan.md` describes: `bom.tolerance`/`bom.dielectric`/`bom.series`/`bom.derating`/`bom.resistor_package`/`bom.capacitor_package`/`bom.inductor_package`/`bom.manufacturers`, a `BomDefaults` object resolved **most specific first, field by field** (`bomDefaults(nl)` reads each field from `nl`, then each parent up to the root — a parent's `bom:` fills only what a child sheet left unstated). There is deliberately no tree-wide override: a parent changes one instance's default via `instance ..., with = proc(sub: Netlist) = setBom*(sub, ...)`, which is why every setter writes to the netlist it is given and never to the root (inside `with` the clone already has a parent, and writing through would change the whole board). A `bom:` default never overrides a part's own `spec:` — changing one from above means naming that component in the same `with` proc; `verax/bom`'s resolver enforces the order. It is the third board-wide default family this submodule carries, alongside `environment.nim` (an *electrical* fact, `t_ambient_max`, registered in `annotations.builtinAnnotations`) and `layouthints.nim` (a *rendering* hint, `layout.side`, never registered) — `bom.*` is neither, so it gets its own namespaced `attrs` family rather than joining either. `bomDefaultKeys` is the `const seq` both `netlist/dsl.handleBom` (the compile-time-strict `bom:` block, `layout:`'s shape) and this module's own parsers read, so a future key is added in one place. `bom/` (not yet built) sits above `parts/` and below `verify.nim`, so this module — like `layoutVariant` naming a `pcb/variant.LayoutVariant` it cannot import — authors the binding and leaves resolving it to a module that may depend back on `netlist/`. `BomDefaults`' fields are the bare zero-value convention `parts/types.Choice` already uses (an unstated field reads as `""`/`0.0`), not `environment.nim`'s `AnnValue`-wrapped provenance, because nothing here needs to distinguish "stated as zero" from "unstated" the way a temperature range does. `validateBomDefaults` (kinds prefixed `bom_default_`) reports only what was *stated* and cannot work — an unknown series name (checked against the four ladders `parts/series.nim` actually holds), a derating factor below 1.0, a negative tolerance — anywhere in the tree, naming the instance path, and never nags a board that states no policy, `validateEnvironment`'s restraint. Wired into `verify.readiness` beside `validateEnvironment`/`validatePackages`.
- **`packages.nim`** — one physical package, several channels that may live on different sheets. A dual op-amp is one chip, one footprint, one BoM line, one silkscreen designator; the netlist models it as N `Component`s (often two instances of one `subckt`, so `XL.U1` and `XR.U1` are separate objects in separate child netlists) that share only a `partNumber`. This module adds the statement *these sections are the same die*. Like `environment.nim` and `contract/design.nim` it **stores membership in namespaced `attrs`** (`package.ref`/`package.section`/`package.def`) rather than `types.nim` or a root registry: `graph.clone` copies `attrs` at every level, so membership survives `clone`/`instantiate`/`flatten`/`extractSubcircuit`/`isolate` with no new code — and a root registry of direct `Component`/`Pin` references would need remapping written and tested across all of those, with `extractInstance` (which clones a child alone) stranding it. A package **definition** (`PackageDef`: sections, per-section logical pins, global pins, a package-pin-id → `PackagePin` map) *is* a registry, keyed by part number, because only a full pinout lets `pcb/graph.addLand` resolve pad `"7"` on an NE5532 to section B's `OUT` and lets `pcb/bom` fall back to a shared part number when `Placement.component` is nil. Definitions hold **no procs** (a package computes nothing) so they could later be read from a file, and there are **no built-ins** — every multi-channel package is a specific part number, so `designs/lib/` owns the catalogue (`designs/lib/opamps.nim`), the line `parts/policy.nim` already draws. `assignSection` is the one writer; `packageInstance(defName, ref)` raises at the `let` for an unregistered definition; `pkg.section("A", "U1")` returns a `proc (Netlist)` for `instance ..., with =` (the cross-sheet path), `pkg.assign(nl, "A", "U1A")` is the flat path. **The global-pin check is by object identity, not by name**: in a stereo board both channels' `V+` nets are distinct `Net` objects sharing the name `VP` (clones of one template net), so `validatePackages` resolves each through `Pin.hierNet`/ports to the outermost net (`outermostNet`) and compares those — a name comparison passes a genuinely miswired board. `validatePackages` returns `Issue`s (kinds prefixed `package_`), wired into `verify.readiness` after `validateEnvironment`. **A SPICE round trip intentionally loses package metadata** — `attrs` never reach a deck, no synthetic device encodes package identity, and a reparsed netlist carries no `package.*` keys; a consumer that needs the packaging keeps the Nim source (`test_netlist_spice.nim` pins this).
- **`pinmux.nim`** — what each pin of a part is *allowed* to be. `PA5` on an STM32H563 can mux to `SPI1_SCK` or `SPI2_SCK` or `TIM2_CH1` but never `SPI3_SCK`; nothing said so, so a design wiring `{"sclk": "SPI1_SCK"}` was believed whatever string was typed, and routing a clock to a pin the silicon cannot reach it on is a board respin. A `PartPinmux` is a `PackageDef`-shaped registry — pure data, no procs, keyed by name with a part-number index, **no built-ins** (`designs/lib/stm32h563.nim` is the first catalogue entry). A capability is `(peripheral, signal)`, spelled `"SPI1.sclk"` in a table and split on the **last** dot; a bare `"GPIO"` is peripheral-less. The `port` statement stamps two namespaced pin attrs (`pinmux.peripheral`/`pinmux.signal`) from `peripheral = "SPI1"` and per-member `functions = {"cs_1": "GPIO"}`, and `pin ..., function = "ADC1.in3"` stamps them for a non-interface pin; `attrs` over a `Pin` registry for the reason `packages.nim` gives — `graph.clone` carries them through `instantiate`/`flatten`/`isolate` free. `connectPort` also now stamps `iface.def` on each port pin, which is what lets the check tell an `spi` port wired as `I2C1` apart. `validatePinmux(nl)` returns `Issue`s (kinds prefixed `pinmux_`), wired into `verify.readiness` after `validateInterfaces`: `pinmux_incapable` (the point of it) and the peripheral/double-book/duplicate checks are `sevError`; `pinmux_pin_unknown` is `sevWarning` unless the table declares `complete = true`, because an MCU table is transcribed incrementally and a partial one must stay usable. **Three load-bearing decisions.** *Explicit `peripheral =`, not inference* — intersecting each pin's candidate set would often work but cannot name the offending pin and silently accepts two ports that both resolve to SPI1. *A `nil` table means check nothing*, never "nothing is allowed" — every part with no registered table is unaffected. *`functions =` exists because a hardware NSS is one pin* — a second or third chip select is a software GPIO, genuinely not an SPI function, and checking it as one is wrong. Signal names in a table are the **interface** names (`cs`, not the datasheet's `NSS`), since the check compares against what a `port` wired against an interface def.
- **`interfaces.nim`** — scalar-net views for buses and declared interfaces. `bus.*` and `iface.*` attrs are the source of truth, so `findBus`/`findInterface` reconstruct after clone and hierarchy; in particular recovery takes a member bus's recorded width rather than assuming a parameterized definition's registry default. `promotePortDirections` copies child port direction and parent interface identity to instance pins, keeping shared-bus ERC valid across hierarchy. A shared signal may be genuinely released by all participants: it suppresses both multi-inout conflict and undriven findings, but never two `ptOutput` drivers. `interfaces/std.nim`'s SPI MISO uses that shape (`ptInOut` at a peripheral); map a wide signal with individual `signal_0` keys rather than one pin name. `narrow(i, signal, k)` / `narrow(i, signal, s)` return `i` with one wide signal cut to a single member (or a re-indexed slice) as a width-1/width-N bus — a **pure value-space** copy that touches neither the netlist nor the registry, so it survives `clone` and cannot rewrite `bus.index` the way `busOf` would; `{"spi": spi1.narrow("cs", k)}` in an `instance` block is how a child owning one member of a shared select bus is wired without per-signal `spi1.bus("cs")[k]` boilerplate, and `[](i, signal, k)` is the same member as a scalar. `wiringOf` and `addPorts` agree on child-side naming: a width-1 group is the bare `label`, a wider one is `label_0 … label_(N-1)`; `wiringOf(InterfaceView)` is built off `def.signals` directly (an earlier version recovered the signal by substring and silently dropped every wide-signal entry once the plain-interface overload member-suffixed). **A differential pair is nothing new here** — `interfaces/std.diffPairInterface`/`usb2Interface` are ordinary two-signal `InterfaceDef`s naming their signals `p`/`n`, and `addInterfaceArray` (`count = N`) is how a lane set is N independent pairs; `contract/roles/interconnect.diff_pair` and `contract/evaluators/diff.nim` are where the actual checking lives, since nothing about *declaring* a pair needed touching this module. `spiInterface` now `implies = @[RoleClaim(role: "spi")]`, the same one line `i2cInterface`/`diffPairInterface` already carry — `cs`'s width is commonly greater than 1 (`spiInterface(3)`'s three-member chip-select bus on `designs/spi_memories.nim`), and it is `contract/design.addImpliedRoles`, not this module, that fans a wide `cs` out into one `spi` role instance per member; see `contract/CLAUDE.md`'s `roles/digital.spi` bullet.
- **`formats/`** — pluggable file-format readers/writers. Every format module implements the same contract: `readNetlist(s: Stream, name = ""): Netlist`, `writeNetlist(nl: Netlist, s: Stream)`, plus `readNetlistFile`/`writeNetlistFile` path wrappers. Format modules only depend on the core types/graph API — the core never depends on a format. `formats/spice.nim` is the only format implemented so far (SPICE `.cir`/`.net` decks); a `formats/kicad.nim` can be added later using the same contract. `formats/common.nim` holds the shared `NetlistFormatError`.
- **SPICE specifics** (`formats/spice.nim`): parses positionally per SPICE's reference-designator-prefix convention (R/C/L/D/Q/M/V/I map to fixed pin-name templates via `deviceKindByPrefix`/`pinTemplates`, and the inverse `designatorPrefix(kind): char` derives the letter back from a `kind` string; `X`/`U` resolve against `.SUBCKT`/`.ENDS` blocks, supporting forward references and nested subcircuit-instantiates-subcircuit). `.MODEL` cards are stored verbatim in `Netlist.models` (passthrough, not structurally parsed); other simulation-control directives (`.OPTIONS`, `.TRAN`, `.PARAM`, ...) are topology-irrelevant and are skipped on read. Unrecognized device-designator prefixes fall back to generic `pin1..pinN` pins rather than erroring. Because raw SPICE has no native concept of pin *type* (power/ground/input/output), `Pin.kind` fidelity through a SPICE round-trip is best-effort only — this is an inherent format limitation, not a bug. `spiceValue(x: float)` is the one correct way to format a synthesized device value (always scientific with an explicit exponent — any format that could end in a letter is a silent-misread hazard, since SPICE reads a trailing letter as a unit multiplier). `parseSpiceMagnitude` is its partial inverse and the counterpart to `annotations.parseAnnFloat`, which *rejects* suffixes because an annotation is in SI base units — here a trailing letter genuinely is a multiplier, because this is what goes into a deck. It refuses two things rather than guessing: anything that is not purely a magnitude (`attrs["value"]` may hold a whole source spec like `"DC 0 AC 1"`, which is why the annotation registry documents that key as never parsed as a number, so only a caller that knows the kind makes the value a bare magnitude should ask), and **RKM notation, where a digit follows the multiplier** — `"2k2"`, `"4u7"`. An EDA tool means 2200 and 4.7 µ by those; **ngspice reads the multiplier and discards the trailing digits, giving 2000 and 4 µ — verified against ngspice-46, not assumed.** Since `value` reaches the deck verbatim, the simulator's reading is the one that gets simulated, so a static check that quietly picked the other would disagree with the simulation about the same part by 10%. `prefixByDeviceKind`/`pinTemplates` also carry `"vcvs" -> 'E'` and `"vccs" -> 'G'` **write-side only**, for `spice/models.idealOpAmp`; unlike `'A'`, an `E`/`G` line genuinely *is* positional and reads back correctly through the generic `pin1..pinN` fallback, so they are kept out of `deviceKindByPrefix` only because nothing yet needs to recover the named `IN+`/`IN-` roles from a deck. `spice/models` added three more write-side letters: `"vswitch" -> 'S'` (a positional four-node line, so a `pinTemplates` entry `1/2/C+/C-` and nothing else is needed), `"iswitch" -> 'W'` (the letter only — a `W` line's third token names a voltage source, like `F`/`H`), and `"mutual_inductance" -> 'K'`. A **`K` card carries no nodes at all** — it names two inductors and a coefficient — so `formatDeviceLine` has a dedicated branch for it keyed on `attrs["spice.couples"]` (the coupled inductors' graph designators), resolving each to its `deckDesignator` spelling at write time; the same verbatim-escape shape as `xspice.ports`, and baking the names instead would go stale the moment `flatten` or a rename touched a winding. **`deckDesignator(comp)` is what actually reaches a deck line, and the letter comes from `Component.kind` rather than from the designator the design wrote.** SPICE infers device type from that first letter and from nothing else, so a part whose designator disagrees with its `kind` is silently simulated as a different device — and the colliding designators are all ordinary ones: `FB` (ferrite bead) reads as a current-controlled current source, `BT` (battery) as a behavioural source, `J` (connector) as a JFET, `VR` (pot) as a voltage source, `TP` as a transmission line. Those fail loudly; the dangerous pair does not, since an inductor filed as `C12` reads as a *capacitor* and a resistor filed as `L7` as an *inductor*, both of which parse and simulate. This was not hypothetical — `designs/ts808_drive.nim` had `VR1` for its drive pot, and 250 kohm of feedback network was being emitted as a 250 kV source, so the stage measured a gain of 12 instead of 65 with nothing reported anywhere. The correct letter is **prepended, not substituted** (`FB1` -> `LFB1`, never `L1`): designators are unique as a set and a truncated one need not be, so substituting would merge `FB1` and `L1` into one device on a board carrying both. A `kind` with no known letter is left alone, since there is nothing to correct it against. `deckInstanceDesignator` does the same for a hierarchical instance, always spelling it `X` — the reader accepts `U` too because other tools emit it, but ngspice reads `U` as a uniformly-distributed RC line. Note the invariant was already enforced for parts the tool *synthesizes* (`transform.replaceComponent` derives its prefix, `probes` validates one) and only the authored path was unguarded. `writeNetlist` calls **`checkDeckDesignators`** on each level first, because graph uniqueness does not imply deck uniqueness: prepending the device letter is not injective, so a resistor designated `XA.R1` and one designated `RXA.R1` are two components in the graph and one line in the deck, which ngspice reads as a device defined twice. That was unreachable while designators were hand-written and short; `spice/flatten` makes generated dotted designators ordinary. Checked per level, since SPICE scopes designators inside a `.SUBCKT`, and it raises rather than renaming — there is no safe way to guess which one was meant. `writeNetlist`/`writeNetlistFile` take an optional `cards: seq[string]` (raw control/analysis lines, e.g. `@[".op"]`) written just before `.END`; empty by default, so plain topology output is unaffected. This is what `verax/spice/ngspice` uses to attach an analysis card without duplicating device-line formatting.
**A `component` may omit its label entirely** (`component kind = "capacitor", value = "100n":`), in which case `graph.addGenerated` picks the designator from `kind` at construction -- at construction rather than at macro expansion because `kind` is an expression and because a `for` loop's iteration count is not knowable to the macro. Numbering is **per netlist, not per design**, which is the property that makes it tolerable: a subcircuit gets its own `C1`, `C2`, so adding a part to one module cannot renumber another, and flattening prefixes with the instance path anyway. Hand-authored designators are respected (a netlist already carrying `R1`/`R2` generates `R3`), an explicit `designator =` still wins, and omitting both a label and `kind` is a compile error rather than a guess. Generated ones are marked `attrs["designator.generated"]` and listed by `graph.generatedDesignators`, because a designator is the join key to a board (`pcb/graph.bindComponent` raises on a mismatch), a BoM line and silkscreen text -- and a generated one is **positional**, so inserting a part earlier renumbers everything after it. Safe for a part nothing names and nothing places; wrong for anything already laid out. That is self-selecting: needing to refer to a part is the signal to write its designator.

  **`instance` takes `with = <proc (Netlist)>`**, run against that instance's own clone immediately after `instantiate` and before anything else sees it. It is what makes omitted designators safe rather than merely convenient: post-hoc override is the only thing that *forces* stable identifiers, and injecting the variation at construction removes the need to address an individual anonymous part at all. Inside the proc the only names in play are the module's own **local** designators -- few, author-controlled, and never leaving the module -- rather than a name that must be unique across the whole design and stable against edits. It composes with `for` and with closures, so a per-channel trim table is ordinary code — and it now also carries **section assignment** for a multi-channel package: `with = u10.section("A", "U1")` tags this instance's `U1` as section A of package `U10` (see `packages.nim`), the only way to say two `subckt` instances share one physical chip. It is a *construction* step, not a mutation of something already built, which is the same line `Component.simReplace` draws: a post-hoc hook adding a simulation view is fine, one that changes what the board *is* afterwards is not.

- **`dsl.nim`** — an opt-in Nim-macro DSL (`import verax/netlist/dsl`) for authoring a `Netlist` directly in `.nim` source instead of hand-calling `graph.nim` or parsing a file format. `netlist("name"): ...` builds a flat netlist from `net`/`component` (with nested `pin`) statements, optionally repeated or selected by a `for`/`if`/`case`/`when`; `subckt("name", [ports]): ...` builds a free-standing template `Netlist` (never registered into any parent), instantiated later via `instance designator, templateIdent, [portNets]`, which expands straight to `graph.instantiate`. Net/component names given as bare identifiers are bound as real Nim `let`s so later statements can reference them (a typo is a compile error); `kind`/`name`/`partNumber` are the only typed "known fields" and get direct field assignment, while any other `key = value` pair lands in that entity's `attrs` bag. `net`'s primary label may also be a bracket of names (`net [a, b, c], kind = ntSignal`) — a group of otherwise-identical nets read the same way a bracket already reads everywhere else in this DSL ("one of these per entry"), sharing `handleOneNet` with the single-net path so a group and a lone `net` statement stay one code path rather than two that could drift. Each entry still gets its own `addNet` call and its own bound identifier — a real `let` per name, evaluated at macro-expansion time over a literal list, unlike a `for` over a runtime seq of names, so every one of them stays addressable by identifier for the rest of the block exactly as a lone `net` statement's would. `name =` is refused on a group rather than silently applied to every member: it would give all of them the same SPICE name, and the only way that surfaces otherwise is `addNet` raising a duplicate-net error that points at the group, not at what caused it. The DSL only ever expands into calls on the `graph.nim` API — like everywhere else in this submodule, back-references are never hand-set outside `graph.nim` itself. A top-level **`environment:`** block states the board-level operating conditions (today the ambient temperature range); it is `spec:` at netlist scope and is spelled differently only because that is what it says — a range read off an enclosure specification is not a property of the netlist the way a net's rail voltage is, and the name is what keeps a design file legible when humidity or altitude is added beside it. A top-level **`bom:`** block states board-level procurement defaults (`netlist/bomdefaults.nim`) — `layout:`'s shape rather than `environment:`'s, since `bom.*` keys are namespaced and owned by `bomdefaults.nim` rather than registered in `netlist/annotations`, so `handleBom` is its own strict, compile-time-checked handler rather than another `handleSpec` call. A `net` or `component` block may contain a `spec:` block, whose keys are validated against `netlist/annotations` **at compile time** — an unknown or wrong-scope key is a compile error naming the registered keys, and a `verax/units` literal inside it cannot be misread. Beside it, a **`notes:`** block (`handleNotes`) takes free-form pairs — an identifier or string-literal key, any value — and stores each under `annotations.notesPrefix` (`notes.<key>`), read back by `notesOf`/`noteOf`: namespaced, so never validated and never vocabulary to any consumer. It exists because the head-of-statement fallback stores a bare key, which `validateAnnotations` then flags as a likely misspelling; `notes:` is how an author says "this is mine, ignore it" without inventing a dotted key. `spec:` is the opposite of the permissive head-of-statement fallback, and deliberately so: the strictness boundary is syntactic, because inside `spec:` there is no open-ended bag for an unknown key to mean anything, exactly the reasoning that makes `xspice/dsl.nim` strict while this module is not. A `model "<name>", "<card>"` statement registers a `.MODEL` card (through `graph.setModel`, not a bare table assignment — `Netlist.models` is state `graph.nim` owns, and expanding to `nl.models[k] = v` would force every design file to `import std/tables` for a statement that has nothing to do with tables). The card body is **never parsed**: tracking every parameter of every device type in every SPICE dialect would mean getting one wrong silently simulates a different part, whereas passing it through means the simulator reads exactly what the datasheet said. What *does* read it is `kinds.hasDeviceModel`, which only asks whether the name is present — and that is what makes the statement matter beyond reaching the deck, because `isPassive` accepts a part with a model, so `spice/models` stops standing it in and `spice/isolate` will traverse it. Matched case-insensitively, as SPICE is. The TS808's clipping diodes are the case: without a card each became two 1 Mohm resistors to ground, and the pair shunted the inverting node with 500k — a second gain leg that lifted the stage's gain at the bottom of the sweep from unity to 4.2 dB, which is where a reported 31.6 dB of peaking came from against a real 35.3. **Parameterized circuits work, and the mechanism is that a `subckt` block is ordinary runtime code inside a `block` expression**: put it in a `proc`, compute values from the arguments before it, and reference them — `value =`, `designator =` and `name =` all take arbitrary expressions rather than literals, and `spec:` keys are validated at compile time while their *values* are expressions. `designs/lib/filters.nim` is the worked example. The block additionally admits **`for`, `if`, `case` and `when`**, and admits them as *control flow over DSL statements* rather than as an opening to arbitrary code: the loop header passes through untouched and the body is expanded by the same dispatcher, so everything inside is still a `net`/`component`/`instance`/`model`. A decoupling bank or a channel per lane is otherwise N nearly-identical lines, which is where a value gets corrected in one copy and not the others; build variants are otherwise two files that drift apart, or one file with the unused half commented out. A bare `discard` is an empty branch, since `if`/`case` need a body and "this variant adds no parts" is ordinary — `discard <expr>` is refused as arbitrary code wearing a keyword. Nothing is weakened by it — `spec:` keys are still validated at compile time and an identifier typo is still a compile error, because neither depends on whether the branch runs, and `addComponent` always raised on a duplicate designator at runtime anyway. Two things do not fit inside one: the `let` a `net`/`component` binds is scoped to the **branch or iteration**, so address anything generated there by name through `graph.findComponent`/`findNet` afterwards; and `role`/`require` are **rejected with a message**, because `design` hoists claims to after the netlist is built and a nested one would attach to a netlist that does not exist yet. `buildNetlistBody*` is exported as an extension point for a higher-level DSL that wants these statements plus its own (see `contract/dsl.nim`). A `component` block may additionally contain one or more `simReplace kind = "...", name = "...", suits = ...: pin ..., ...` statements (see `src/verax/spice/CLAUDE.md`) — each only ever *adds* to `Component.simModels`, so none of them mutates the component it's attached to, and a component-level `simDefault = "..."` names which one is used when nothing states a purpose. Several are told apart by `name`, and `suits` (a bare string or a bracketed list) is what says which question each answers; a duplicate `name` raises.
