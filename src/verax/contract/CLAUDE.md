# `contract` submodule

`src/verax/contract/` is design *intent*: what a circuit is meant to be and what it must do. It depends only on `verax/netlist`, so a design and its contract can be authored, read and inspected with no simulator in the build. `src/verax/contract.nim` is the hub (`types`, `roles/built_in`, `design`, `evaluate`, `evaluators/static`); `contract/dsl.nim` is opt-in per-import, the same rule everywhere else in this codebase.

**A role is a parameterized bundle of assertions, not a tag.** That is the whole model, and it is the thing that makes the layer extensible: a bare tag (`kind = "i2c"`) puts the meaning in whatever reads the tag, so a new protocol means changing this library, whereas a template puts the meaning in the definition. **The built-in roles use no privileged mechanism** — they are ordinary `RoleDef`s registered the ordinary way — because a built-in that cheats makes user-defined roles second-class and then nobody writes them. `tests/test_contract_roles.nim` pins that down by defining a role in the test file and checking it takes the identical path, and `designs/lib/i2c_parts.nim`'s **`i2c_transaction`** is the first one written outside this library and used by a real design: two `settled_v` claims on a controller's `done` and `verdict` pins, with `tSettle`/`tWindow` written into `Assertion.condition` exactly as `settledRailExpand` does. It exists because **every registered quantity is electrical** — a voltage, current, impedance, frequency, time or count — and there is no digital one, so the outcome of a protocol exchange reaches the report by being driven out through a `dac_bridge` and claimed as the voltage that arrives. The conditions are not decoration there: a bare `require settled_v(n)` gets `tSettle = 0` and a one-millisecond run, and that transaction spends five of them waiting on an EEPROM write cycle.

- **`types.nim`** — `Subject`, `Expectation`, `Assertion`. Three shape decisions carry the forward-compatibility story and should not be traded away: `subjects` is a **seq** (setup/hold is inherently one signal *versus* another, so a two-subject quantity must not be a special case bolted on later); `quantity` is an **open string naming an analysis `Measurement`** (`dc_voltage`, `bw_3db`, `z_min`); and `Expectation` is a **variant object**, so `ekRelative` (a bound referring to another measurement — "no more than a fifth of the primary filter") and `ekPredicate` (a Nim proc) are additive rather than a redesign. `satisfies` is the comparison every future evaluator shares, and a `NaN` never satisfies anything: "the measurement did not happen" must not read as a pass.
- **Why `quantity` is a `Measurement` name.** Evaluating an assertion becomes "run whatever analysis produces `bw_3db`, then compare", with one comparison shared by every quantity; the failing witness comes free, because the `Measurement` and its curve already exist; and a bench result is also a `Measurement`, so correlating measured against simulated is later the same comparison with a different source. It also keeps the coupling honest — a quantity nothing can produce is a claim nobody can check, and that shows up immediately.
- **`roles/`** — `roles/core.nim` is the machinery (the `RoleDef`/`RoleInstance` types, the registry, the `paramFloat`/`subject`/`assertionId` helpers); the built-in `RoleDef`s are split by category across `roles/power.nim` (`power_rail`, the `regulator` family, `settled_rail`, `current_path`, `source_sweep`, `load_sweep`), `roles/analog.nim` (`opamp_stage`, `gain_stage`, `channel_match`, `oscillator`, `large_signal`) and `roles/digital.nim` (`i2c`); and `roles/built_in.nim` assembles them into `RoleDef`s, houses `registerBuiltinRoles` and calls it at init. Import `roles/core` for the machinery alone; import `roles/built_in` (which re-exports `core`, and is what the hub, `dsl` and `design` import) to also get the built-ins registered. `RoleDef` has **two halves, deliberately separate**. `apply` writes annotations onto the netlist and is the half with a life independent of any checking: `spice/isolate` terminates a cut rail from `Net.attrs["voltage"]` long before anything asks whether the rail is *correct*, and if a role were only assertions, `isolate` would have to introspect the assertion list to recover a voltage. `expand` is pure and returns assertions. Both are **proc values on a data object**, not compile-time constructs, so a role built at runtime registers and behaves identically. Built-ins: `power_rail` (single-subject, and it replaces something real today), `i2c` (multi-subject, so part binding is actually exercised), `regulator`/`opamp_stage`/`gain_stage`/`large_signal`, which exist to bind the topology their own claims need, **`source_sweep` and `load_sweep`, the two ways to ask for a difference rather than a bias** (`source_sweep` binds a source the design already has and sweeps it; `load_sweep` binds nothing but the node, because the stimulus is a constant-current sink the analysis injects and a test load is not a part anybody solders -- and both put the swept range in `Assertion.condition`, so two claims over two ranges are two runs whose answers are not comparable), **`settled_rail`, which binds nothing at all** -- a net, a settling time and what the node must then be doing -- **`current_path`, the one built-in whose subject is a *component* rather than a net** (`isat`, `iRmsMax`, `iAvgMax`, `iRipple`, plus `maxIsatDerating`/`maxRmsDerating`, which state no current at all and read the part's own `isat`/`current_rating` back off it, so a substitution changes the limit in one place) -- and **`oscillator`, its counterpart for a circuit whose intent is instability**: what a node is *running at* rather than what it settled to (`osc_freq`, `swing_pp`, `osc_thd_pct`), with an optional `kick` part naming a node to put `kickV` on as an `.ic`, since a Wien bridge's operating point is a balance it sits in forever. `kick` is optional and so `spice.oscillator` declares no `binds`, which is right -- plenty of circuits are periodic without one, and `uic` is not free. Every `oscillator` claim is opt-in: there is no default frequency for an oscillator, and no default amplitude or distortion budget either. It is a separate role rather than parameters on `opamp_stage`/`gain_stage` because those are backed by an `.ac` sweep and every claim they make is about how far a stage is from oscillating -- and worse, the *measurement* does not survive the change of intent, since a sweep drives an ideal source onto the input net and a Wien bridge returns its positive feedback to exactly that node. That is what lets it reach the circuits the others cannot: `power_rail`'s `dc_voltage` is an operating point and an operating point has no ripple in it, so a switching converter's rail reads as its average by construction and would pass any ripple claim ever made about it; `regulator` is about the way up and needs a part to stand up as a ramp. Its `tSettle`/`tWindow` are **conditions, not limits** -- they say what was run, the answer is a function of them, so they ride in `Assertion.condition` and join the evaluator's setup key, exactly as `large_signal`'s drive level does. **`gain_stage` is `opamp_stage`'s AC-coupled counterpart and is a separate role rather than more parameters on it**, for two reasons: it claims against the band rather than against DC (see `analysis/opamp`), and it deliberately makes **no stability claim at all** — `peaking_db` cannot tell an intentional band-pass shape from resonance, and `opamp_stage` claims it unconditionally, so a single role could not offer both without forcing one. Stating both on the same stage is the supported way to get a margin *and* a band, and `designs/ts808_drive.nim` does exactly that. **`channel_match` is the first role whose subjects are two other role instances** rather than nets: its parts `a` and `b` are `RolePart(kind: skClass)`, bound with `roleRef("<instance>")`, and `channelMatchExpand` states its claims (`gain_delta_max_db`, `f_lo_ratio`/`f_hi_ratio`, `gain_delta_at_f` when `atF` is stated) with the two `skClass` subjects *themselves*. The evaluator dereferences -- an expander is pure and has no `Design`, so it cannot walk `a`/`b` into an amplifier and two nets, exactly the asymmetry `originRole` exists for. Ordering is load-bearing and enforced, not conventional: `design.resolve`'s `skClass` branch raises when the named instance is absent, so `channel_match` must be declared after the two stages. `roleRef` needs no macro change -- `dsl.subjectOf(Subject)` is an identity overload, so a helper returning a `Subject` routes as a binding. `designs/riaa_preamp.nim` is the worked example: two channels of one `subckt` measure a gain delta of exactly 0 dB, and a 1% feedback-resistor error on one channel moves it to 67 mdB. Its `atF` parameter moves the gain claim from `gain_max_db` onto `gain_at_f` and stamps the frequency into `Assertion.condition`, which is the only channel an assertion has for it — a start-up or loop-gain measurement needs a component designator the assertion's subjects do not carry, and the role is where that comes from. Optional parameters expand a claim only when stated: `power_rail`'s `targetZ` adds the PDN impedance assertion, and omitting it adds nothing, because a decoupling target follows from the load's transient current and inventing a default would manufacture a claim the designer never made and then report it as theirs. **`without` is reserved on every role**, and is the one parameter no role declares: it names claim suffixes this instance does not make (`without = "phase_margin"`, comma-separated for several). A role's always-claims are otherwise unconditional, and some do not fit every circuit the role otherwise describes — `opamp_stage` claims `phase_margin_deg`, `analyzeLoopGain` cannot open a Sallen-Key's loop, and the claim can then only ever come back unchecked. Carrying an unmeasurable claim in every run is its own harm, since `NOT CHECKED` is precisely the section that must not become background noise; forking the role instead is how a shared vocabulary dies. Declining is **not** silence: `explain` prints `declines ...`, and a suffix matching nothing **raises** rather than quietly leaving the claim in place — the same hazard as a misspelled annotation key, and `addRole` catches it by expanding once, which is free because an expander is pure. Everything that reads a design's claims goes through `expandInstance`, so what `explain` prints and what `evaluate` checks cannot drift. Role *parameters* carry their defaults in the expander, not the registry — a defaulted *design annotation* is a silent-drift hazard worth keeping visible and should not be blurred with a role default.

  **`regulator`, `linear_regulator` and `switching_regulator` are one role specialised twice, not three roles.** `regulator` carries everything a regulator is asked whatever it is made of -- the way up (`final_v`, `overshoot_pct`, `rise_time_10_90`, `inrush_peak`, `settle_time`), a **load step**, **ripple rejection**, and its **output current against the part's own rating** -- and the two specialisations call `regulatorExpand(inst)` whole before adding what only their topology is asked (`linear_regulator`: dropout, line and load regulation, DC output resistance, all through `spice.dc_sweep`; `switching_regulator`: output ripple, switching rate, inductor peak and saturation derating, all through evaluators that already existed). A claim added to the base reaches all three and cannot drift between them. The parts and params are shared through module-level `let`s because `RoleDef.params` is what `Design.validate` checks a stated parameter against: a specialisation that forgot to re-declare `maxDroop` would reject a design using it, with a message about an unknown parameter that is in fact perfectly good.

  Four things about them are worth not rediscovering. **Every new claim is `hasParam`-gated on its own limit**, and nothing is gated on the *step* or the *frequency*, which is `source_sweep`'s shape: the magnitude is setup, so it rides in the conditions and a claim stated without one is refused by the evaluator with a message naming what is missing. Gating a group on its magnitude also hides it from `verify.claimingRoles`, which expands each parameter alone and would then never have a step and a limit at once. **Which PSRR method runs is decided by which limit is stated** -- `minPsrrDb` is the `.tran` tone, `minPsrrBandDb` the `.ac` sweep -- and not by a `psrrMethod` string, for the same `claimingRoles` reason: it expands with the placeholder `"1"`, a float placeholder still selects a branch and a string one selects nothing, so a string mode parameter made every `.ac` quantity report as claimable by no built-in role at all. `psrrAtF` then *redirects* the swept claim from `psrr_min_db` onto `psrr_at_f` rather than adding a second one -- the `gain_stage`/`atF` pattern, and two claims about one curve would be one claim that can only ever be the weaker. **The output-current claims are made about the bound `sense` part, not about the regulator**, which is forced rather than chosen: a regulator reaching the deck as a code model or a subcircuit instance has no terminal current of its own to probe, and what carries its output current is the inductor after a buck or the pass element inside a linear's loop model. And **the conditions are stamped inside the `template`, at every exit**, not in a trailing `for a in result.mitems` -- these expanders have many more exit paths than the four `regulatorExpand` was written around, and a condition applied at only some of them is a claim quietly planned into a second simulation run.
- **`design.nim`** — `Design` **owns** a `Netlist`, exactly as `Pcb` does and for the same reasons; `netlist(...)` returns a bare `Netlist` with nowhere to hang design-global data, and nothing is added to `netlist/types.nim`. Role **membership** is the exception and lives on the entity (`net.attrs["role.i2c0"] = "sda"`) so it survives `clone`/`extractSubcircuit`/`isolate` — including `isolate`'s rename of ground to `"0"`, which a name-keyed side-car store would have lost. A subject may address something **inside a subcircuit instance** by a `hierSep`-separated path, resolved through `graph.find*`: a stereo board is one channel instanced twice, and a claim about the left channel's amplifier has no other way to say which amplifier it means — the identifier was bound inside a `subckt` in another module and is long out of scope at the design site. `Component.innerComponent`/`innerNet`/`innerPin` build the `Subject`, walking the child *immediately* so a typo raises there naming what the instance actually contains. A one-line `subjectOf(Subject)` identity overload opens the DSL's existing `when compiles(subjectOf(value))` binding test to them without the macro learning anything. Because `find*` tries the flat key first, the same name resolves before `spice/flatten` has run and after. `roleRef(name)` is the same one-line trick for the other direction: it returns `Subject(kind: skClass, name: name)`, so a role can bind *another role instance* as a part (`channel_match`'s `a`/`b`). `resolve`'s `skClass` branch resolves to no netlist entity -- `tagMembership` therefore tags nothing, which is right -- but **raises when the instance does not exist**, and that is what makes "declare the referenced roles first" an enforced ordering rather than a comment; `validate` already rejects a `skClass` part bound to a net because the kinds differ. `explain` prints what every role expanded to; that is not a nicety, since assertions generated on your behalf that you cannot inspect are how a contract layer turns into filler that always passes.
- **`dsl.nim`** — `design(...)` accepts everything `netlist(...)` does (reusing `buildNetlistBody`, not duplicating it) plus `role` and `require`. **Part bindings and parameters are told apart by type, not position**: the expansion routes each `key = value` with `when compiles(subjectOf(value))`, so a `Net`/`Component` is a binding and a quantity/number/string is a parameter. That keeps the syntax flat without the macro consulting the role registry, which is a runtime table it cannot see; a wrong *name* is still caught, by `addRole`. `require` is spelled with ordinary Nim comparisons over `quantity(subjects)`, and the unit is taken from the literal so it cannot drift from the value.
- **Not an expression language, deliberately.** Almost every claim is "quantity Q of subjects S under conditions C lies in interval I". When it is not, the escalation is: put the arithmetic in a Nim proc emitting a *derived quantity* (SPI setup margin is a computation over datasheet numbers, not a measurement), then `ekRelative` (a bound that references another measurement — `number * measurement` on the right of `==`/`>=`/`<=`), then a Nim predicate (`require pred(a = ..., b = ...) do (a, b: float) -> bool: ...`). **Nim is the expression language** — the predicate is a non-capturing proc, so the macro needs no parser, no evaluator and no bespoke error messages. Both are additive `ExpectKind`s, spelled in `docs/authoring.md`, and the planner decomposes either into hidden measurement requests rather than teaching evaluators about them.
- **`evaluate.nim`** — the checking half. An `AssertionResult` carries pass / fail / **notEvaluated** / **notEvaluable** and is deliberately **not** an `Issue`: `Issue` cannot say "checked, and it is fine" or "could not check", and silence meaning pass is how assertion systems become theatre. The two negative statuses are not interchangeable — `notEvaluable` means nothing can produce this quantity for these subjects, `notEvaluated` means an evaluator exists but did not run or did not return a number (its capability was withheld, the simulation raised, the measurement came back `NaN`).
- `Evaluator.binds` names the role *parts* an evaluator reads back off `Assertion.origin`, beyond the assertion's own subjects — declared rather than inferred, for the same reason `BehavioralModel.passesSignal` is: something has to answer "can a bare `require` reach this quantity?" **without running anything**, and only the evaluator knows. Empty means the subjects suffice (a `dc_voltage`, a PDN sweep); non-empty means the quantity is reachable *only* through a role that binds those parts. That is what `verax quantities` reports in its third column, and the three answers there — `require`, `role: X`, `-- needs a role binding` — are genuinely different, since conflating any two is how a reader writes a claim nothing will check. **An evaluator's only argument is an `EvalContext`**, and that is deliberate rather than incidental: `EvalProc` is the plugin ABI, so anything an evaluator might ever need has to be reachable through it. A bare `Design` was not enough, and three things had already found side doors — a shared operating point in a module-level `var`, the offered capability set known to the planner and not to the evaluator, and no route at all for a `Pcb` or a bench reading. The context carries `design`, `allowed`, and a **type-erased `scratch: Table[string, RootRef]`**; type-erased because `contract` may not name an `OperatingPoint` or a `Pcb` without gaining an edge to `analysis` or `pcb`, so a module that owns such a type declares `ref object of RootObj`, stashes it under a dotted key it owns, and downcasts on the way out. That keeps the layering intact *and* stops the context itself needing a new field every time something new needs carrying. A context lives exactly one run, which is what turns "one `.op` per design" from a documented rule into a guarantee — see `analysis/operating`. `plan(d, allowed)`/`evaluate(d, allowed)` remain as overloads that build a fresh context per call, which is the right default for a caller sweeping many candidate designs. **`Evaluator.needs` is a `set[Capability]`, not one.** More than one built-in genuinely needs two and had no way to say so while it was a scalar: `spice.pdn` declared `.ac` and solved an operating point for its bias derating, `spice.large_signal` declared `.tran` and solved one to find the bias its stimulus sits on, and under `--caps=ac` or `--caps=tran` each ran an analysis the caller had withheld. Under-declaring is invisible while every capability happens to be available and becomes a wrong answer the moment one is not — which is exactly what a bench host is. The gate is `ev.needs <= allowed` and the rejection names the missing ones by label (`needs the .op + .ac capabilities`). An empty set is normalised to `{capStatic}` by `registerEvaluator`, since an omitted declaration must never read as "runs everywhere". **Evaluation is planned before it is run.** Quantity-to-evaluator is **many-to-one** — `analyzePdn` emits eight measurement names from one `.ac` — so an `EvalProc` takes a *batch* and `plan` groups assertions by `(evaluator, setupKey)`. "One analysis run per distinct setup" is therefore a property of the planner, provable by counting steps, rather than something each evaluator reimplements; a single `.op` answers every `dc_voltage` claim in a design. `plan` is pure and `explainPlan` prints it, for the same reason `explain` exists: an assertion set you cannot inspect before it executes is the failure mode this layer is meant to prevent. **`ekRelative` and `ekPredicate` never reach an evaluator.** `plan` turns each into hidden measurement requests — the left-hand measurement and every named dependency as plain assertions carrying a `\x1f`-prefixed id in `Plan.hidden` — routed through the identical evaluator path, plus one `ResolveStep` that folds them back into the single authored claim. `resolveHidden` compares the two values (or runs the proc), propagates a dependency's `esNotEvaluated`/`esNotEvaluable` and its `assumptions`/`issues`, and checks the two measured units against each other; `evaluate` and `readiness` then report exactly one result per authored claim and never surface a hidden request. The evaluator ABI (`EvalProc` over a batch of plain assertions) is untouched, so an existing or third-party evaluator cannot even see that a claim was relative.
- **Setup topology is recovered through `Assertion.origin`.** `overshoot_pct(vdd)` names the rail but not the regulator driving it, and `analyzeStartup` needs both. Since `roles.nim` stamps the role-instance name into `origin`, an evaluator reads the bindings back off `Design.roles[origin]` — a role already knows its own topology, so its claims do not have to restate it. Resolution order is subjects, then origin-role bindings, then `condition`, then `notEvaluable` **naming what was missing**; that message is the product when a claim cannot be checked. This is what made the simulated adapters possible without redesigning the core. `subjectRole`/`subjectRoleBinding` are the subject-side pair, for a multi-subject quantity whose subjects are `skClass` references: `originRole` answers "the role that *expanded* this", these answer "the role a subject *points at*". Both return `none` rather than raising, so the evaluator writes the refusal that names what was missing.
- **`registerEvaluator` raises when a quantity is already produced by a *different* evaluator.** `quantityIndex` is a flat map, so a second registration would take over every claim on that quantity in every design with nothing said -- the same quantity name in the report either way and a different analysis behind it. Re-registering under the *same* name still replaces, because that is the documented way an application overrides a built-in: an override says so by keeping the name, a collision is an accident, and once it has happened the two are indistinguishable. `verdict()` is the single place pass/fail semantics live, so every evaluator gets identical behaviour. Its two *declining* paths — `NaN` and unit mismatch — carry the analysis's `assumptions` **and `issues`** out with them, for exactly the reason `failBatch` does: `reason` is written inside `verdict` and cannot name a cause `verdict` does not know, while the analysis that produced the `NaN` usually does know and said so in an `Issue`. Dropping those stranded the diagnosis — a Sallen-Key's phase margin read `the quantity was not found in the range that was analysed`, which is true and sends the reader to widen a sweep that is not the problem, while the issue one field away said the loop break never opened the loop. Three decisions are pinned there: a **`NaN` measurement is `notEvaluated`, not `esFail`** (`satisfies` guarantees `NaN` never *passes*; this goes further and declines to call it a failure, because `z_antiresonance = NaN` means no interior peak was found, which is the good outcome), and a **unit mismatch is `notEvaluable`** rather than a silent comparison of volts against hertz.
- **`evaluators/static.nim`** — the producers for the `i2c` role's quantities, needing no toolchain. Two are worth reading for what they decline to answer: `controller_count` returns `notEvaluable` with no role binding, because every device on an I2C bus has an inout data pin and nothing in a netlist distinguishes the controller from a target; `rc_corner` rests on an invented per-pin bus capacitance and reports it as an `Assumption`, since a netlist carries neither trace nor pin capacitance. Assumptions ride on every result, and `invented(results)` answers "how much of this did we make up?". **`static.dc_isolation`** is the one two-net evaluator here (`arity: 2 .. 2`): `dc_path_exists(a, b)` is a breadth-first walk across `condConductive` parts only — a transformer, a diode or an IC stops it — so `require dc_path_exists(vpoe, poe5v) == 0` is how a coupled-inductor isolation barrier becomes a checked claim (`designs/xbar_poe.nim`). No simulator, no capability gate; it reads the design netlist directly, before any `simReplace` is applied.
- **`roles/interconnect.nim` and `evaluators/diff.nim`** — the `diff_pair` role and its four quantities, and the worked example of "a differential pair needs no new declaration mechanism". A pair is an ordinary two-signal `InterfaceDef` whose signals are named `p`/`n` (`verax/netlist/interfaces/std.diffPairInterface`/`usb2Interface`) — `diff_pair`'s parts bind to them by the same-name matching `addRoleFromInterface` already does, and a lane set is `iface lane, pairDef, count = N`, the existing interface-array mechanism producing N independent role instances. `diff_pair_symmetry` is real: `contract/evaluators/diff.compareLegs` walks both legs in lock-step through `kinds.conductiveExits`, one two-terminal series part at a time (a component with more than two connected pins is a branch, not a series element, and is excluded — the walk cannot and does not try to be a general topology comparison), comparing kind and, where a bare magnitude parses, value within 1%; a mismatch anywhere ends the walk and names the offending part in a `diff_pair_leg_mismatch` Issue, and reaching two dead ends together, or exceeding a 12-hop bound with every step still agreeing, both read as symmetric. `intra_pair_skew`, `z_diff` and `inter_pair_skew` (arity `2..high`, reached only by a bare `require` naming one net per pair — there is no grouping statement) are **registered but always `notEvaluable`**: skew and differential impedance are routing properties, and `pcb/` has tracks and a stackup with `epsilonR` but no length accumulation and no Z0 solver yet. Registering them anyway, rather than leaving them unregistered, is deliberate — `evaluableQuantities()` is what `verax quantities` renders and `didYouMean` ranks against, so a claim naming one gets a true, specific reason instead of "no evaluator produces X", which reads as "you made that up". `EvalContext.scratch` is the declared route for a future `Pcb` to reach these without `contract` gaining an edge to `pcb`. `addImpliedRoles` also gained a working `RoleClaim.binds` here — it existed as a field, unread, since `InterfaceDef.implies` was written; this is the use case (an industry-named `dp`/`dn` def still implying `diff_pair`, whose parts are `p`/`n`) that made reviving it worth the four lines.
- **Deferred with reasons**: `normalizeAnnotations` (foreign key -> canonical via `AnnDef.aliases`) waited for a KiCad reader, and now the reader exists (`pcb/formats/kicad.nim`) and *produces* the real collision the deferral was waiting for, rather than a guessed one — a footprint's `(property "Value" "10k")` lands in `Placement.attrs["kicad.Value"]` (`pcb/formats/kicad.readFootprint`), deliberately namespaced and never registered, and it is genuinely not always the same claim as netlist `value`: `"10k"` on a resistor is the same fact spelled twice, `"STM32F103"` on an IC is not a value in the annotation registry's sense at all. Writing the alias pass is still undone — it is a `netlist/annotations.nim` change with its own test surface, and this stage deliberately does not resolve it, only lands the real collision where the alias pass would have to look — a serialized intent format waits for the same reason. Runtime-loadable *evaluators* (a compiled-product goal) are deferred too, but the hedges that keep them possible — open `quantity` strings, proc-valued `expand`, plain-data assertions, a runtime registry — are already taken.
