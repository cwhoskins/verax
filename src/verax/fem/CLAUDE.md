# `fem` submodule

`src/verax/fem/` is the interface to an external finite-element field solver -- the only way to answer plane-shape, return-path, coupling and thermal-spreading questions that a lumped SPICE netlist cannot express. Like `verax/spice` it is a *simulator interface*, not a general solver: it owns the problem statement, the mesh vocabulary and the backend contract, and knows nothing about what question a field answers (`verax/analysis`'s job). It depends on `verax/pcb` (board geometry is the problem domain) and transitively `verax/netlist`; nothing depends back. `src/verax/fem.nim` is the hub over `types`, `mesh`, `backend`, `extrude`.

**Scope: electromagnetic *and* thermal, one contract.** `ProblemKind` covers electrostatic / magnetostatic / full-wave and steady / transient heat conduction. `Material` carries the constants for *both* physics in one object rather than a variant, because the same copper pour is a conductor in an EM problem and a heat-spreader in a thermal one, and a material type per physics is precisely how the two drift out of agreement about the same region.

**This is a skeleton, and two `pcb` gaps are why -- stated here, not worked around:**

1. **There is no `Pcb` reader.** `pcb/formats/` is a contract (`readPcb`/`writePcb`) with no implementation, so a board reaches `fem` only if it was built by hand in Nim. A KiCad or ODB++ reader is the prerequisite for `fem` being useful on a real design.
2. **`Zone` carries only its authored outline** -- `Zone.fills` does not exist (`pcb/types.nim`). A plane's real copper, with its thermal reliefs and clearances, is not in the model. Adding `Zone.fills` is documented there as purely additive; it is a separate task.

There is also **no backend** (MFEM is the intended first one) and **no mesher** (a mesh comes from a backend or a file). The backend-free parts are all in the hub; a solver backend will not be.

- **`types.nim`** -- `FemError` and the problem statement: `FemProblem`, `Region`, `Material`, `BoundaryCondition`, `Excitation`. `Region.outline` is a simple closed polygon in the board frame (X right, Y up, **metres**), `Region.net` a forward reference only. `newFemProblem` / `addMaterial` / `addRegion` are the builders; `addRegion` raises `FemError` on an unregistered material or a degenerate z-extent. **`validate` returns warnings, it does not raise** -- following `spice/xspice/build.checkAbi`, a silent pass must not read as proof a problem is well posed. Deliberately not modelled: anisotropic or dispersive materials (one `epsR`, not a tensor or Debye model), nonlinear temperature-dependent conductivity, radiation view factors, coupled multiphysics in one solve (an EM loss field feeding a thermal run is two `solve` calls with a caller in between).

- **`mesh.nim`** -- the solver-neutral `Mesh` (nodes, elements, region tags, named boundary-face sets). **No mesher lives here** -- meshing a 3-D geometry well is research-grade and every serious backend ships its own. **Coordinates are `float64` metres, not `pcb/units.Nm`**: a mesh node is a solver artefact that does not land on the 1 nm design lattice, and snapping it there is meaningless in the interior and wrong on a curved boundary. The single nm -> m conversion is at `extrude`; nothing downstream is integer. This is the same kind of unit call `src/verax/CLAUDE.md` records for keeping `pcb/units.nim` disjoint from `units.nim`. `check` validates a mesh a backend did not build itself. Deliberately absent: quality metrics, refinement, adaptivity, periodic node pairing.

- **`backend.nim`** -- the contract, the analogue of `spice/backend.nim`. Every backend implements `writeCase` / `solve` / `available` over these types. **`available()` has no counterpart in `spice/backend`, deliberately**: ngspice's backend never probes for its binary, which pushed the skip decision into 22 test files each re-implementing `findExe("ngspice")`; one proc on the contract keeps it in one place. `Field` is an **object variant over real/complex** (a static/thermal solve is real, a full-wave solve complex) -- reading a magnetostatic result as complex is not merely wrong, the branch has no `cvalues`. `[]` / `cplx` / `mag` / `db` mirror `spice/backend` so a reader who knows one knows the other. **The intended first backend is MFEM** (`fem/mfem`, not written), opt-in per import as `spice/ngspice` is.

- **`extrude.nim`** -- the one module importing `verax/pcb`. `extrudeCopper` turns tracks, pads and filled areas into extruded `Region`s with z-extents from the stack-up; `extrudeStackup` adds the dielectric; `problemFromPcb` assembles both plus their materials. A stroked track is approximated by its bounding box -- offsetting a centre-line to a filled polygon is the one geometry primitive `pcb/geometry` does not yet provide; `shFill` areas use their real (arc-flattened) outline. **`extrudeZones` refuses** with a `FemError` naming `Zone.fills`: meshing an authored outline as solid copper models a plane without its reliefs and clearances -- the class of wrong answer that looks plausible, and "refuse rather than guess" is the standing `spice/CLAUDE.md` rule. Deliberately not modelled: mask/paste as dielectric layers, component bodies as thermal masses, via barrels as conductors (a via is a `Hole`, not a `Copper`).
