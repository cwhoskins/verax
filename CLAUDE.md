# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Run all tests: `nimble test` (compiles and runs every `tests/t*.nim` file via `tests/config.nims`, which adds `src` to the path)
- Run a single test file: `nim c -r --path:./src tests/test_netlist_core.nim` (or `tests/test_netlist_spice.nim`, `tests/test_netlist_dsl.nim`, `tests/test1.nim`)
- Type-check a module without running anything: `nim check --path:./src src/nimcir/netlist.nim`
- Package metadata (version, license, dependencies) lives in `nimcir.nimble`; the library has no dependencies beyond the Nim standard library (`requires "nim >= 2.2.10"`)

## Architecture

`nimcir` is a proprietary-licensed Nim library. `src/nimcir.nim` is the top-level package module; it is intentionally *not* a re-export hub — submodules (`submodule.nim`, `netlist.nim`) are imported directly by their own path (e.g. `import nimcir/netlist`), not through `nimcir.nim`.

### `netlist` submodule

`src/nimcir/netlist/` models an electronic circuit netlist in memory and reads/writes it to netlist file formats.

- **`types.nim`** — the core, format-agnostic data model: `Netlist`, `Net`, `Component`, `Pin`, all `ref object`s. The graph is deliberately built with *direct object references* in both directions (`Pin.component`/`Pin.net`, `Net.pins`, `Component.pins`, `Netlist.parent`/`Netlist.children`) so it is fully walkable from any starting point — not just reachable through the name-keyed `OrderedTable` dictionaries (`Netlist.nets` by net name, `Netlist.components` by reference designator). Nim 2.x's default ORC GC collects the resulting reference cycles automatically. Every entity has an open-ended `attrs: OrderedTable[string, string]` bag for format-specific extras, keeping the core schema format-agnostic.
- **`graph.nim`** — the only place allowed to mutate the graph's back-references (`addComponent`, `addNet`, `addPin`, `connect`/`disconnect`, `addChild`, `addPort`, `clone`, `instantiate`). Code elsewhere must go through these procs rather than hand-setting `.net`/`.pins`/`.component`/`.parent` directly, or the bidirectional links will get out of sync.
- **Hierarchy model**: a "sub-netlist" is a child `Netlist` hung off a `Component` whose `subNetlist` field points at it (e.g. a SPICE `X`/subcircuit instance). `instantiate()` deep-clones a template `Netlist` per instance via `clone()`, so each instantiation gets independent `Net`/`Component`/`Pin` objects rather than sharing one template — except nets registered in the `globalNets` table passed to `clone`/`instantiate` (e.g. SPICE node `"0"`), which are reused as the *same* object across every hierarchy level to match real ground/global-net semantics. A hierarchical instance's pins connect normally to nets in the *parent* scope; each such pin's `hierNet` additionally points straight at the matching port `Net` inside `component.subNetlist`, so hierarchy boundaries can be walked in either direction without name lookups.
- **`formats/`** — pluggable file-format readers/writers. Every format module implements the same contract: `readNetlist(s: Stream, name = ""): Netlist`, `writeNetlist(nl: Netlist, s: Stream)`, plus `readNetlistFile`/`writeNetlistFile` path wrappers. Format modules only depend on the core types/graph API — the core never depends on a format. `formats/spice.nim` is the only format implemented so far (SPICE `.cir`/`.net` decks); a `formats/kicad.nim` can be added later using the same contract. `formats/common.nim` holds the shared `NetlistFormatError`.
- **SPICE specifics** (`formats/spice.nim`): parses positionally per SPICE's reference-designator-prefix convention (R/C/L/D/Q/M/V/I map to fixed pin-name templates; `X`/`U` resolve against `.SUBCKT`/`.ENDS` blocks, supporting forward references and nested subcircuit-instantiates-subcircuit). `.MODEL` cards are stored verbatim in `Netlist.models` (passthrough, not structurally parsed); other simulation-control directives (`.OPTIONS`, `.TRAN`, `.PARAM`, ...) are topology-irrelevant and are skipped. Unrecognized device-designator prefixes fall back to generic `pin1..pinN` pins rather than erroring. Because raw SPICE has no native concept of pin *type* (power/ground/input/output), `Pin.kind` fidelity through a SPICE round-trip is best-effort only — this is an inherent format limitation, not a bug. The writer emits topology only (no analysis/control cards); validating a generated deck by actually simulating it (e.g. with `ngspice -b`) requires adding a `.op`/`.print`-style analysis to the file first.
- **`dsl.nim`** — an opt-in Nim-macro DSL (`import nimcir/netlist/dsl`) for authoring a `Netlist` directly in `.nim` source instead of hand-calling `graph.nim` or parsing a file format. `netlist("name"): ...` builds a flat netlist from `net`/`component` (with nested `pin`) statements; `subckt("name", [ports]): ...` builds a free-standing template `Netlist` (never registered into any parent), instantiated later via `instance designator, templateIdent, [portNets]`, which expands straight to `graph.instantiate`. Net/component names given as bare identifiers are bound as real Nim `let`s so later statements can reference them (a typo is a compile error); `kind`/`name`/`partNumber` are the only typed "known fields" and get direct field assignment, while any other `key = value` pair lands in that entity's `attrs` bag. The DSL only ever expands into calls on the `graph.nim` API — like everywhere else in this submodule, back-references are never hand-set outside `graph.nim` itself.
