# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- **Check a design**: `nimble build` then `./bin/nimcir check designs/foo.nim`.
- **Designs** under `designs/`: `ts808_drive` (single-supply overdrive), `sensor_node` (LDO + I2C), `aa_filter` (4th-order Sallen-Key), `charge_pump` (Dickson doubler, whose `settled_rail` claim found a 403 mV edge spike across COUT's ESR and ESL where a hand-run with ideal capacitors reported 5.1 mV of droop), `wien_osc` (oscillator -- kicked into life with an `.ic`, then measured for rate, swing and distortion by the `oscillator` role), `riaa_preamp` (stereo, instancing `lib/riaa.nim` twice) and `lt8640a_buck` (the datasheet reference design, simulated through **two** Nim-authored XSPICE code models -- `lib/lt8640a_avg.nim` for the rail voltage and `lib/lt8640a_sw.nim`, peak current mode at fifty timepoints a cycle, for the ripple -- with `spice/transform.selectSimModel` picking by what is being asked) and `carrier` and `sensor_head` (each a **module when imported and a program when checked**, split by `when isMainModule`: a board states what is plugged into it for the bench, and `asSubcircuit` drops the connectors so those assumptions cannot leak into a system) and `system_sensor_rig` (both boards wired through an explicit cable — the design that found an 8.71 ohm anti-resonance neither board has on its own, on a sensor head that passed its own check by 30x) and `param_filter` (two Sallen-Key sections a decade apart, both built by `lib/filters.sallenKeyLP(fc, r, q)` — no component value appears in the design file, so the claims check the design equations rather than checking that somebody did the arithmetic twice), `divider_net` (a voltage divider and a current divider both stated as a **total impedance and a ratio**, and the three-resistor network that replaces the voltage divider's bottom leg with the current divider -- both taps must read the same 2.5 V, which is the substitutability property measured rather than asserted, and the split itself is read at a sense node two levels down inside the instance because both legs return to the same ground and nothing in the parent netlist witnesses it) and `adj_regulator` (two LM317 rails sized from the datasheet equations in `lib/adjreg.nim` -- the part is a *value* carrying its reference, ADJ current, range, dropout, minimum load and thermal resistance, and for simulation a `SimReplacement.build` swaps it for the **loop** it closes, an error amplifier holding the reference between OUT and ADJ plus a current source for the ADJ pin, so ngspice solves the divider in the netlist and nothing in the design file is compared against itself: drop the `iAdj*rAdj` term and the 5 V rail measures 5.036 V and misses its 0.5% band). Shared parts and subcircuits live in `designs/lib/`, which `nimble verify` does **not** pick up because `listFiles` is not recursive — they are compiled as dependencies of the designs that import them.
- **Seeing what was actually simulated**: `NIMCIR_KEEP_DECKS=<dir> ./bin/nimcir check <design>` copies every deck handed to ngspice into `<dir>`. The fragments are derived, not authored, so this is the only way to check a surprising number against the circuit that produced it. This is the primary loop — a design is an ordinary `.nim` file using `nimcir/contract/dsl` that ends with `quit(verifyMain(d))`, so `nim c -r --path:./src designs/foo.nim` is the same check without the wrapper (~1.1 s cold, ~0.7 s warm). Flags, forwarded to the design binary: `--offline`, `--caps=op,ac,tran`, `--verbose`, `--strict`. Exit codes are graded: `0` clean, `1` a claim failed, `2` structural problem, `3` a claim nothing could check, `4` a requested capability is unavailable here, `5` the design did not compile (only `nimcir check` produces `5`, and it is separate on purpose — told only "it failed", a reader edits the circuit to fix a syntax error).
- **Discovery** (works in a repo that is not this one, reads the live registries, writes nothing): `nimcir roles`, `nimcir role <name>`, `nimcir quantities`, `nimcir annotations`, `nimcir guide`, `nimcir env`, `nimcir new <blank|rail|i2c> <path>`.
- `nimble verify` checks every design under `designs/` and every file under `templates/`; `nimble guide` prints the authoring guide.
- Run all tests: `nimble test` — **and read the output, never the exit code.** `nimble` returns 0 whether the suite passed or not, verified both ways; the check that means something is `nimble test 2>&1 | grep -cE "FAILED|Error:"` returning 0. The `test` task in `nimcir.nimble` is written out by hand rather than left to nimble's built-in one, which *printed* a compile error and then exited 0 anyway — so a green run meant only that nimble itself had run, and three real failures across two files sat hidden behind it. The hand-written task at least aborts at the first failing file and prints it. compiles and runs every `tests/*.nim` file via `tests/config.nims`, which adds `src` to the path). The `nimcir/spice/ngspice` backend tests in `tests/test_spice_ngspice.nim` are skipped automatically (not failed) when `ngspice` isn't found on `PATH`; likewise `tests/test_xspice_build.nim` and `tests/test_xspice_digital.nim` skip unless `$NGSPICE_SRC` points at a *configured* ngspice source tree.
- Run a single test file: `nim c -r --path:./src tests/test_netlist_core.nim` (or `tests/test_netlist_spice.nim`, `tests/test_netlist_dsl.nim`, `tests/test_spice_probes.nim`, `tests/test_spice_transform.nim`, `tests/test_spice_extract.nim`, `tests/test_spice_ngspice.nim`, `tests/test_spice_ac.nim`, `tests/test_units.nim`, `tests/test_netlist_annotations.nim`, `tests/test_netlist_environment.nim`, `tests/test_contract_roles.nim`, `tests/test_contract_dsl.nim`, `tests/test_contract_evaluate.nim`, `tests/test_contract_eval_spice.nim`, `tests/test_spice_isolate.nim`, `tests/test_spice_models.nim`, `tests/test_analysis_io_check.nim`, `tests/test_analysis_spice_fallback.nim`, `tests/test_analysis_measure.nim`, `tests/test_analysis_pdn.nim`, `tests/test_analysis_startup.nim`, `tests/test_analysis_transient.nim`, `tests/test_analysis_opamp.nim`, `tests/test_pcb_units.nim`, `tests/test_pcb_geometry.nim`, `tests/test_pcb_core.nim`, `tests/test_pcb_index.nim`, `tests/test_pcb_bom.nim`, `tests/test_xspice_spec.nim`, `tests/test_xspice_ifs.nim`, `tests/test_xspice_dsl.nim`, `tests/test_xspice_instance.nim`, `tests/test_xspice_build.nim`, `tests/test_xspice_digital.nim`, `tests/test_verify_readiness.nim`, `tests/test_cli_discovery.nim`, `tests/test1.nim`)
- Type-check a module without running anything: `nim check --path:./src src/nimcir/netlist.nim`
- Package metadata (version, license, dependencies) lives in `nimcir.nimble`; the library has no dependencies beyond the Nim standard library (`requires "nim >= 2.2.10"`), and that stays true because the MCP server is a **separate package** under `mcp/` — "opt-in per import" is the rule everywhere else here, but a nimble dependency can only be made opt-in per *package*. `namedBin["nimcir/cli"] = "nimcir"` builds the binary from `src/nimcir/cli.nim` rather than `src/nimcir.nim`, so `import nimcir` in an unrelated program does not drag in the simulator, `osproc` and the whole analysis tree
- Run an example script (none are part of `nimble test`): `nim c -r --path:./src examples/divider.nim` (builds a netlist with `nimcir/netlist/dsl` and prints it as SPICE), `examples/pdn_sweep.nim` (decoupling impedance vs frequency), `examples/opamp_bode.nim` (closed-loop response and loop gain of an amplifier stage), `examples/design_contract.nim` (roles, annotations and requirements), `examples/xspice_gain.nim` / `examples/xspice_dff.nim` / `examples/xspice_integrator.nim` (XSPICE code models -- memoryless, event-driven and analog-state respectively; need `$NGSPICE_SRC`)

## Architecture

`nimcir` is a proprietary-licensed Nim library. `src/nimcir.nim` is the top-level package module; it is intentionally *not* a re-export hub — submodules (`submodule.nim`, `netlist.nim`, `spice.nim`, `analysis.nim`, `pcb.nim`, `contract.nim`, `parts.nim`) are imported directly by their own path (e.g. `import nimcir/netlist`), not through `nimcir.nim`.

Three package-root modules sit outside any submodule because the dependency order (`netlist` <- `spice` <- `analysis`, `netlist` <- `pcb`, `netlist` <- `contract`) gives them nowhere else to live — but for two different reasons. `units.nim` and `eng.nim` sit *below* every submodule: more than one needs them and none may own them. `verify.nim` sits *above* every submodule: it needs `contract` and `analysis` at once and neither may depend on it.

`src/nimcir/units.nim` is typed electrical quantities — `Volts`/`Ohms`/`Farads`/`Henries`/`Hertz`/`Seconds`/`Amps`/`Fraction`, plus `Degrees`, `Decibels` and `Celsius` which are not electrical and are here because the role registry declares `minPhaseMargin` in degrees and `maxPeaking` in dB, and a bare `50.0` in a list of unit literals is precisely the misread this module removes. A `Decibels` stores the dB figure rather than the ratio it denotes, because every consumer compares against a measurement already in dB. Note Nim reads `dB` and `db` as one identifier, so both spellings work. `Celsius` is the one type carrying two *different* quantities — an absolute temperature (`t_ambient_max = 70.degC`) and a temperature difference (`delta_t = 16.degC`) — which the key each is stated under distinguishes and which nothing here enforces, since this is deliberately not a dimensional-analysis system; `netlist/environment` is the only code that adds them. It is also the one type rendered **without** SI prefixes, because a half-degree rise printed `500 mdegC` is exactly the misread the module exists to remove, and there is no kelvin constructor for the same reason: `20.K` as a rise is 20 degC and as an absolute temperature is -253 degC, and one suffix cannot mean both. With suffix constructors (`3.3.V`, `20.mohm`, `600.pH`, `400.kHz`, `5.pct`) that scale to SI base units. It exists for one reason: `esr = 20.mohm` cannot be misread, whereas `"20m"` and `"0.02"` differ by a thousand and look equally plausible. **Deliberately not a dimensional-analysis system** — no unit arithmetic, no derived units, no compile-time dimension checking; adding those is a much larger design that buys nothing for the job at hand. Distinct from `pcb/units.nim`, which is board *geometry* (`Nm`/`Deg`); the type names and suffixes are disjoint.

`src/nimcir/eng.nim` is the one package-root helper: `eng(x, unit)` renders a float in engineering notation with an SI prefix (`20.1 mohm`, `600 pH`, `15.9 MHz`) for report text and messages. It sits at the root because both `spice` and `analysis` need it and `analysis` already depends on `spice`. It is **presentation only** — a value written into a deck must go through `netlist/formats/spice.spiceValue`, which always emits an explicit exponent, because SPICE reads a trailing letter as a unit multiplier (`15.9M` in a deck is 15.9 *milli*).

`src/nimcir/verify.nim` is the runner: it checks a `Design` and renders one *readiness report*. It is the only module that imports `contract` and `analysis` together, which is why it cannot live in either — `contract` must never gain an edge to `analysis`, since a design staying inspectable with no simulator in the build is what that separation buys.

**It imports `analysis/contract_eval` unconditionally, and that is the point.** Without it a perfectly good requirement reports `no evaluator produces 'z_max_in_band'` — which is false; `spice.pdn` produces it, the module registering that evaluator merely was not imported. A reader who believes the message deletes a correct requirement. With one entry point that always registers the simulated evaluators and gates on *capabilities* instead, the same claim reports `requires capSpiceAc, which was not offered` — true, and it says what to do about it. What is *offered* remains the caller's choice (`allowed`), so nothing is forced to simulate.

The report reads back the design's stated `environment:` — the ambient range and the hottest part in it — and only when it was stated: nothing is temperature-dependent yet, so nagging every design would be noise, but a premise quietly carried is a premise nobody checks. The report is **rendered fresh, not composed** from `report`/`summary`/`explainPlan`/`explain`. Each of those answers one question in isolation and each re-lists the same assertions, so concatenating them prints one failing claim three times; the ordering and de-duplication *are* the product. Sections run in order of how much each undermines everything below it — structure, **checks**, failures, **not checked** — and `NOT CHECKED` is the centre of gravity, never collapsed: an assertion nobody evaluated is not one that passed, and silence reading as approval is the failure mode the contract layer exists to prevent. A failed or unchecked result also prints any `Issue` attached to it, **de-duplicated across the whole report** — evaluation is batched, so one loop-gain run's diagnosis rides on every claim in its batch and would otherwise print once per claim. A *passing* result's issues are not printed: it passed.

**The body is `CHECKS`: one block per *test*, where a test is one analysis run.** That grouping is the plan step seen after running, and it is the only one that recovers three facts a flat list of results loses — which claims came out of one simulation (so a single wrong setup explains all of them at once), what that simulation *was*, and which invented values it rested on. It cannot be recovered after the fact: an `AssertionResult` carries its evaluator's name but not its setup key, and two steps of one evaluator are two different runs. So `readiness` goes through `runPlan` (which returns one `seq` per step) rather than `evaluate` (which flattens), and `Readiness` gained `checks: seq[Check]` and `rejected`, with `results` kept as the flat concatenation so `summary`/`failed`/`invented` go on working. Each block carries three things. **`ran:`** — what was actually simulated, from a new `Evaluator.setupDoc` proc field beside `setupKey`; the key exists to *group*, and `vdd|100000.0|100000000.0` is a correct key that says nothing about what was simulated, while the fragment handed to ngspice is derived rather than authored and so needs saying. A `nil` `setupDoc` falls back to the key, and one that raises is caught, on the same reasoning as `previewRole`. **`assuming:`** — the batch's own assumptions, deduplicated, `annAuthored` excluded. Pooled at the foot of the report they said forty values were invented *somewhere* and left the reader to work out which number each one moved; under the run that rests on them the question is answered. `foldAssumptions` collapses records sharing `(key, value, unit, detail)` onto one line naming every entity — lossless, and it took one design's PDN block from 39 lines to 21, which is the difference between a list read and a list skipped. That is also why `annotations.note` gained a `note(entity, detail)` overload: a designator baked into the sentence cannot be folded on, and `$Assumption` renders the two forms identically. **The claims** — one identity line (id, quantity, subjects, and `conditionText`, which spells `[f_from=100k, f_to=100M]` as `over 100 kHz .. 100 MHz`), one comparison line putting `expect` and `measured` together with `acceptance` rendering a tolerance as the interval it accepts, and `because …` — `Assertion.rationale`, which was previously printed nowhere at all — whenever the claim did not pass. `FAILED` and `NOT CHECKED` render through the same `renderClaim`, so a limit is not spelled two ways in one report, and claims that reached no test are counted in `CHECKS` but listed only under `NOT CHECKED`, since printing them twice teaches the reader to skip one of the two places. `capLabel` moved to `contract/evaluate` so a withheld capability reports `needs the .op capability` rather than the enum identifier `capSpiceOp`. A `Readiness` holds `AssertionResult`s and `Issue`s and **never an `AnalysisReport`** — `AssertionResult` has no field for one, so `raw`'s thousands of curve points cannot leak in; a test pins the rendered size so a future "attach the curve for context" change fails loudly.

Two things it reports that nothing else can. `didYouMean` ranks `evaluableQuantities()` by edit distance when nothing produces a quantity, because a misspelling is the likeliest way to write an uncheckable claim and `no evaluator produces 'z_ripple'` alone says the door is locked without mentioning a door exists. And `claimLint` catches a claim that states no unit against a quantity measured with one: `unitsAgree` treats an empty unit as "not stated, therefore unchecked", which is right for a bare count like `pullup_count` and dangerous elsewhere — `unitOf(Fraction)` is `""`, so `require overshoot_pct(vdd) <= 5.pct` compares 0.05 against a measurement of 5.0 and is wrong by a hundred with nothing said. The real fix is a `units` field on `Evaluator` parallel to `produces`; until then this reports it after the fact rather than comparing silently.

`describeQuantities` reports *reachability* alongside each quantity, computed by `claimingRoles()` — which expands every registered role with every parameter stated, and then each parameter on its own, because a parameter can **redirect** a claim rather than add one (`gain_stage`'s `atF` moves the gain claim from `gain_max_db` onto `gain_at_f`, so either expansion alone hides a branch the other shows). Computed rather than written down for the same reason `previewRoleDelta` is: a hand-kept list is exactly the thing that drifts from the expanders, and this is the answer a reader is about to act on. Listing quantities without it invited the obvious mistake — ten of twenty-six were unreachable by any built-in path and nothing said which. `verify.nim` also holds the **catalog** — `describeRoles`/`describeRole`/`describeQuantities`/`describeAnnotations`, rendered to strings rather than printed because the CLI echoes them and the MCP server returns them. `previewRole` expands a role against placeholder bindings (safe: `RoleExpander` takes only a `RoleInstance` and never touches a netlist — that is exactly what separates `expand` from `apply`), and `previewRoleDelta` finds which *parameter* buys which extra claim by diffing two expansions, so that documentation cannot drift from the expander. An expander that raises yields nothing rather than propagating: a third-party role must not make `nimcir roles` unusable.

`src/nimcir/cli.nim` is the `nimcir` binary — thin over the above, with one piece of real logic: it locates nimcir's sources for `--path:` through a chain of *validated* candidates (`--path:` flag, `$NIMCIR_PATH`, a repo checkout found by walking up for `nimcir.nimble`, the compile-time `currentSourcePath()`, `nimble path nimcir`), falling back to passing no `--path` at all, which is correct for a design repo that has run `nimble setup`. Each candidate is checked for `nimcir/contract/dsl.nim` rather than trusted — nimble builds a package that declares binaries inside a temporary directory and deletes it afterwards, so the compiled-in path can dangle for an installed copy. It compiles and runs a design as **two processes, never `nim c -r`**, because that merges "this file does not compile" with "an assertion failed" into one exit status.

The trap that made this necessary, recorded because the fix is easy to undo: `voltage_source` is in `kinds.conductiveKinds`, so `isPassive` is true and a PDN isolation *absorbs* a supply rather than cutting it — and an ideal source is a dead short at AC. Verified empirically, the same rail measured 129 mohm with no source and **0 ohm with one**, passing every target that could be set. `spice/models.expandSourceImpedance` is what stops that, and removing it silently restores a check that always passes.

### `netlist` submodule

`src/nimcir/netlist/` models an electronic circuit netlist in memory and reads/writes it to netlist file formats.

- **`types.nim`** — the core, format-agnostic data model: `Netlist`, `Net`, `Component`, `Pin`, all `ref object`s. The graph is deliberately built with *direct object references* in both directions (`Pin.component`/`Pin.net`, `Net.pins`, `Component.pins`, `Netlist.parent`/`Netlist.children`) so it is fully walkable from any starting point — not just reachable through the name-keyed `OrderedTable` dictionaries (`Netlist.nets` by net name, `Netlist.components` by reference designator). Nim 2.x's default ORC GC collects the resulting reference cycles automatically. Every entity has an open-ended `attrs: OrderedTable[string, string]` bag for format-specific extras, keeping the core schema format-agnostic.
- **`graph.nim`** — the only place allowed to mutate the graph's back-references (`addComponent`, `addNet`, `addPin`, `connect`/`disconnect`, `removeComponent`, `addChild`, `addPort`, `renameNet`, `clone`, `instantiate`). `renameNet` rekeys `nets` and sets `Net.name`, leaving `ports` *keys* alone (a port name is the published interface, independent of the net behind it); it exists because `spice/isolate` has to promote some rail to SPICE node `"0"`, which means nothing until the net is actually named `"0"`. Code elsewhere must go through these procs rather than hand-setting `.net`/`.pins`/`.component`/`.parent` directly, or the bidirectional links will get out of sync.

  It also owns **hierarchical naming**: `hierSep` is `'.'`, `hierName` joins with it, and `findNet`/`findComponent`/`findPin` resolve a `hierSep`-separated path — **flat key first, then descending into `children`**. That ordering is what lets one call serve an authored hierarchy and a flattened one alike, so nothing holding such a name has to know which it is looking at. `findPin` searches split points **right to left**, longest component prefix winning, because both halves may contain a dot (XSPICE names a differential port's pins `name.p`/`name.n`). `adoptNet`/`adoptComponent` re-home an existing object under a new name rather than copying it — every `Pin.net` back-reference and every `attrs` entry, including the `role.*` tags that must outlive a transform, comes along untouched. `mergeNets` folds one net into another, which is what a subcircuit port *is* once the hierarchy is gone. `registerGlobalNet` exists for the same reason `setModel` does: `global = true` expanded to a bare `globals[name] = net`, which forced every design using it to `import std/tables` — and that went unnoticed until the first design with a subcircuit, because the statement is only worth making when there is a child to share a net with.
- **Hierarchy model**: a "sub-netlist" is a child `Netlist` hung off a `Component` whose `subNetlist` field points at it (e.g. a SPICE `X`/subcircuit instance). `instantiate()` deep-clones a template `Netlist` per instance via `clone()`, so each instantiation gets independent `Net`/`Component`/`Pin` objects rather than sharing one template — except nets registered in the `globalNets` table passed to `clone`/`instantiate` (e.g. SPICE node `"0"`), which are reused as the *same* object across every hierarchy level to match real ground/global-net semantics. A hierarchical instance's pins connect normally to nets in the *parent* scope; each such pin's `hierNet` additionally points straight at the matching port `Net` inside `component.subNetlist`, so hierarchy boundaries can be walked in either direction without name lookups.
- **`issue.nim`** — the shared `Issue` result type (`kind`/`severity`/`message`/`net`/`pins`/`components`/`attrs`). It lives here rather than in `analysis`, where it started, for the same reason `kinds.nim` does: `netlist/annotations` validates the vocabulary and must report what it finds, `pcb` will want to report design-rule findings, and `analysis` already depends on `spice` — a type all three need has to sit below all three. `analysis/issue.nim` re-exports it unchanged, so every existing import still means what it did.
- **`annotations.nim`** — the *vocabulary*: which `attrs` keys mean something, what type and unit each carries, and where each value came from. `attrs` is open-ended so a format never extends the core schema; the price is that **a typo in a key is indistinguishable from an absent key** — write `ESL` for `esl` and `spice/models` silently uses a package default *and reports it as an assumption*, so it looks like it worked. `AnnDef` declares key/kind/unit/scopes/doc/aliases, `validateAnnotations` reports misspelled bare keys, wrong-scope keys and unparseable values, and `setAnnotation` overloads check the unit (`esr = 20.nF` is rejected). **Naming rule: bare means registered, dotted means owned** — `value`/`voltage`/`esr`/`esl`/`package`/`tolerance`/`zin`/`rout`/`lout`/`gain`/`gbw`/`t_ambient_min`/`t_ambient_max`/`delta_t` are the shared vocabulary; `xspice.*`, `parasitics.*`, `role.*`, `ann.src.*`, `kicad.*` and anything a user invents are namespaced and never validated. The registry is a **runtime table seeded from a `const`**: the `const` is what the DSL macro reads to reject a bad key at compile time, and the table is what keeps runtime registration possible. `parseAnnFloat` **rejects SPICE magnitude suffixes** rather than interpreting them — `"20m"` is 20 milli in a deck and 20 units read naively, and picking either silently is the failure the whole module exists to prevent. Provenance is in the accessor's *return type* (`AnnValue[T]{source, value}`), which is why it could not be added later without touching every call site; accessors are **pure and never default**, because inventing a stand-in is a policy decision belonging to whichever consumer knows what a sensible stand-in is. `Assumption` lives here too, next to `AnnSource`, since `spice` produces assumptions and cannot import `analysis`.
- **`kinds.nim`** — electrical classification of the open-ended `Component.kind` string (`classifyConductivity` -> `condConductive`/`condBlocking`/`condAmbiguous`, `isPassive`) and of a net's rail role (`isRail`, `isGround`). Its own module, not a helper inside its first consumer, because two independent subsystems must agree on the answer: `analysis/io_check` walks DC paths and `spice/isolate` decides what to absorb and where to stop, and a net that terminates one walk must not be traversed by the other. `analysis` already depends on `spice`, so the shared answer can live in neither. `behaviouralKinds` (`vcvs`/`vccs`/`cccs`/`ccvs`) is the one thing `isPassive` accepts that `classifyConductivity` still calls ambiguous, and the split is deliberate: a controlled source is **not** a DC path in the conduction sense — its output *is* a source, not a connection to its input — so `io_check` must keep refusing to walk through one; but its behaviour genuinely is fully described by its value, which is the question `isPassive` is actually asked. Without that, a controlled source synthesized by `spice/models` to preserve a signal path would be discarded by the very isolation meant to keep it. `builtinDesignatorPrefixes`/`designatorPrefixFor` map a `kind` to its **reference-designator** prefix (`ferrite_bead` -> `FB`, `opamp` -> `U`, fallback `U`), a runtime table extensible with `registerDesignatorPrefix` like every other registry here. **Deliberately separate from `formats/spice.prefixByDeviceKind`, and it must stay separate**: a ferrite bead is `FB` on a schematic and needs `L` in a deck, a battery is `BT` and `V`. They answer different questions -- a naming convention for people versus how SPICE decides what device it is reading -- and deriving either from the other is how `FB1` came to be simulated as a current-controlled current source. A wrong designator prefix is cosmetic where a wrong device letter is a wrong answer, which is why `U` is an acceptable fallback here and nothing is guessed there. `isRail`/`isGround` accept *either* signal (`Net.kind` OR a connected `Pin.kind`) because the two are populated inconsistently by netlist origin — requiring both would make every partially-annotated netlist look railless.
- **`environment.nim`** — where the board lives, and how hot each part runs in it. Two numbers stand between the netlist and any temperature-dependent answer, and neither is electrical: the **board's** ambient range (`t_ambient_min`/`t_ambient_max`, netlist-scope, from an enclosure spec and the same for every part) and a **part's** rise above it (`delta_t`, component-scope). They are stated separately on purpose — the range is fixed when the product is specified, while a rise is a per-part consequence of a circuit that does not exist yet at that point, so folding them into one absolute temperature per part would mean restating the enclosure spec on every component with a copy to drift at each one. **It wires the two together and models nothing**: there is no tempco here, no capacitance- or ESR-versus-temperature curve, and the figures are deliberately **not** passed to the deck as `.options temp`, which would change how every semiconductor in the design behaves and would silently move every number this repo has measured. What it provides is the input such a model needs — `partTemperatureRange(c, env)` shifts the ambient range by the part's rise at **both** ends, since a dissipating part is above the air whatever the air is doing, and a board specified to -40 does not have to hold a self-heating regulator's ratings at -40 while everything that does *not* dissipate still does. Storage is `attrs` rather than fields on `types.nim` for the reason annotations always are, and here it is load-bearing: `clone` copies them, so the range and every rise survive `materializeSimNetlist`, `flatten`, `extractSubcircuit` and `isolate` — and a fragment cut out for simulation is precisely where a model pass will read them. `environmentOf` reads the **root**, so a child netlist gets the same answer as the board (a subcircuit has no weather of its own). **A part's rise defaults to 0 and says that it did**: `temperatureRise` returns `annDefaulted`, which is the one place a default is applied by an accessor rather than by a consumer, and it does not generalise — an unstated ESR and a zero ESR are different claims about a part, whereas an unstated rise and a zero rise agree for every part that is not dissipating. `deltaT` is still the pure accessor for anything that wants to see the absence, and `riseAssumption` phrases the default once for every consumer. `validateEnvironment` reports what was *stated* and cannot work — an inverted range, half a range, or a `delta_t` with no range to be a rise above — and never nags a design that stated nothing, since nothing consumes the range yet. Authored via the DSL's `environment:` block; `setOperatingTemperature`/`setDeltaT` are the runtime path a file reader takes.
- **`formats/`** — pluggable file-format readers/writers. Every format module implements the same contract: `readNetlist(s: Stream, name = ""): Netlist`, `writeNetlist(nl: Netlist, s: Stream)`, plus `readNetlistFile`/`writeNetlistFile` path wrappers. Format modules only depend on the core types/graph API — the core never depends on a format. `formats/spice.nim` is the only format implemented so far (SPICE `.cir`/`.net` decks); a `formats/kicad.nim` can be added later using the same contract. `formats/common.nim` holds the shared `NetlistFormatError`.
- **SPICE specifics** (`formats/spice.nim`): parses positionally per SPICE's reference-designator-prefix convention (R/C/L/D/Q/M/V/I map to fixed pin-name templates via `deviceKindByPrefix`/`pinTemplates`, and the inverse `designatorPrefix(kind): char` derives the letter back from a `kind` string; `X`/`U` resolve against `.SUBCKT`/`.ENDS` blocks, supporting forward references and nested subcircuit-instantiates-subcircuit). `.MODEL` cards are stored verbatim in `Netlist.models` (passthrough, not structurally parsed); other simulation-control directives (`.OPTIONS`, `.TRAN`, `.PARAM`, ...) are topology-irrelevant and are skipped on read. Unrecognized device-designator prefixes fall back to generic `pin1..pinN` pins rather than erroring. Because raw SPICE has no native concept of pin *type* (power/ground/input/output), `Pin.kind` fidelity through a SPICE round-trip is best-effort only — this is an inherent format limitation, not a bug. `spiceValue(x: float)` is the one correct way to format a synthesized device value (always scientific with an explicit exponent — any format that could end in a letter is a silent-misread hazard, since SPICE reads a trailing letter as a unit multiplier). `parseSpiceMagnitude` is its partial inverse and the counterpart to `annotations.parseAnnFloat`, which *rejects* suffixes because an annotation is in SI base units — here a trailing letter genuinely is a multiplier, because this is what goes into a deck. It refuses two things rather than guessing: anything that is not purely a magnitude (`attrs["value"]` may hold a whole source spec like `"DC 0 AC 1"`, which is why the annotation registry documents that key as never parsed as a number, so only a caller that knows the kind makes the value a bare magnitude should ask), and **RKM notation, where a digit follows the multiplier** — `"2k2"`, `"4u7"`. An EDA tool means 2200 and 4.7 µ by those; **ngspice reads the multiplier and discards the trailing digits, giving 2000 and 4 µ — verified against ngspice-46, not assumed.** Since `value` reaches the deck verbatim, the simulator's reading is the one that gets simulated, so a static check that quietly picked the other would disagree with the simulation about the same part by 10%. `prefixByDeviceKind`/`pinTemplates` also carry `"vcvs" -> 'E'` and `"vccs" -> 'G'` **write-side only**, for `spice/models.idealOpAmp`; unlike `'A'`, an `E`/`G` line genuinely *is* positional and reads back correctly through the generic `pin1..pinN` fallback, so they are kept out of `deviceKindByPrefix` only because nothing yet needs to recover the named `IN+`/`IN-` roles from a deck. **`deckDesignator(comp)` is what actually reaches a deck line, and the letter comes from `Component.kind` rather than from the designator the design wrote.** SPICE infers device type from that first letter and from nothing else, so a part whose designator disagrees with its `kind` is silently simulated as a different device — and the colliding designators are all ordinary ones: `FB` (ferrite bead) reads as a current-controlled current source, `BT` (battery) as a behavioural source, `J` (connector) as a JFET, `VR` (pot) as a voltage source, `TP` as a transmission line. Those fail loudly; the dangerous pair does not, since an inductor filed as `C12` reads as a *capacitor* and a resistor filed as `L7` as an *inductor*, both of which parse and simulate. This was not hypothetical — `designs/ts808_drive.nim` had `VR1` for its drive pot, and 250 kohm of feedback network was being emitted as a 250 kV source, so the stage measured a gain of 12 instead of 65 with nothing reported anywhere. The correct letter is **prepended, not substituted** (`FB1` -> `LFB1`, never `L1`): designators are unique as a set and a truncated one need not be, so substituting would merge `FB1` and `L1` into one device on a board carrying both. A `kind` with no known letter is left alone, since there is nothing to correct it against. `deckInstanceDesignator` does the same for a hierarchical instance, always spelling it `X` — the reader accepts `U` too because other tools emit it, but ngspice reads `U` as a uniformly-distributed RC line. Note the invariant was already enforced for parts the tool *synthesizes* (`transform.replaceComponent` derives its prefix, `probes` validates one) and only the authored path was unguarded. `writeNetlist` calls **`checkDeckDesignators`** on each level first, because graph uniqueness does not imply deck uniqueness: prepending the device letter is not injective, so a resistor designated `XA.R1` and one designated `RXA.R1` are two components in the graph and one line in the deck, which ngspice reads as a device defined twice. That was unreachable while designators were hand-written and short; `spice/flatten` makes generated dotted designators ordinary. Checked per level, since SPICE scopes designators inside a `.SUBCKT`, and it raises rather than renaming — there is no safe way to guess which one was meant. `writeNetlist`/`writeNetlistFile` take an optional `cards: seq[string]` (raw control/analysis lines, e.g. `@[".op"]`) written just before `.END`; empty by default, so plain topology output is unaffected. This is what `nimcir/spice/ngspice` uses to attach an analysis card without duplicating device-line formatting.
**A `component` may omit its label entirely** (`component kind = "capacitor", value = "100n":`), in which case `graph.addGenerated` picks the designator from `kind` at construction -- at construction rather than at macro expansion because `kind` is an expression and because a `for` loop's iteration count is not knowable to the macro. Numbering is **per netlist, not per design**, which is the property that makes it tolerable: a subcircuit gets its own `C1`, `C2`, so adding a part to one module cannot renumber another, and flattening prefixes with the instance path anyway. Hand-authored designators are respected (a netlist already carrying `R1`/`R2` generates `R3`), an explicit `designator =` still wins, and omitting both a label and `kind` is a compile error rather than a guess. Generated ones are marked `attrs["designator.generated"]` and listed by `graph.generatedDesignators`, because a designator is the join key to a board (`pcb/graph.bindComponent` raises on a mismatch), a BoM line and silkscreen text -- and a generated one is **positional**, so inserting a part earlier renumbers everything after it. Safe for a part nothing names and nothing places; wrong for anything already laid out. That is self-selecting: needing to refer to a part is the signal to write its designator.

  **`instance` takes `with = <proc (Netlist)>`**, run against that instance's own clone immediately after `instantiate` and before anything else sees it. It is what makes omitted designators safe rather than merely convenient: post-hoc override is the only thing that *forces* stable identifiers, and injecting the variation at construction removes the need to address an individual anonymous part at all. Inside the proc the only names in play are the module's own **local** designators -- few, author-controlled, and never leaving the module -- rather than a name that must be unique across the whole design and stable against edits. It composes with `for` and with closures, so a per-channel trim table is ordinary code. It is a *construction* step, not a mutation of something already built, which is the same line `Component.simReplace` draws: a post-hoc hook adding a simulation view is fine, one that changes what the board *is* afterwards is not.

- **`dsl.nim`** — an opt-in Nim-macro DSL (`import nimcir/netlist/dsl`) for authoring a `Netlist` directly in `.nim` source instead of hand-calling `graph.nim` or parsing a file format. `netlist("name"): ...` builds a flat netlist from `net`/`component` (with nested `pin`) statements, optionally repeated or selected by a `for`/`if`/`case`/`when`; `subckt("name", [ports]): ...` builds a free-standing template `Netlist` (never registered into any parent), instantiated later via `instance designator, templateIdent, [portNets]`, which expands straight to `graph.instantiate`. Net/component names given as bare identifiers are bound as real Nim `let`s so later statements can reference them (a typo is a compile error); `kind`/`name`/`partNumber` are the only typed "known fields" and get direct field assignment, while any other `key = value` pair lands in that entity's `attrs` bag. The DSL only ever expands into calls on the `graph.nim` API — like everywhere else in this submodule, back-references are never hand-set outside `graph.nim` itself. A top-level **`environment:`** block states the board-level operating conditions (today the ambient temperature range); it is `spec:` at netlist scope and is spelled differently only because that is what it says — a range read off an enclosure specification is not a property of the netlist the way a net's rail voltage is, and the name is what keeps a design file legible when humidity or altitude is added beside it. A `net` or `component` block may contain a `spec:` block, whose keys are validated against `netlist/annotations` **at compile time** — an unknown or wrong-scope key is a compile error naming the registered keys, and a `nimcir/units` literal inside it cannot be misread. This is the opposite of the permissive head-of-statement fallback, and deliberately so: the strictness boundary is syntactic, because inside `spec:` there is no open-ended bag for an unknown key to mean anything, exactly the reasoning that makes `xspice/dsl.nim` strict while this module is not. A `model "<name>", "<card>"` statement registers a `.MODEL` card (through `graph.setModel`, not a bare table assignment — `Netlist.models` is state `graph.nim` owns, and expanding to `nl.models[k] = v` would force every design file to `import std/tables` for a statement that has nothing to do with tables). The card body is **never parsed**: tracking every parameter of every device type in every SPICE dialect would mean getting one wrong silently simulates a different part, whereas passing it through means the simulator reads exactly what the datasheet said. What *does* read it is `kinds.hasDeviceModel`, which only asks whether the name is present — and that is what makes the statement matter beyond reaching the deck, because `isPassive` accepts a part with a model, so `spice/models` stops standing it in and `spice/isolate` will traverse it. Matched case-insensitively, as SPICE is. The TS808's clipping diodes are the case: without a card each became two 1 Mohm resistors to ground, and the pair shunted the inverting node with 500k — a second gain leg that lifted the stage's gain at the bottom of the sweep from unity to 4.2 dB, which is where a reported 31.6 dB of peaking came from against a real 35.3. **Parameterized circuits work, and the mechanism is that a `subckt` block is ordinary runtime code inside a `block` expression**: put it in a `proc`, compute values from the arguments before it, and reference them — `value =`, `designator =` and `name =` all take arbitrary expressions rather than literals, and `spec:` keys are validated at compile time while their *values* are expressions. `designs/lib/filters.nim` is the worked example. The block additionally admits **`for`, `if`, `case` and `when`**, and admits them as *control flow over DSL statements* rather than as an opening to arbitrary code: the loop header passes through untouched and the body is expanded by the same dispatcher, so everything inside is still a `net`/`component`/`instance`/`model`. A decoupling bank or a channel per lane is otherwise N nearly-identical lines, which is where a value gets corrected in one copy and not the others; build variants are otherwise two files that drift apart, or one file with the unused half commented out. A bare `discard` is an empty branch, since `if`/`case` need a body and "this variant adds no parts" is ordinary — `discard <expr>` is refused as arbitrary code wearing a keyword. Nothing is weakened by it — `spec:` keys are still validated at compile time and an identifier typo is still a compile error, because neither depends on whether the branch runs, and `addComponent` always raised on a duplicate designator at runtime anyway. Two things do not fit inside one: the `let` a `net`/`component` binds is scoped to the **branch or iteration**, so address anything generated there by name through `graph.findComponent`/`findNet` afterwards; and `role`/`require` are **rejected with a message**, because `design` hoists claims to after the netlist is built and a nested one would attach to a netlist that does not exist yet. `buildNetlistBody*` is exported as an extension point for a higher-level DSL that wants these statements plus its own (see `contract/dsl.nim`). A `component` block may additionally contain one or more `simReplace kind = "...", name = "...", suits = ...: pin ..., ...` statements (see the `spice` submodule below) — each only ever *adds* to `Component.simModels`, so none of them mutates the component it's attached to, and a component-level `simDefault = "..."` names which one is used when nothing states a purpose. Several are told apart by `name`, and `suits` (a bare string or a bracketed list) is what says which question each answers; a duplicate `name` raises.

### `pcb` submodule

`src/nimcir/pcb/` models the *physical* board — layers, stack-up, copper, holes, component placements, board outline — and is where any future DRC/DFM/SI/PI work lands. It depends on `nimcir/netlist`; the netlist never depends back on it. `src/nimcir/pcb.nim` is the hub (`units`, `geometry`, `types`, `graph`, `index`, `bom`); file formats stay opt-in per-import under `pcb/formats/`, same as `netlist/formats/` and `spice/ngspice`.

**The electrical model is not duplicated.** A `Pcb` *owns* a `Netlist` built through the ordinary `netlist/graph` API, and every PCB entity holds a **forward reference only** into it (`Copper.net: Net`, `Copper.pin: Pin`, `Placement.component: Component`). `netlist/types.nim` is untouched and stays geometry-free, so a netlist-only consumer carries none of this weight while an analysis pass can still walk from a trace to the pins it connects in one hop. `Placement`/`Component` join on reference designator (`bindComponent` enforces the match; `placementOf` is the reverse lookup).

- **Two lookups are first-class**, because they are what layout analysis actually asks. By **net name**: `Pcb.netCopper` (name -> every `Copper` on it), maintained by `pcb/graph`, queried via `copperOn(pcb, netName | net, layerName = "")`. By **location**: `pcb/index.nim`, a per-layer uniform grid over cached per-feature AABBs. `query`/`queryPoint`/`near` are bounding-box *candidates*; `hitTest` applies the exact `geometry.contains` predicates on top — do not confuse the two. Any feature spanning more than `SpatialIndex.maxCells` cells (a board-sized pour) goes to a per-layer `oversized` list instead of into every bucket; that overflow is the one thing that makes a uniform grid viable on PCB data. `graph` sets `index.dirty` on every mutation and every query rebuilds when it is set, so callers never manage the index by hand.
- **`units.nim`** — `Nm = distinct int64` nanometres and `Deg = distinct float64` degrees, with `mm`/`mil`/`inch`/`um` constructors and `toNm(v, LengthUnit)` for readers. `int64` nm spans the whole ODB++ coordinate range (±2450 mm) and exactly round-trips KiCad (int32 nm internally). Known, deliberate loss: ODB++'s finest legal quantum is 1/400 µm = 2.5 nm, so ODB++ input rounds to the nearest nm — far below any fab tolerance. **Canonical frame: X right, Y *up*, angles CCW-positive, degrees; polygon winding islands CCW / holes CW.** ODB++ and Gerber are already Y-up; KiCad is the outlier (Y-down, rotation CCW-as-displayed) and its reader must negate Y and angle at the boundary, or every rotated footprint silently mirrors.
- **`geometry.nim`** — the dimensionless `Curve` (`cvSeg`/`cvArc`) is deliberately separate from the `Shape` that has area (`shStroke` for tracks, `shFill` for pours, `shPad` for a flashed aperture, `shText`). **Arcs are canonically centre + radius + start angle + signed sweep**, since KiCad's three-point form and ODB++'s endpoints-plus-centre form are both awkward for AABBs and sampling; `arcFrom3Points`/`arcFromEndpointsCenter` convert once, at the reader. `Aperture` is a `ref object` **interned in `Pcb.apertures`** (mirroring ODB++'s `$n` symbol table and KiCad's shape tokens) so one object backs thousands of pads; its raw source `name` is kept verbatim even when parsed, and unrecognised names fall back to `akCustom` rather than erroring. `Transform` does footprint-local -> board coordinates.
- **`types.nim`** — `Pcb`, `PcbLayer`, `Stackup`/`StackEntry`/`StackMaterial`, `Copper`, `Zone`, `Hole`, `Placement`, `Outline`, plus `SpatialIndex`'s *storage* (its algorithms live in `index.nim`; the type is declared here only so `Pcb` can hold one without a circular import). Every entity carries the same open-ended `attrs: OrderedTable[string, string]` bag as `netlist/types`, so a format module never extends this schema.
- **`graph.nim`** — as with `netlist/graph.nim`, **the only place allowed to mutate back-references and indexes**. Nothing else sets `.pcb`, `.layer`, `.net`, `.pin`, `.hole`, `.pads`, `.lands`, `.box`, `.sourceIndex` or `.index`. Use `addLayer`, `addCopper`, `setNet`, `setShape`, `removeCopper`, `addZone`, `addHole`/`attachPad`/`setSpan`, `addPlacement`/`bindComponent`/`addLand`, `internAperture`, `addStackEntry`.
- **Layers are keyed by name, never by ordinal** — KiCad renumbered every layer ID in v9 (`B.Cu` went 31 -> 2, inner layers to `2+2n`) and ODB++ `ROW` numbers are explicitly allowed to be non-sequential. `Pcb.layers` **insertion order is physical stack order**, so readers add top to bottom.
- **Ordinal warning**: ODB++ cross-references everything positionally (`FID` feature numbers, `CMP`/`PKG`/`NET` record indexes). `PcbLayer.copper` is kept in source order and must never be re-sorted or deduped; `Copper.sourceIndex` is only meaningful immediately after a load, and `removeCopper` renumbers it (and says so).
- **`Copper.negative`/`PcbLayer.negative`** exist because ODB++ `POWER_GROUND` layers are routinely `POLARITY=NEGATIVE`, where drawn features are *clearances*, not copper. A by-net copper index that ignores this is exactly inverted on every plane layer.
- **`Hole`** unifies two very different encodings: KiCad states the layer span directly, while ODB++ has no hole record at all (holes are pad features on a `TYPE=DRILL` layer, classified by the matrix row's `START_NAME`/`END_NAME`, the `.drill` attribute, and the layer's `tools` file keyed by the feature's dcode). `setSpan` derives `vkThrough`/`vkBlind`/`vkBuried` from which outer layers the span touches. `drillDia` and `finishedDia` are separate because ODB++ `tools` distinguishes them.
- **`Zone` models only the *authored* outline.** Derived fill geometry (KiCad `filled_polygon`, ODB++ `SNT PLN` surfaces) is deliberately out of scope; adding a `fills` field later is purely additive. Consequence to state honestly: plane-shape, return-path and power-integrity analysis are **not** answerable from this model yet.
- **`bom.nim`** — `buildBom(pcb, groupBy = nil)` *compiles* a BoM from what the board file already carries; it does **not** resolve parts against a supplier catalogue (that is a separate `nimcir/bom` concern). Both formats do carry per-part data on the board itself — KiCad `(property "Reference"/"Value"/...)` plus schematic-propagated user fields and `dnp`/`exclude_from_bom`; ODB++ `PRP` records plus an explicit `BOM DATA` block (`CPN`/`IPN`/`DSC`/`VND`/`MPN`/`VPL_*`) — so a reader drops all of it into `Placement.attrs` and `bom.nim` promotes the well-known keys, trying both naming conventions. `excludeFromBom` placements are dropped; `doNotPopulate` ones are **kept** on their own lines.
- **`formats/common.nim`** — the format contract is **path-based, not `Stream`-based**, a deliberate departure from `netlist/formats/common.nim`: an ODB++ job is a *directory tree* whose members may be LZW-`.Z` compressed, which no single `Stream` expresses; a KiCad board is one file, so a path covers both. `proc readPcb*(path: string, step = ""): Pcb` / `proc writePcb*(pcb: Pcb, path: string)`; the `step` param exists because one ODB++ job may hold several steps (board/panel/coupon). **No reader is implemented yet** — `formats/kicad.nim` and `formats/odbpp.nim` are the next task, against this contract.
- Two gotchas to carry into those readers: KiCad has **no explicit board outline** (it must be stitched from `Edge.Cuts` graphics with a tolerance — hence `Outline.stitchTolerance` — *including items owned by footprints*), and **ODB++ net names are not unique** (the spec calls them "for reference only"; the reserved `$NONE$` repeats with mutually-disconnected meaning), so a reader must synthesise unique names before registering into the name-keyed `Netlist.nets`/`Pcb.netCopper`.

### `contract` submodule

`src/nimcir/contract/` is design *intent*: what a circuit is meant to be and what it must do. It depends only on `nimcir/netlist`, so a design and its contract can be authored, read and inspected with no simulator in the build. `src/nimcir/contract.nim` is the hub (`types`, `roles`, `design`, `evaluate`, `evaluators/static`); `contract/dsl.nim` is opt-in per-import, the same rule everywhere else in this codebase.

**A role is a parameterized bundle of assertions, not a tag.** That is the whole model, and it is the thing that makes the layer extensible: a bare tag (`kind = "i2c"`) puts the meaning in whatever reads the tag, so a new protocol means changing this library, whereas a template puts the meaning in the definition. **The built-in roles use no privileged mechanism** — they are ordinary `RoleDef`s registered the ordinary way — because a built-in that cheats makes user-defined roles second-class and then nobody writes them. `tests/test_contract_roles.nim` pins that down by defining a role in the test file and checking it takes the identical path.

- **`types.nim`** — `Subject`, `Expectation`, `Assertion`. Three shape decisions carry the forward-compatibility story and should not be traded away: `subjects` is a **seq** (setup/hold is inherently one signal *versus* another, so a two-subject quantity must not be a special case bolted on later); `quantity` is an **open string naming an analysis `Measurement`** (`dc_voltage`, `bw_3db`, `z_min`); and `Expectation` is a **variant object**, so `ekRelative` (a bound referring to another measurement — "no more than a fifth of the primary filter") and `ekPredicate` (a Nim proc) are additive rather than a redesign. `satisfies` is the comparison every future evaluator shares, and a `NaN` never satisfies anything: "the measurement did not happen" must not read as a pass.
- **Why `quantity` is a `Measurement` name.** Evaluating an assertion becomes "run whatever analysis produces `bw_3db`, then compare", with one comparison shared by every quantity; the failing witness comes free, because the `Measurement` and its curve already exist; and a bench result is also a `Measurement`, so correlating measured against simulated is later the same comparison with a different source. It also keeps the coupling honest — a quantity nothing can produce is a claim nobody can check, and that shows up immediately.
- **`roles.nim`** — `RoleDef` has **two halves, deliberately separate**. `apply` writes annotations onto the netlist and is the half with a life independent of any checking: `spice/isolate` terminates a cut rail from `Net.attrs["voltage"]` long before anything asks whether the rail is *correct*, and if a role were only assertions, `isolate` would have to introspect the assertion list to recover a voltage. `expand` is pure and returns assertions. Both are **proc values on a data object**, not compile-time constructs, so a role built at runtime registers and behaves identically. Built-ins: `power_rail` (single-subject, and it replaces something real today), `i2c` (multi-subject, so part binding is actually exercised), `regulator`/`opamp_stage`/`gain_stage`/`large_signal`, which exist to bind the topology their own claims need, **`settled_rail`, which binds nothing at all** -- a net, a settling time and what the node must then be doing -- and **`oscillator`, its counterpart for a circuit whose intent is instability**: what a node is *running at* rather than what it settled to (`osc_freq`, `swing_pp`, `osc_thd_pct`), with an optional `kick` part naming a node to put `kickV` on as an `.ic`, since a Wien bridge's operating point is a balance it sits in forever. `kick` is optional and so `spice.oscillator` declares no `binds`, which is right -- plenty of circuits are periodic without one, and `uic` is not free. Every `oscillator` claim is opt-in: there is no default frequency for an oscillator, and no default amplitude or distortion budget either. It is a separate role rather than parameters on `opamp_stage`/`gain_stage` because those are backed by an `.ac` sweep and every claim they make is about how far a stage is from oscillating -- and worse, the *measurement* does not survive the change of intent, since a sweep drives an ideal source onto the input net and a Wien bridge returns its positive feedback to exactly that node. That is what lets it reach the circuits the others cannot: `power_rail`'s `dc_voltage` is an operating point and an operating point has no ripple in it, so a switching converter's rail reads as its average by construction and would pass any ripple claim ever made about it; `regulator` is about the way up and needs a part to stand up as a ramp. Its `tSettle`/`tWindow` are **conditions, not limits** -- they say what was run, the answer is a function of them, so they ride in `Assertion.condition` and join the evaluator's setup key, exactly as `large_signal`'s drive level does. **`gain_stage` is `opamp_stage`'s AC-coupled counterpart and is a separate role rather than more parameters on it**, for two reasons: it claims against the band rather than against DC (see `analysis/opamp`), and it deliberately makes **no stability claim at all** — `peaking_db` cannot tell an intentional band-pass shape from resonance, and `opamp_stage` claims it unconditionally, so a single role could not offer both without forcing one. Stating both on the same stage is the supported way to get a margin *and* a band, and `designs/ts808_drive.nim` does exactly that. Its `atF` parameter moves the gain claim from `gain_max_db` onto `gain_at_f` and stamps the frequency into `Assertion.condition`, which is the only channel an assertion has for it — a start-up or loop-gain measurement needs a component designator the assertion's subjects do not carry, and the role is where that comes from. Optional parameters expand a claim only when stated: `power_rail`'s `targetZ` adds the PDN impedance assertion, and omitting it adds nothing, because a decoupling target follows from the load's transient current and inventing a default would manufacture a claim the designer never made and then report it as theirs. **`without` is reserved on every role**, and is the one parameter no role declares: it names claim suffixes this instance does not make (`without = "phase_margin"`, comma-separated for several). A role's always-claims are otherwise unconditional, and some do not fit every circuit the role otherwise describes — `opamp_stage` claims `phase_margin_deg`, `analyzeLoopGain` cannot open a Sallen-Key's loop, and the claim can then only ever come back unchecked. Carrying an unmeasurable claim in every run is its own harm, since `NOT CHECKED` is precisely the section that must not become background noise; forking the role instead is how a shared vocabulary dies. Declining is **not** silence: `explain` prints `declines ...`, and a suffix matching nothing **raises** rather than quietly leaving the claim in place — the same hazard as a misspelled annotation key, and `addRole` catches it by expanding once, which is free because an expander is pure. Everything that reads a design's claims goes through `expandInstance`, so what `explain` prints and what `evaluate` checks cannot drift. Role *parameters* carry their defaults in the expander, not the registry — a defaulted *design annotation* is a silent-drift hazard worth keeping visible and should not be blurred with a role default.
- **`design.nim`** — `Design` **owns** a `Netlist`, exactly as `Pcb` does and for the same reasons; `netlist(...)` returns a bare `Netlist` with nowhere to hang design-global data, and nothing is added to `netlist/types.nim`. Role **membership** is the exception and lives on the entity (`net.attrs["role.i2c0"] = "sda"`) so it survives `clone`/`extractSubcircuit`/`isolate` — including `isolate`'s rename of ground to `"0"`, which a name-keyed side-car store would have lost. A subject may address something **inside a subcircuit instance** by a `hierSep`-separated path, resolved through `graph.find*`: a stereo board is one channel instanced twice, and a claim about the left channel's amplifier has no other way to say which amplifier it means — the identifier was bound inside a `subckt` in another module and is long out of scope at the design site. `Component.innerComponent`/`innerNet`/`innerPin` build the `Subject`, walking the child *immediately* so a typo raises there naming what the instance actually contains. A one-line `subjectOf(Subject)` identity overload opens the DSL's existing `when compiles(subjectOf(value))` binding test to them without the macro learning anything. Because `find*` tries the flat key first, the same name resolves before `spice/flatten` has run and after. `explain` prints what every role expanded to; that is not a nicety, since assertions generated on your behalf that you cannot inspect are how a contract layer turns into filler that always passes.
- **`dsl.nim`** — `design(...)` accepts everything `netlist(...)` does (reusing `buildNetlistBody`, not duplicating it) plus `role` and `require`. **Part bindings and parameters are told apart by type, not position**: the expansion routes each `key = value` with `when compiles(subjectOf(value))`, so a `Net`/`Component` is a binding and a quantity/number/string is a parameter. That keeps the syntax flat without the macro consulting the role registry, which is a runtime table it cannot see; a wrong *name* is still caught, by `addRole`. `require` is spelled with ordinary Nim comparisons over `quantity(subjects)`, and the unit is taken from the literal so it cannot drift from the value.
- **Not an expression language, deliberately.** Almost every claim is "quantity Q of subjects S under conditions C lies in interval I". When it is not, the escalation is: put the arithmetic in a Nim proc emitting a *derived quantity* (SPI setup margin is a computation over datasheet numbers, not a measurement), then `ekRelative`, then a Nim predicate. **Nim is the expression language** — a macro can compile an ordinary Nim expression into a predicate plus its measurement dependencies, at the cost of no parser, no evaluator and no bespoke error messages.
- **`evaluate.nim`** — the checking half. An `AssertionResult` carries pass / fail / **notEvaluated** / **notEvaluable** and is deliberately **not** an `Issue`: `Issue` cannot say "checked, and it is fine" or "could not check", and silence meaning pass is how assertion systems become theatre. The two negative statuses are not interchangeable — `notEvaluable` means nothing can produce this quantity for these subjects, `notEvaluated` means an evaluator exists but did not run or did not return a number (its capability was withheld, the simulation raised, the measurement came back `NaN`).
- `Evaluator.binds` names the role *parts* an evaluator reads back off `Assertion.origin`, beyond the assertion's own subjects — declared rather than inferred, for the same reason `BehavioralModel.passesSignal` is: something has to answer "can a bare `require` reach this quantity?" **without running anything**, and only the evaluator knows. Empty means the subjects suffice (a `dc_voltage`, a PDN sweep); non-empty means the quantity is reachable *only* through a role that binds those parts. That is what `nimcir quantities` reports in its third column, and the three answers there — `require`, `role: X`, `-- needs a role binding` — are genuinely different, since conflating any two is how a reader writes a claim nothing will check. **An evaluator's only argument is an `EvalContext`**, and that is deliberate rather than incidental: `EvalProc` is the plugin ABI, so anything an evaluator might ever need has to be reachable through it. A bare `Design` was not enough, and three things had already found side doors — a shared operating point in a module-level `var`, the offered capability set known to the planner and not to the evaluator, and no route at all for a `Pcb` or a bench reading. The context carries `design`, `allowed`, and a **type-erased `scratch: Table[string, RootRef]`**; type-erased because `contract` may not name an `OperatingPoint` or a `Pcb` without gaining an edge to `analysis` or `pcb`, so a module that owns such a type declares `ref object of RootObj`, stashes it under a dotted key it owns, and downcasts on the way out. That keeps the layering intact *and* stops the context itself needing a new field every time something new needs carrying. A context lives exactly one run, which is what turns "one `.op` per design" from a documented rule into a guarantee — see `analysis/operating`. `plan(d, allowed)`/`evaluate(d, allowed)` remain as overloads that build a fresh context per call, which is the right default for a caller sweeping many candidate designs. **`Evaluator.needs` is a `set[Capability]`, not one.** More than one built-in genuinely needs two and had no way to say so while it was a scalar: `spice.pdn` declared `.ac` and solved an operating point for its bias derating, `spice.large_signal` declared `.tran` and solved one to find the bias its stimulus sits on, and under `--caps=ac` or `--caps=tran` each ran an analysis the caller had withheld. Under-declaring is invisible while every capability happens to be available and becomes a wrong answer the moment one is not — which is exactly what a bench host is. The gate is `ev.needs <= allowed` and the rejection names the missing ones by label (`needs the .op + .ac capabilities`). An empty set is normalised to `{capStatic}` by `registerEvaluator`, since an omitted declaration must never read as "runs everywhere". **Evaluation is planned before it is run.** Quantity-to-evaluator is **many-to-one** — `analyzePdn` emits eight measurement names from one `.ac` — so an `EvalProc` takes a *batch* and `plan` groups assertions by `(evaluator, setupKey)`. "One analysis run per distinct setup" is therefore a property of the planner, provable by counting steps, rather than something each evaluator reimplements; a single `.op` answers every `dc_voltage` claim in a design. `plan` is pure and `explainPlan` prints it, for the same reason `explain` exists: an assertion set you cannot inspect before it executes is the failure mode this layer is meant to prevent.
- **Setup topology is recovered through `Assertion.origin`.** `overshoot_pct(vdd)` names the rail but not the regulator driving it, and `analyzeStartup` needs both. Since `roles.nim` stamps the role-instance name into `origin`, an evaluator reads the bindings back off `Design.roles[origin]` — a role already knows its own topology, so its claims do not have to restate it. Resolution order is subjects, then origin-role bindings, then `condition`, then `notEvaluable` **naming what was missing**; that message is the product when a claim cannot be checked. This is what made the simulated adapters possible without redesigning the core.
- **`registerEvaluator` raises when a quantity is already produced by a *different* evaluator.** `quantityIndex` is a flat map, so a second registration would take over every claim on that quantity in every design with nothing said -- the same quantity name in the report either way and a different analysis behind it. Re-registering under the *same* name still replaces, because that is the documented way an application overrides a built-in: an override says so by keeping the name, a collision is an accident, and once it has happened the two are indistinguishable. `verdict()` is the single place pass/fail semantics live, so every evaluator gets identical behaviour. Its two *declining* paths — `NaN` and unit mismatch — carry the analysis's `assumptions` **and `issues`** out with them, for exactly the reason `failBatch` does: `reason` is written inside `verdict` and cannot name a cause `verdict` does not know, while the analysis that produced the `NaN` usually does know and said so in an `Issue`. Dropping those stranded the diagnosis — a Sallen-Key's phase margin read `the quantity was not found in the range that was analysed`, which is true and sends the reader to widen a sweep that is not the problem, while the issue one field away said the loop break never opened the loop. Three decisions are pinned there: a **`NaN` measurement is `notEvaluated`, not `esFail`** (`satisfies` guarantees `NaN` never *passes*; this goes further and declines to call it a failure, because `z_antiresonance = NaN` means no interior peak was found, which is the good outcome), and a **unit mismatch is `notEvaluable`** rather than a silent comparison of volts against hertz.
- **`evaluators/static.nim`** — the producers for the `i2c` role's quantities, needing no toolchain. Two are worth reading for what they decline to answer: `controller_count` returns `notEvaluable` with no role binding, because every device on an I2C bus has an inout data pin and nothing in a netlist distinguishes the controller from a target; `rc_corner` rests on an invented per-pin bus capacitance and reports it as an `Assumption`, since a netlist carries neither trace nor pin capacitance. Assumptions ride on every result, and `invented(results)` answers "how much of this did we make up?".
- **Deferred with reasons**: `normalizeAnnotations` (foreign key -> canonical via `AnnDef.aliases`) waits for a KiCad reader, because KiCad has a property literally called `Value` that is *not* our `value` and the pass should be written against the real collision rather than a guessed one; a serialized intent format waits for the same reason. Runtime-loadable *evaluators* (a compiled-product goal) are deferred too, but the hedges that keep them possible — open `quantity` strings, proc-valued `expand`, plain-data assertions, a runtime registry — are already taken.

### `parts` submodule

`src/nimcir/parts/` answers a question the netlist layer deliberately does not:
given that a circuit needs 22.5 nF *here*, which capacitor is that. It depends on
`nimcir/units` and `nimcir/netlist`; neither depends back on it, and no analysis
requires it — a design annotating its parts by hand never imports it.

**The asymmetry it exists for.** A parameterized module (`sallenKeyLP(fc, r, q)`)
computes that it needs 22.5 nF and cannot compute what part that is: the choice
depends on rail voltage, temperature range, space and cost, none of which the
module can see. But the *board* cannot choose either, because it cannot see which
of the module's capacitors sets a corner and which is a bypass — and that
distinction is decisive, since a timing capacitor must be Class 1 (a Class 2
dielectric loses capacitance to DC bias and temperature, moving the corner) while
a decoupling capacitor should be Class 2, which is where the density is. **The
module knows the part's function, the board knows its environment, and neither can
choose the part alone.** So the module states a `CapRequest`/`ResRequest`/
`IndRequest` carrying a value and a *use*, and the board supplies a `PartPolicy`
that returns a `Choice`. Both rejected alternatives fail concretely: per-component
builder parameters (`c1Package`, `c1Dielectric`, …) multiply out with every part
*and* still leave the board guessing at function, while a pass that annotates
afterwards loses `spec:`'s compile-time checking and must address parts by
generated name.

`PartPolicy` holds **procs on a data object**, like `RoleDef`, so a policy built at
runtime from a preferred-parts database behaves identically to the built-in one; a
`nil` member means the policy has nothing to say about that kind of part and the
caller leaves the component unannotated rather than inventing something.
**`parts/series.nim` is the other half of the same question** -- not which *kind* of part, but which of the values that part is sold in. It holds the preferred-value ladders (`seriesE12`/`seriesE24`/`seriesE96`), `nearest` (by *ratio*, since the ladder is geometric and the tolerance a part is bought at is a percentage, with the next decade's first value as a candidate so a mantissa just under ten rounds up), and the `PreferredSeries` proc-valued hook a builder takes -- `exactSeries` (the default: rounds nothing, the position `designs/lib/filters.nim` states) plus `e12`/`e24`/`e96`. **The tables are written out, not computed**: seven of E24's twenty-four values deviate from `10^(n/24)` through the middle of the decade, so a computed ladder is a plausible list of numbers nobody sells. Two things a test pins that the names do not say -- 240 R is an E24 value and *not* an E96 one, so rounding a resistance the designer stated moves it to 243 R and takes a divider's ratio with it; and E96's worst gap is 1.33 -> 1.37, a 3.01% step, so rounding costs up to **1.49%** rather than the 1.2% `10^(1/96)` suggests.

`policy.defaultPolicy()` draws the same line `spice/models` draws for stand-in
values — **guess where the guess is forced, refuse where it is a choice**: C0G for
a timing part is physics and is defaulted silently; X7R for a decoupling part is a
judgement and is defaulted *and noted every time*; a voltage rating is derived from
the working voltage when the module states one and **left unset when it does not**,
because a coupling capacitor in an unbiased stage genuinely has no known working
voltage and inventing one would invent the circuit. `annotate.applyChoice` writes a
`Choice` as ordinary **registered** annotations with `annDerived` provenance — what
a policy decided is visible exactly as a hand-typed `spec:` block would be, and a
mechanism whose output could only be understood by re-reading the mechanism would
be worse than typing the values out.

Note what the builder does **not** pass for its bypass capacitors: `working`. It
does not know the supply, and does not need to — `spice/models` computes the DC
across each capacitor from the netlist at simulation time, when rail voltages are
stated. The policy answers "what kind of part", the netlist answers "what is across
it", and neither has to know the other's business.

### `spice` submodule

`src/nimcir/spice/` runs simulations against a `Netlist` through an external SPICE backend (currently `ngspice` only) and provides simulation-only netlist transforms. It depends on `nimcir/netlist` (core types/graph, and `formats/spice` for deck serialization); the core never depends back on it. `src/nimcir/spice.nim` is the hub, exporting the backend-agnostic pieces (`backend`, `probes`, `transform`, `extract`, `isolate`, `models`, `flatten`, `boundary`) — a concrete backend like `ngspice` is opt-in per-import, same as file formats under `netlist/formats/`.

- **Simulation-only component replacement** (`Component.simModels: OrderedTable[string, SimReplacement]`, defined in `netlist/types.nim` alongside `Netlist.models` as a pragmatic simulation-aware field on an otherwise format-agnostic core type): records "for simulation purposes, replace this component with a device of `kind`, wired as `pinNets` (pin name -> net *name*) describes", set via the DSL's `simReplace` statement co-located inside a `component` block. **A part may carry several, because which model is right depends on the question being asked** -- an averaged model of a switching regulator answers the rail voltage and the start-up ramp in milliseconds of wall clock and has no ripple in it to find, while a switching one answers the ripple and costs fifty timepoints a cycle; neither is better, and a design forced to pick one would be choosing which question it is allowed to ask. Storage is **one table**, with `simReplace` an accessor pair over it (the getter returns the default, the setter still means "this is *the* model", so every call site predating multiple models is unchanged) -- a field beside a table of alternatives would give "what stands in for this part" two answers that nothing keeps in step. `simDefault` names the default explicitly; empty means the first added. `addSimModel` raises on a duplicate name for the reason `addComponent` raises on a duplicate designator. It never mutates the component itself — it's inert data until `spice/transform.materializeSimNetlist(nl, globalNets)` clones `nl` and applies every stored `simReplace` (recursing into `nl.children`) via `spice/transform.replaceComponent`. The real design netlist passed in is never mutated. `graph.nim`'s `clone()` copies `.simReplace` by reference (treated as immutable once built). `SimReplacement.build` is an optional proc that **replaces** the `kind`/`pinNets` shape entirely, and exists because that shape cannot express an XSPICE code model: `replaceComponent` never touches `nl.models`, so the `.MODEL` card would be lost, `kinds.hasDeviceModel` would go false, the part would stop being passive and `spice/isolate` would drop it at the boundary — the exact failure the model was added to fix. It is handed the materialized clone and the part to stand in for, and mentions only netlist types, so `netlist/types.nim` learns nothing about XSPICE.
- **`backend.nim`** — the shared result/error types. `SimVector` is an **object variant** over `SimDataKind` (`sdReal` -> `values: seq[float]` for `.op`/`.tran`/`.dc`, `sdComplex` -> `cvalues: seq[Complex64]` for `.ac`), so reading an `.ac` result as a real vector is not merely discouraged — the field does not exist on that branch. The discriminator is known before any value is parsed (`Flags:` precedes `Values:` in the rawfile). `[]` still raises `SpiceSimError` rather than letting a bare `FieldDefect` escape, so the failure stays a `CatchableError` like every other one here, and still raises `KeyError` for a missing name because `analysis/spice_fallback` depends on that. Complex data is read through `cplx`/`mag`/`db`/`phaseDeg`/`freq`; `mag` is defined for both kinds so an impedance or gain reader need not branch, and `freq` pulls the real part because ngspice emits the frequency axis as complex with a zero imaginary part.
- **`transform.nim`** — `replaceComponent(nl, oldDesignator, kind, pinNets, ...)` removes the old component (`graph.removeComponent`) and adds a new one of `kind`, auto-deriving a SPICE-correct designator (via `formats/spice.designatorPrefix`) rather than reusing the old designator's letter, since SPICE infers device type from that letter, not any `kind` field. It also owns **model selection**: `selectSimModel(c, purpose)` picks which of a part's `simModels` stands in, and `materializeSimNetlist` takes the `purpose` every analysis passes (`spOperating`, `spSmallSignal`, `spStartup`, `spSteadyState`, `spLargeSignal`). The vocabulary names **what is being asked, not which SPICE card gets written**, and that is the whole design rather than a naming preference: both LT8640A models are `.tran` models, so naming the card would put them in one bucket and leave the choice to a coin toss. Three rules, each against a specific failure -- a model naming the purpose in `suits` wins; no match falls back to the default, because `suits` is *advisory* and a model that declared itself for steady-state only must not make a `.op` on the same design impossible; two models naming one purpose **raises** listing both, since that is an ambiguity rather than a preference and picking either would silently decide which analysis the design gets. `clone` carries every model, not just the default, or the alternative is dropped one transform before the analysis that asked for it.
- **`isolate.nim`** — cutting a *simulatable* fragment out of a full design. `extract.nim` answers "given this exact designator list, detach it and promote boundary nets to ports"; two things are still missing before the result will simulate, and this supplies both. **Choosing the list**: `isolate`/`isolateNets`/`isolateFrom` grow a selection outward from seed components and/or seed nets through parts whose behaviour is fully described by their value (`kinds.isPassive`), recording everything else in `Isolated.dropped` rather than traversing it. **Terminating the cut**: ground becomes node `"0"` (via `graph.renameNet`), every other rail gets an ideal source at its nominal voltage (`IsolationSpec.railVoltages` or `Net.attrs["voltage"]` — never guessed; an unknown rail raises unless `requireKnownRails = false`), and every open or excluded net gets a 1 Gohm leak to ground so it has a DC reference instead of producing a singular matrix. **Where the boundary falls is the whole result**, and two rules do the work: a rail is a boundary and is never traversed *through* (every bypass cap on a board shares VDD, so one hop through it absorbs the design) unless it was named a seed; and an unmodellable component is never traversed through either. `maxHops` is a backstop, not the mechanism. `excludeRails` exists because an ideal voltage source is a dead short at AC — terminating the rail whose impedance you are measuring would report Z = 0 at every frequency.
- **`boundary.nim`** — where a board stops, and what is on the other side. **A connector is not a component in the sense the rest of this library uses the word**: each of its pins touches exactly one net, so there is nothing to pass *through* to, and its electrical behaviour is entirely whatever is plugged into it — which a netlist cannot know. Standing one in with per-pin impedances is therefore wrong in a specific way rather than approximate: measured, a USB inlet became 1 Mohm to ground and the board's `v(vbus)` read **0 V**. Two separable things follow, and only one of them fixes a wrong answer. `asSubcircuit` promotes every connector pin's net to a port and drops the connectors, giving the board as a reusable `.SUBCKT` — a **composition** feature that changes no measurement; ports are named after the **net**, matching `extract.extractSubcircuit`, because a net name is already unique where `J1.VBUS` would have to be invented and checked, and ground is never a port since node `"0"` is global. **A design states its drives on the connector pins**, via `driveConnector` after the `design(...)` block: each drive is recorded on the `Pin` as namespaced `boundary.*` attrs and a `SimReplacement.build` replaces the connector with them at materialise time. Recording it as *data* rather than as a captured closure is not tidiness — `SimReplacement.build` is `{.nimcall.}` and has no environment to capture a drive in — and it has the better property anyway: the drive survives `clone`, is visible in the netlist, and anything can read it back. Going through `simReplace` is what keeps the connector in the **design** netlist, so a BoM and a layout still see the part that gets soldered while only the simulation copy sees the supply behind it. `designs/sensor_node.nim` was converted from `kind = "voltage_source"` with `rout`/`lout` — which modelled what was *behind* the connector and put a part on the BoM nobody solders — and every measured number is unchanged, which is the correct outcome for a refactor that describes the same electrical situation. `harness` attaches what is outside — a source of stated stiffness (`driveSource`), a resistive load (`driveLoad`), a constant-current sink (`driveSink`) or nothing (`driveOpen`) — so an *outgoing* connector is expressed the same way an incoming one is — which is the **simulation** feature and takes that 0 V to 4.995 V. **`driveLoad` and `driveSink` are not interchangeable, and the difference is not only accuracy**: a resistor's current follows the rail, so it *damps* the decoupling network, while a constant-current sink is an **open circuit at AC** and damps nothing. Measured on the same board, the anti-resonant peak reads 3.57 ohm against a 33 ohm resistor and 4.01 ohm against a 100 mA sink — so modelling a regulated load (an MCU, a module with its own converter) as a resistor understates by 12% the very peak a PDN sweep is run to find. They agree at the operating point and nowhere else. A source is attached through its own `rout`/`lout` and never directly, for the reason `expandSourceImpedance` exists: an ideal source is a dead short at AC, so a port driven by one reports the rail behind it as 0 ohm at every frequency. A port nobody described is left alone rather than defaulted, and an unknown port name raises. **`harness` does not build itself by instantiating `asSubcircuit`'s template**, and that is worth knowing rather than rediscovering: flattening would immediately undo the round-trip and the result would be identical for more work. The subcircuit is for export and for saying where the boundary *is*, not for making the sums come out. **One description, two questions.** `asSubcircuit` is what lets a board answer both "what does it do on the bench" and "what does it do plugged into the product": `harness` for the first, and instantiating the templates into a parent netlist for the second. The boards keep their own connectors — only the copies lose them — so nothing has to be rewritten to move between the two. What that buys is measurable: a supply board on its own reports 4.89 / 4.78 / 4.56 V depending purely on the sink you *assumed*, while wired to the real sensor board it reports 4.781 V because the actual load is in the circuit. `graph.instantiateByPort` and the DSL's `instance XA, tmpl, {"vin": usb, "vout": rail}` wire **by name**, and that is not a convenience: a connector-derived port list came from whichever nets the connectors sat on, two boards in one system routinely both call a port `vin`, and swapping two same-shaped nets is a miswiring that raises nothing and simulates happily. Every port must be named — an unwired one raises listing what the board exposes, because an open port on a board-to-board connection is a disconnected system and the point of assembling one is that the connection exists. `formats/spice.writeSubcktDefinition` is how such a template leaves the process, since `writeNetlist` drops `Netlist.ports` — correct for a board, whose top-level deck has no port concept, and silently wrong for a template built to be reused.
- **`flatten.nim`** — dissolving hierarchy so a simulation can see through it, and the resolution of what `docs/RESOLVED_FINDINGS.md` §14 left deferred. `flatten(nl, keep)` splices every subcircuit instance into its parent, depth-first and innermost first: port nets merge through `Pin.hierNet`, ground merges rather than becoming `XL.0`, `clone`-shared globals are left alone, and child `.MODEL` cards merge three ways (absent → hoist unmangled, identical → drop, conflicting → mangle and rewrite `attrs["value"]`, which is real rather than hypothetical since `xspice/instance` derives a card name from the designator). It **mutates in place**; run it on a clone. `keep` names instances to leave intact, because the one real objection to flattening is that it dissolves a component something refers to by designator — and a `keep` entry matching nothing **raises**, on the same reasoning as `without`. Every analysis calls `flattenForSim` on its work copy immediately after cloning and **before any model pass**, and that ordering is the whole argument for this route over teaching the isolation walk to traverse: `expandPinModels`, `expandSourceImpedance` and `expandCapacitorParasitics` all walk only `nl.components`, so a part inside an instance is invisible to every one of them. Left un-flattened, an op-amp inside a subcircuit never gets a macromodel and reaches the deck as `U1` — which ngspice reads as a uniformly-distributed RC line. It lives under `spice/` rather than beside `graph.instantiate` because flattening destroys the hierarchy the designer wrote: it is a simulation-only concession, and putting it in `netlist/` would invite someone to flatten a real design.
- **`models.nim`** — simulation-only device models, both of which *invent numbers the netlist does not contain* and so both return `seq[string]` assumption lines for `AnalysisReport.assumptions`. `expandCapacitorParasitics` rewrites each capacitor into series C + ESR + ESL from `attrs["esr"]`/`attrs["esl"]`, else a per-`attrs["package"]` typical, else a global fallback. This is not a refinement: an ideal capacitor's impedance falls monotonically forever, so a PDN sweep over ideal caps shows no ESR floor, no self-resonance and no anti-resonance — none of the three things such a sweep is run to find. `idealOpAmp(name, aol, gbw, vsatHi, vsatLo)` returns a template `Netlist` (ports `INP`/`INN`/`OUT`) built as a VCVS of gain `aol` into an RC pole at `gbw/aol` into a unity-gain buffer, for `graph.instantiate`. `opampModel`, the flat macromodel every un-named op-amp gets, reads **both** `gain` and `gbw` off the component -- `gbw` was a `const 1.0e6` there until it was noticed that the assumption line reported that 1 MHz with `annDefaulted` provenance *while a stated `gbw` sat one field away unread*, which is the worst shape a default can take: the report then reads as the design not having stated one. `analysis/opamp` already honoured the annotation, so the two paths disagreed about the same part, and this is the only path for every amplifier a `.tran` sees. It models open-loop gain, roll-off and the 90° of lag that comes with them, and *nothing else* — no offset, slew rate, output impedance or second pole. **It does saturate, when told what its rails are.** Unbounded, the output buffer is a VCVS, which is an ideal source and therefore cannot run out of swing however hard the loop drives it — so a stage whose only nonlinearity is the amplifier saturating measured perfectly clean, which is a statement about the model rather than about the circuit. Given finite `vsatHi`/`vsatLo` the buffer becomes a `B` source carrying `min(max(V(N2), lo), hi)`. Clamping the VCVS's *output* with diodes instead achieves nothing, because an ideal source holds its node regardless of what is hung across it; the clamp has to sit between the pole and the buffer. `supplyRailsOf` reads the rails off the part's `V+`/`V-` pins' nets (from the **net**, unlike a regulator's output voltage — here the rail is what the part is connected to rather than something it makes), and a single-supply part with `V-` on ground gets 0 for the lower one. **The clamp is applied only by a large-signal caller**, and that is not an optimisation: `min`/`max` has a zero derivative at its limit, so an `.ac` linearisation of a stage whose operating point sits on a rail comes back with no gain at all rather than with the small-signal gain it has — and a single-supply stage with a ground-referenced input sits exactly there. `spec.vsatHeadroom` backs the limits off each rail; at its default of 0 the model saturates exactly at the supply, which no real amplifier does, so it bounds the swing rather than predicting it and says so as an assumption. Its own pole capacitor is marked `attrs["parasitics.expanded"]` so parasitic expansion never gives a modelling element a resonance the real part does not have. `expandResistiveParts` does the same for `wire`, `jumper` and `fuse`, which collapse to the resistor each one is and differ only in where the number comes from — and **that difference is the hazard**: a link's `value` is ohms (a "0 ohm jumper" is sold that way) and a fuse's is **amps**, so reading a 2 A fuse's value as 2 ohms would put forty times its real cold resistance in series with a rail and quietly explain away a drop nobody would otherwise accept. A fuse's resistance therefore comes from `dcr` and its `value` is read as `current_rating`. Deliberately not modelled: a fuse *blowing* (an I²t integral over a fault — a design check asks whether the circuit works, not what it does while failing) and trace inductance (roughly a nanohenry a millimetre, and a netlist carries no length — that is `nimcir/pcb`'s to answer). `prefixByDeviceKind` also gained `cccs` -> `'F'` and `ccvs` -> `'H'`, for a narrower reason than `E`/`G`: an `F`/`H` line is *not* positional over nets, since its third token names the controlling voltage source, so writing one still emits the wrong arguments — but without the entry a `cccs` reaches the deck under its own `C` and is read as a **capacitor**, silently. A loud failure about a device that exists beats a silent 2 F capacitor.

  **The invariant, and it is generated rather than listed** (`tests/test_spice_spellable.nim`): *a kind `kinds.isPassive` accepts must be something the deck writer can spell — either `designatorPrefix` knows its letter, or a model pass rewrites it into parts that do.* Passivity is what makes it load-bearing: `expandPinModels` stands in for every part `isPassive` **rejects**, so those never reach a deck as themselves, while `spice/isolate` absorbs every part it **accepts**, so those do. The test iterates `conductiveKinds`/`blockingKinds`/`behaviouralKinds` rather than reciting a list, for the same reason `describeQuantities` computes reachability rather than writing it down — a hand-kept list is exactly what drifts from the tables it describes. Adding a kind with neither a letter nor a model fails it by name. It was violated three times before anyone wrote it down. `expandFerriteBeads` rewrites every `kind == "ferrite_bead"` into the standard three-element model — a series `dcr` into a parallel R‖L‖C — and it is called from `expandPinModels`, so every analysis gets it. **A bead is not an inductor and modelling it as one is wrong in the direction that matters**: an inductor's impedance climbs without limit, a bead's peaks where the core goes lossy and falls again, and that peak is the entire reason a bead is chosen over an inductor. The element values fall out of the three numbers a datasheet gives — `R = z_peak - dcr`, `L = R/(2*pi*f_peak*Q)`, `C = Q/(2*pi*f_peak*R)` — so at `f_peak` the reactances cancel and the impedance *is* `R`: the peak lands where the datasheet says by construction rather than by fitting, verified at 600.00 ohm at exactly 100 MHz. `Q` is the one thing the datasheet's headline numbers cannot pin down (they fix the height and the location, not the width) and defaults to 1.0, a broad peak — beads are deliberately lossy, and a high-Q one would be the inductor it was chosen instead of. `value` is read as ohms when `z_peak` is absent, which follows the convention a bead is *sold* by ("a 600 ohm bead"), and `f_peak` defaults to the 100 MHz datasheets quote; both are declared. This is also **what stops a bead being simulated as the wrong device**: `ferrite_bead` is in `conductiveKinds`, so `isPassive` accepts it and the per-pin stand-in skips it, but SPICE has no bead device and a deck line beginning `FB` is read by ngspice as a current-controlled current source. After this pass there is no bead left to misread. `designs/sensor_node.nim` switched from `kind = "inductor", value = "600n"` to the real part and its `vdda` overshoot went from **109 m% to 0** — the old figure was an undamped LC ringing, because an ideal inductor has no DC resistance and a bead has 350 mohm of it. `expandCapacitorParasitics` also **bias-derates a Class 2 ceramic before expanding it**, and that is the single largest correction in this module: an X5R bank at about two thirds of its rating measured **1.23 ohm** of worst in-band rail impedance where the same parts at their nominal values said **173 mohm** — seven times, larger than every other correction here put together, which is why it is on by default. `dcAcrossCapacitor` takes only the unambiguous case (one plate on the reference, the other on a rail with a stated voltage); a coupling capacitor between two signal nets returns 0, meaning *not known here*, and is left alone rather than guessed at, since knowing would need an operating point this pass runs before. Dielectric is taken from `dielectric`, else inferred — a package naming a non-ceramic family is never guessed into a ceramic — and a missing `voltage_rating` is assumed at twice the working voltage. Both assumptions are declared. The honest caveat, which belongs with any number that came through here: **real DC-bias loss depends far more on case size and capacitance density than on the dielectric letter**; a 10 uF 0402 X5R can be a fifth of its label at rated voltage while a 100 nF 1206 X7R barely moves, and both are "Class 2". Class 1 is the exception that is exact rather than typical: C0G/NP0 is paraelectric and does not depend on applied voltage at all, which is what makes `cuTiming` -> C0G a physics decision. `tests/test_analysis_pdn.nim`'s fixtures had to be made C0G for exactly this reason — every check in them is a closed-form identity about the capacitance a part *has*, and derating moved `f_z_min` by 25% and `z_at_100kHz` by 54% when it landed. `expandSourceImpedance` puts a finite `rout`/`lout` in series with every source, because **an ideal source is a dead short at AC**: a PDN sweep over a design carrying its own regulator reports 0 ohm at every frequency and passes any target — measured, the same rail reads 129 mohm undriven and 0 with an ideal source on it. The default is 10 mohm in series with 1 uH, the flat part standing for the regulator's closed-loop output resistance and the inductive part for both the supply wiring and the rise in output impedance above the loop's bandwidth. The *exact* figures matter little and that is the point: the supply sits in **parallel** with the decoupling, so once its impedance is above the capacitors' the answer barely moves — which is what makes a default defensible here and not, say, for an ESR. `rout = 0.ohm` plus `lout = 0.H` opts back into an ideal source, which is right for a stimulus and wrong for a supply. `expandPinModels` stands in for every part `kinds.isPassive` rejects — no model, no `subNetlist`, no `simReplace` left to apply — by giving each pin an impedance chosen from `Pin.kind`: low for `ptOutput`, high for everything else, and `ptGround` untouched because a resistor from the reference to itself models nothing. Without it a `.op` over any board with an MCU on it dies inside ngspice on `u1 vdd 0 sda scl` with an unknown-model error, which tells the reader nothing about their circuit. Two limits are stated rather than discovered: an output is modelled as a low impedance **to ground**, since a netlist does not record which state it drives (a small-signal stand-in, not a logic level), and an open-drain or open-emitter output is genuinely high-impedance but indistinguishable from a push-pull one by `Pin.kind` alone — tag it `ptInOut` or annotate `zin`. The pass **destroys any path through the part**, every pin being tied to the reference independently; that is right for asking what a part loads a rail or a bus with and wrong for anything a signal must pass through. Which is why parts that *do* carry a path are routed through a separate **behavioural-model registry** keyed by `Component.kind`, consulted first: `regulator`/`ldo`/`vreg`/`dcdc`/`smps`/`buck`/`boost` become an ideal source at their output voltage instead. Its `BehavioralResult.handled = false` means **leave the part exactly as it is** — emphatically not "fall back to per-pin impedances", because an LDO stood in for by two independent resistors to ground reports its rail at 0 V, which is a confident wrong answer where refusing to simulate was an honest one. That was a real regression, caught and fixed: a board with an AMS1117 on it went from `notEvaluated` to `FAIL, measured 0 V`. The regulator model reads its output voltage from the **component**, never the net, and that is the whole reason a `dc_voltage` claim stays worth making — the net's `voltage` is what the rail is *required* to be and the component's is what was *chosen*, so a 5 V part on a 3.3 V rail reports `measured 5.00 V, expected 3.30 V +-5.00%`; read it off the net and the check measures its own assumption back and passes every time, the same trap `runDcVoltage` avoids by refusing to isolate. A regulator stating no `voltage` is declined rather than guessed at, with a note saying what to state — and `failBatch` carries assumptions on the failure path precisely so that note survives, since otherwise the reader is left holding a raw ngspice error instead of the one sentence that fixes it. `bufferModel` is the signal-path counterpart, covering `buffer`/`voltage_follower`/`unity_gain_buffer`/`line_driver`/`level_shifter`: it becomes a VCVS from input to output, because a buffer sitting in a feedback path and stood in for by two impedances to ground does not merely lose accuracy — it **opens the loop**, and a loop-gain figure measured over an opened loop is a confident number about a circuit that is not the one on the bench. Unity is assumed where nothing states otherwise, which is defensible here and was not for a regulator: a part whose kind is `buffer` has a gain of one *by definition*, whereas nothing about the word `regulator` says what voltage it makes. `opampModel` covers `opamp`/`op_amp`/`operational_amplifier` and is what makes a *cascade* measurable: an analysis models the one amplifier it is named, and before this every other op-amp in the path fell through to per-pin impedances — 1 Mohm on each input, 50 ohm on the output — which does not lose accuracy so much as **delete the stage**, and a 4th-order Sallen-Key filter measured end to end reported 82 dB of peaking against a response that is flat to 20 kHz. It is emitted **flat rather than as an instance of `idealOpAmp`**, which is the non-obvious part: `spice/isolate` treats any component carrying a `subNetlist` as something it may not traverse, so a macromodel dropped in as a subcircuit is cut at the very boundary it was added to bridge — the same broken path one layer along, worth 11 kHz instead of 20 on that filter. Emitted flat, every part is a resistor, capacitor or VCVS, all of which `isPassive` accepts. Deliberately **not** registered for `comparator`: this macromodel is linear and a comparator's entire behaviour is that it is not. Its `passesSignal` stays `false` unlike a buffer's, because `signalPathPins` is forwards-only and cannot answer for a part with *two* inputs — the simulated stand-in still closes the path, so an `.ac` sees the cascade while the static walk stays conservative. This is the chain, and it runs most-specific first: a `subNetlist` or a `simReplace` is honoured and never reaches the registry; a registered kind gets its model; only a part with neither falls through to per-pin impedances, which is the **last** resort and not the first answer. `registerBehavioralModel` is a runtime table for the same reason the role and evaluator registries are, and carries a `passesSignal` flag declared rather than inferred — a *static* check has to know the answer without simulating. That flag is what lets `analysis/opamp`'s feedback walk cross such a part, **forwards only**, entering at the input pin and leaving at the output (`signalPathPins`): the stated reason to exclude an active device from a feedback test is that its gain and direction are unknown, and for a registered kind they are not. Refusing anyway would leave the static check calling a loop open while the `.ac` closes it — two answers about one circuit. Every substituted value returns as an `Assumption` keyed `zin`/`rout`/`lout` with `annDefaulted` provenance, and a stated value produces no assumption at all — the record exists precisely where the choice between "somebody measured this" and "we guessed" is made.
- **`probes.nim`** — `addVoltageProbe(net)` is a pure label helper (no graph mutation: ngspice's default `.control`/`write` already dumps every node voltage). `addCurrentProbe(nl, pin)` *does* mutate: it splits the pin onto a fresh net and inserts a 0V voltage source in series, because ngspice only exposes branch current for voltage sources/inductors. It **refuses an XSPICE code model outright**: an `A` line's port text is rendered from the model's own `ModelSpec` at instantiation and kept verbatim in `attrs["xspice.ports"]`, so re-netting a pin would move it in the graph and not in the deck -- leaving the probe source in series with nothing while the code model went on driving the original net, which is a probe reading zero on a branch that is carrying current. `addImpedanceProbe(nl, net, refNet)` wires a `DC 0 AC 1` current source across `refNet -> net`; with a 1 A drive `v(net)` **is** Z in ohms, so an `.ac` sweep reads driving-point impedance with no division (the amplitude defaults to 1 for exactly that reason — `.ac` is linear, so drive level cannot affect the answer). Both probe/replacement mutators are meant to run on a clone or a `materializeSimNetlist` result, never the real design netlist.
- **`extract.nim`** — `extractInstance(comp, globalNets)` pulls a hierarchical component's `subNetlist` out standalone (thin wrapper over `clone()`). `extractSubcircuit(nl, name, designators, globalNets)` extracts an arbitrary *flat* selection of `nl.components`: clones the whole netlist, computes boundary nets from the *original* graph (any net touching both a selected and a non-selected component) and promotes them to ports, then removes everything not selected.
- **`ngspice.nim`** — `writeDeck`/`writeDeckFile` are thin wrappers over `formats/spice.writeNetlist`'s `cards` param. **`run(nl, analysis, setup)` separates the two kinds of dot card, and the separation is the point.** One *analysis* per call is a real limit — ngspice's default `write` keeps only the last analysis's plot (confirmed empirically, not assumed) and a `SimResult` holds exactly one plot, one `plotName` and one `dataKind`. But `.ic`, `.nodeset`, `.options`, `.param` and `.temp` are not analyses: they configure the analysis that follows and produce no plot. The old guard counted `cards.len`, so `run(nl, @[".ic v(out)=0.1", ".tran 1u 10m uic"])` — one analysis, one setup line — was refused for being "two cards", and `docs/findings.md` §23 recorded the oscillator blocker as "`run` must accept more than one card" when what it needed was for `run` to stop counting setup as analysis. Setup cards are written first, then the analysis; a *known* analysis card in the `setup` slot raises (`analysisCards`/`isAnalysisCard`), while an unknown card is passed through rather than guessed at, on the same reasoning as `parseSpiceMagnitude`. The `run(nl, cards: seq[string])` overload is kept because every existing call site passes a single-element seq and there is nothing wrong with those; more than one still raises there rather than being split by guesswork, since that overload cannot know which the caller meant. `analysis/transient.TransientSpec.initialConditions` is the first consumer: node -> volts, emitted as `.ic` and forcing `uic`, which is what reaches a circuit that will not start from its own operating point. **`uic` is not free and the cost is declared as an assumption on every run that uses it**: it skips the operating-point solve, so every node *not* named starts at zero rather than at its bias. Verified end to end on an LC tank — 0 V forever from its own operating point, 2 V of ring at 5000 Hz measured against 5033 Hz ideal when kicked. `run` treats "a parseable raw output file exists" as the success signal rather than the process exit code, which was found to be unreliable (a clean run with only benign warnings can still exit non-zero; a malformed deck can SIGABRT). Output is parsed from ngspice's ASCII rawfile format (`set filetype=ascii` + `write <path>` inside `.control`), including `.ac`'s `Flags: complex` layout, where each value is a bare `real,imag` pair with no space around the comma and the line shape is otherwise identical to a real plot. **A parseable rawfile is not the same as a solution**, and the difference cost a real answer: ngspice reports a failed DC solve as a *warning*, writes whatever its last iterate was and exits zero, so the numbers arrive looking exactly like an answer — the LT8640A reference design's 5 V rail read **1.71 V** as a clean FAIL because one node had no DC path. The log is now scanned for `singular matrix`, `iteration limit reached`, `too many iterations` and `no convergence`, and the run raises naming the node. The marker list is deliberately narrow: `gmin stepping failed` and `source stepping failed` are *strategy* notes and ngspice usually recovers after them, so treating those as fatal declared the TS808's bias-finding `.op` a failure and took its large-signal drive offset to 0 V. `run` also unions its explicit `codemodels` argument with `xspice/instance.collectCodeModels(nl)`, so no call site has to know which code models survived four transforms. `$NIMCIR_KEEP_DECKS` copies every deck handed to ngspice into a directory: each fragment simulated here is *derived* — isolated, terminated, model-substituted — so it is not the netlist anyone wrote, and reasoning about a surprising number from the design file alone is guesswork. Probing an internal node of a *nested* subckt instance via ngspice's hierarchical node-path syntax is unsupported — use `extract.nim` to pull the region of interest to the top level first instead.

### `analysis` submodule

`src/nimcir/analysis/` answers questions *about* a netlist, from pure graph walks up to full circuit simulation. It depends on `nimcir/netlist` and `nimcir/spice`; neither depends back on it.

**Two result types, because there are two kinds of question.** `Issue` (`issue.nim`) is a yes/no finding — something is wrong, here is what and where; `kind` is an open-ended string, and a check *never raises* on a netlist-content problem, the problem is the return value. `AnalysisReport` (`report.nim`) is a *measurement*: extracted scalars (`Measurement`), the `Issue`s they imply, the full `SimResult` curve behind them, and `assumptions`. A frequency response does not fit in an `Issue`.

**`assumptions` is load-bearing, not decoration.** Every simulation-backed analysis here works by filling in data a netlist does not carry — an assumed regulator soft-start ramp, a package-typical capacitor ESL, a substituted ideal op-amp, an ideal rail source, a leak resistor on an open port — and a number derived from an invented input has to say so where the reader will see it. They are `Assumption` records from `netlist/annotations`, not prose, so a consumer can count them or filter by provenance — `invented()` returns the values nobody actually stated, which is unanswerable while assumptions are strings.

`src/nimcir/analysis.nim` is the hub and exports only what runs with no external toolchain (`issue`, `io_check`, `measure`, `report`). Anything needing a simulator is opt-in per-import, the same rule `spice.nim` applies to `spice/ngspice`: `spice_fallback` (`.op`), `operating` (`.op`), `derating` (`.op`), `pdn` (`.ac`), `startup` (`.tran`), `transient` (`.tran`), `opamp` (`.ac`), `contract_eval` (all three).

- **`contract_eval.nim`** — registers the simulation-backed evaluators into `nimcir/contract`'s registry: `dc_voltage` via `.op`, plus harvest adapters wrapping `analyzePdn`, `analyzeStartup`, `analyzeTransient`, `analyzeOpAmpResponse` and `analyzeLoopGain`. `spice.transient` declares `settled_v`/`ripple_pp`/`settled_min`/`settled_max` and **not** `final_v`, even though `analyzeTransient` measures one: `spice.startup` already produces that quantity, and `registerEvaluator` refuses a second producer outright. It lives here rather than in `contract/` because `contract` depends only on `netlist` — that is what keeps a design inspectable with no simulator in the build — and an `Evaluator` is a proc-valued data object, so registering from another module is the ordinary path. **Every adapter runs its analysis in measurement-only mode**: each `*Spec` carries limit fields stating the same kind of claim an `Assertion` states, and leaving them live reports one claim twice, possibly at two thresholds. The assertion is the authority. The disabling values are **not consistent** and are verified, not assumed — `targetZ`/`overshootLimit`/`maxPeaking` are `>` tests needing `Inf` (`targetZ = 0` flags *every* rail), `minPhaseMargin` is a `<` test needing `-Inf`, while `currentLimit`/`minBandwidth` are gated on `> 0` and so are disabled by zero. Non-limit issues (`pdn_no_decoupling`, `opamp_no_feedback`, `*_simulation_failed`) still ride along on `AssertionResult.issues` as diagnosis.

- **`measure.nim`** — pure curve math over `openArray[float]`: no netlist, no simulator, no I/O. This is deliberately where the bulk of each analysis's *reasoning* lives, so it is testable offline. `harmonicAmplitudes`/`thd` integrate **directly over the samples' own timestamps** rather than resampling onto a uniform grid: a `.tran` result is not uniformly sampled, and ngspice takes its smallest steps exactly where a clipped or slewing edge is — which is where the harmonics live — so resampling would discard resolution precisely there. The window is the **last whole number of periods**, endpoints interpolated to be exact, because a Fourier integral over a fractional period leaks the fundamental into every harmonic bin and a leaked fundamental reads as distortion the circuit does not have. Fewer than two whole periods, or no fundamental, yields `NaN` rather than a confident zero. Procs taking a frequency axis accept `logX`, and the frequency wrappers (`corner3dB`, `unityGainFreq`) pass `logX = true`: on a `dec` sweep, linear interpolation between decade-spaced samples is visibly wrong near a corner. **Anything not found is `NaN`, never raised or clamped** — "this response never crosses -3 dB in the swept band" is a real answer about the circuit. `gainMax`/`bandEdges` are the **band-referenced** counterparts to `corner3dB`, and the pair exists because the two reference points answer different questions: `corner3dB` measures from the *first swept point*, which is right for a DC-coupled low-pass and is the **stopband** of every AC-coupled stage — a single-supply amplifier's gain-setting leg is capacitively coupled, so its gain at DC is unity *by construction*, and that is what makes one supply work rather than a fault. `bandEdges` references the response's maximum instead and returns both corners, `NaN` on a side that never falls that far (a DC-coupled stage genuinely has no lower edge, and reporting the bottom of the sweep as one would invent a corner). `fundamentalFreq` is where an oscillator's specification starts, and it is deliberately **not** a spectral estimate: an FFT's resolution is one over the window, so a 20 ms window resolves 50 Hz and would place a 1.59 kHz oscillator to within 3% -- useless against a network whose whole job is to fix that frequency. Counting rising crossings of the window's own **mean** instead resolves to the *timestep*. The mean rather than zero, because a single-supply oscillator sits at mid-rail and has no zero crossings at all; with a hysteresis band, because a harmonic-rich wave crosses the mean six times a period and would otherwise read at three times its rate. Fewer than two crossings is `NaN` -- the answer for a circuit that did not start, and it must stay distinguishable from 0 Hz. `gainMax` is named for what it measures rather than "passband" because **no attempt is made to detect the shape** — on a flat-topped band-pass the maximum *is* the passband, on a resonance it is the peak, and guessing which would be a judgement this cannot back up. Malformed *input* (empty or mismatched arrays) is a caller bug and does raise.
- **`io_check.nim`** — the static checks (`checkOutputConflicts`, `checkDCPaths`, `checkRailVoltages`, bundled as `analyzeIO`). **`checkRailVoltages` is a structural finding and not an assumption, and that distinction is the whole point of it.** A rail with a stated voltage gets an ideal source at an isolation boundary; a rail without one is *cut loose as a floating node*, which changes the topology rather than substituting a value. In `designs/ts808_drive.nim` the divider-derived 4.5 V bias initially carried no voltage, and cutting it loose detached the drive stage's gain leg — an amplifier with a gain of 65 measured as a unity-gain follower, 5.9 mdB of peaking against a real 31.6 dB, every claim passing, `exit 0 (clean)`. The floating rail *was* reported, as one assumption among fifteen, reading exactly like the package-typical ESR two lines above it. Being reported and being noticed are different, and the difference is which section it lands in. `sevWarning` rather than `sevError` because a rail nothing simulates is harmless and a design may legitimately not know a voltage yet; the message names the components that would lose their connection, skipping bypass capacitors, since a rail carrying only power pins and decoupling loses little by floating, plus `spice_fallback.nim`'s opt-in `.op`-backed resolution of anything the static walk can't classify. Classification tables now live in `netlist/kinds.nim` and are re-exported from here, so the old `classifyConductivity`/`Conductivity` API is unchanged.
- **`operating.nim`** — one `.op`, solved once and handed to everything after it. **The reason this can be a straight line rather than a fixed point is that at DC a capacitor is an open circuit, so the operating point cannot depend on capacitance** — verified, not assumed: `v(mid)` on a divider with a cap across the lower leg is bit-identical with 100 pF and with 1000 uF. So the `.op` is solved first, every Class 2 ceramic is derated from its *actual* node voltages, and the `.ac`/`.tran` that follows runs against the derated values, with no iteration and no ordering ambiguity. It buys two things. It closes a blind spot that mattered: `spice/models` could previously only read a *stated* rail voltage, so a capacitor on any unannotated node was not derated at all — and that covers precisely the nodes where bias is worst. A 10 uF rated 6.3 V on a 12 V divider's midpoint sits at 95% of rating and came through at its full nominal value; with the operating point it derates to **3.29 uF**. And it removes duplicate solves — `dc_voltage` solved one, `analysis/derating` solved one per claimed rail, all of them the same design with the same answer; `templates/rail.nim` went from three decks to two and `designs/sensor_node.nim` now runs exactly one `.op` for two rails. `voltageAt` returns **`NaN` for a node the solver never saw**, which is a different answer from zero and must stay so. `contract_eval` owns the cache (`sharedOperatingPoint`), **scoped to the `EvalContext`** and stored in its `scratch` under `"spice.operating_point"`. It was previously a module-level `var` keyed on `Design` *reference identity* with no content invalidation, carrying a documented rule instead of a guarantee: a caller that edited a design and evaluated again got the first answer back silently, two designs checked in one process shared one slot, and `verify.readiness` had to bracket every run with `clearSharedOperatingPoint` to stay safe. A context lives exactly as long as one run and a design does not change under a run, so there is no window in which the entry can be wrong — which is what makes a sweep over candidate component values safe, and that is the obvious way to have hit the old bug. Stated limit: **a `.tran` bias moves with time**, so one number from t = 0 does not describe a charge pump's flying capacitor or a rail that is still soft-starting; derating those from this is less wrong than not derating them, and still wrong.
- **`derating.nim`** — the other half of what a rating is for. `spice/models` uses `voltage_rating` to place a ceramic on its DC-bias curve, which *changes* the answer; this asks whether the part is being used within what it can take, which changes nothing and is the difference between a board that works and one that fails in the field. One `.op` over the whole design — **not isolated**, for the same reason `runDcVoltage` is not: a fragment terminated with ideal sources would check parts against voltages the boundary invented. Checks `voltage_rating` against the DC actually across each part, and `power_rating` on a resistor against V²/R. Ceilings are **per dielectric family** because the reason to derate differs: a tantalum is held to 50% because it fails *short* and takes the rail with it, whereas a ceramic's headroom is mostly about capacitance, which `spice/models` now models directly — applying the tantalum rule to ceramics would double-count it. `power_rail` gains an opt-in `maxDerating` param, and the evaluator is keyed by rail (one `.op` per claimed rail, since the quantity reduces to a *worst* over a filtered set and one run cannot serve two subjects). **`current_rating` and `isat` are registered, set by the part policy, and checked by nothing** — a branch current is not in a `.op` for anything but a voltage source, and an inductor's peak needs a `.tran`. That is a real gap and it is the one that matters for a converter, where saturation is the failure mode.
- **`pdn.nim`** — `analyzePdn(nl, powerNet, groundNet)`: decoupling impedance vs frequency. Isolates everything on the rail (`isolateNets`, with the rail *excluded* from termination so it isn't AC-shorted by an ideal source), expands capacitor parasitics, injects 1 A of AC and sweeps. Reports the ESR floor and composite self-resonance (`z_min`/`f_z_min`), the worst in-band impedance, `z_at_<f>` at named frequencies, and — the point of the whole thing — `z_antiresonance`/`f_antiresonance`, the interior impedance *peak* where a bulk cap's inductance rings against a ceramic's capacitance. That peak is created by adding decoupling, is not fixed by adding more of the same capacitor, and is invisible to any ideal-capacitor model. **The target check is bounded on both sides** (`targetFrom` 100 kHz, `targetTo` 100 MHz): below the supply's regulation bandwidth the *regulator* holds the rail up, and it was cut away at the boundary; above ~100 MHz the impedance is set by plane capacitance and package/via inductance, none of which is in a netlist. Checking outside that band flags every board for something no capacitor change can fix. The sweep still runs to 1 GHz so the rise is visible. Two substitutions happen around the isolation and their *order* is the load-bearing part: `expandPinModels` runs **before** it, because `isolate` refuses to traverse an unmodellable component and records it in `dropped`, so by the time it has run there is nothing left to model — once each such part is a per-pin impedance it is passive, and the rail sees what it actually hangs off instead of an open circuit. `expandSourceImpedance` runs **after**, on the fragment, alongside the capacitor parasitics. `modelUnmodelledParts = false` and `modelSources = false` restore the older behaviour of cutting parts away and leaving sources ideal.
- **`startup.nim`** — `analyzeStartup(nl, regulator, outputNet, measureNet)`: rail ramp-up and inrush, via `.tran` only. `measureNet` defaults to `outputNet` and differs whenever there is post-regulator filtering — a series inductance into a capacitor bank is a resonant circuit that can ring the rail well past target, and measuring at the regulator pin would show a clean ramp and miss it. **State plainly what this is**: unless the component carries a `simReplace`, it substitutes an ideal source following an assumed soft-start ramp and measures what the *output network* does — the RC/RLC rise, the overshoot that network produces, and the current the capacitors demand while charging. There is no control loop, no current limit or foldback, no dropout, no load regulation. A rail that overshoots here would overshoot on a real board; a rail that looks clean here can still misbehave for loop-stability reasons this cannot see. Loads that carry no model are stood in for by `models.expandPinModels` before isolation, so the rail ramps into something rather than into an open circuit — with **the regulator excluded**, since it is about to be stood up as a soft-start ramp and the behavioural regulator model would otherwise quietly overwrite the one thing this analysis exists to measure. Every caller that seeds an isolation on a particular part passes it in `exclude` for that reason. **Every rail downstream of the regulator is seeded and left un-terminated too** (`downstreamRails`, a walk crossing `isPassive` parts only, which therefore stops dead at the regulator and never reaches its *input* rail — that one genuinely is up before start-up begins and must keep its ideal source). Nothing downstream is at its nominal voltage while the rail is ramping; that is the premise of the measurement. Leave a ferrite-filtered analog rail out of the seed set and it becomes a boundary termination — a stiff ideal source at 3.3 V — driving current backwards through the filter into a rail still at zero: measured, **2.8 kA of inrush against a true 163 mA**. This is the transient twin of what `IsolationSpec.excludeRails` already exists to prevent in `.ac`, where an ideal source is a dead short; the same field carries both and only the reason differs. Seeding rather than merely excluding is what pulls that rail's own capacitor bank into the fragment, and the regulator really does have to charge it. **A regulator that brought its own model is honoured through every route a `SimReplacement` has, including `build`** -- which is the only one that can express a code model, and which `replaceComponent` would have read as an empty `kind` wired to nothing. Three assumptions that held only for the ramp this analysis invents itself were removed with it: the part is resolved through `findComponent` so a hierarchical path works; the inrush probe no longer assumes a pin named `"+"` (that is the pin of *this* analysis's PWL source and no other model has to have one) but looks for a pin on the output net, reporting **no** `inrush_peak` rather than a zero when there is none -- a switching regulator drives a switch node into an inductor, so the current reaching the rail is the inductor's and no single branch carries it; and `StartupStart` decides where t = 0 is, with `ssAuto` starting from zero with `uic` when the part brought a model. It has to: an operating point finds the state a soft start settles *to*, so the `.tran` would begin at the end of the ramp and report a rise time of zero for a part that takes milliseconds. The `regulator` role's `tRun` is the matching condition, since a run length derived from the *assumed* ramp says nothing about the schedule a part's own model keeps to.
- **`transient.nim`** — two analyses over one `.tran` run, neither of which **binds a driving part**, which is the point of it: `analyzeStartup` wants a regulator to stand up as a ramp and `analyzeOpAmpResponse` wants an amplifier and an input, so between them they miss a charge pump, an oscillator and a converter measured cycle by cycle. `analyzeTransient(nl, measureNet, spec)` reports what a node **settled to** -- `settled_v`, `ripple_pp`, `settled_min`, `settled_max`, `final_v` -- and `analyzeOscillation(nl, measureNet, spec)` reports what it is **running at**: `osc_freq`, `swing_pp`, `osc_thd_pct`. They share `runWindow` deliberately -- same netlist, same window, same `uic` -- since having two questions diverge in the *simulator setup* as well as in the arithmetic is how one of them quietly measures a different circuit. The design is simulated **as authored, with no isolation**, following `runDcVoltage`'s precedent rather than `analyzePdn`'s: a rail terminated at its nominal by the boundary would be a check that measures its own assumption and passes every time. **The window is the product** -- `tSettle` says when the measurement opens and is *stated rather than detected*, because what counts as settled is a judgement about the circuit (a converter's output settles in a hundred microseconds, a soft-started rail is not settled for five milliseconds) and a detector that guessed wrong would report a start-up transient as ripple. Everything before it is simulated and discarded, via the `.tran` card's `tstart` and again over the samples, which are not the same job: one controls how much data crosses the process boundary and the other controls what is measured. `capacitorParasitics` is on and load-bearing rather than merely more accurate: a switching converter's output ripple is mostly the inductor's current triangle across the output capacitor's ESR, and an ideal capacitor has none. **The derived print step is also ngspice's ceiling on its own internal timestep**, so it sets how accurately the circuit is *solved* and not merely how often the answer is written down -- which is why `runWindow` takes `windowSamples` and `analyzeOscillation` passes ten times what `analyzeTransient` does. A settling voltage and a peak-to-peak barely notice; a frequency does. On `wien_osc`, whose window is 31 whole periods, a thousand samples read 1568.4 Hz where ten thousand read 1573.26 and a hundred thousand 1573.31 -- the ordinary default wrong by 0.31%, three times that design's claim band, in a way that looks like a circuit measurement rather than a setting. **Reaching a circuit that will not start from its own operating point** is `TransientSpec.initialConditions`: node -> volts, emitted as `.ic` and forcing `uic`. An oscillator's operating point is a balance it never leaves, so a `.tran` from it reports a flat line -- a correct answer to a question nobody asked. `uic` is not free and the cost is declared as an assumption on every run that uses it: the operating-point solve is skipped, so every node *not* named starts at zero rather than at its bias. `analyzeOscillation` measures frequency **first**, because `thd` integrates over whole periods of it and a Fourier integral over the wrong period leaks the fundamental into every harmonic bin; a `NaN` frequency raises `KindDidNotOscillate` naming which of the two causes it was -- the node never moved (kick it) or it is moving but not periodically inside the window (widen it).
- **`opamp.nim`** — three separate procs, because the three questions cost different amounts and are wrong in different ways if conflated. `checkFeedback` is a pure graph walk: is there a path from the output back to the inverting input through passives only? It accepts *blocking* parts, since a capacitor from output to inverting input is an integrator — negative feedback at every frequency that matters, though an open circuit at DC — and a DC-conductive-only walk would call every integrator broken. `analyzeLargeSignal` is the one that is *not* small-signal, and exists because everything else here is: `.ac` linearises about the operating point, so a clipping diode is whatever conductance it has at rest and never clips — the right model for gain and stability, the wrong one for an overdrive where the clipping **is** the product. It drives a sine and reports `thd_pct`, `output_swing`, `clip_high`/`clip_low` and `gain_compressed_db`. **The stimulus carries the node's own DC bias**, found by running a `.op` on the same fragment first: a single-supply stage sits at a mid-rail operating point, and hanging a `SIN(0 ...)` source on its input would clamp that node to zero and measure a circuit biased into its own stop. Coupling through a large capacitor is the other way to preserve the bias and is worse — the settling time constant becomes the input resistance times that capacitor, seconds for an ordinary input network, turning a millisecond run unusable. Stated limit: the substituted macromodel has no slew limit, no output current limit and no supply rails, so it never clips *itself* — distortion measured here is what the **network** produces, and a stage whose only nonlinearity is the amplifier running out of swing reads as clean. `analyzeOpAmpResponse` sweeps the **closed-loop** response for gain, bandwidth and *peaking*, and reports each of those **twice over, against two different references** — which is the only way to describe both a filter and a guitar pedal with one analysis. `gain_dc_db`/`bw_3db`/`peaking_db` are referenced to the first swept point; `gain_max_db`/`f_gain_max`/`f_lo_3db`/`f_hi_3db` are referenced to the response's maximum. For a DC-coupled stage the two agree and the second set is redundant. For an AC-coupled one the first set is arithmetically correct and answers nothing: the TS808 drive stage reports `gain_dc_db` of 0.001 dB against a real midband gain of 35.8, and a `bw_3db` of 710 kHz measured 3 dB below *unity*, on the far side of a passband that ends at 7 kHz. Nothing was removed when the second set arrived, because for the circuits the first set was written for it is still the right question. `gain_at_f` is the third way of asking and the one an audio stage is actually specified by ("20 dB at 1 kHz"); it is emitted only when `OpAmpSpec.gainAtFreq > 0`, and is `NaN` outside the swept band rather than extrapolated. `analyzeLoopGain` breaks the loop at the inverting input, injects there, and computes `T = -V(A)/V(B)` for a real phase and gain margin. **Phase margin is deliberately not read off the closed-loop curve**: it is a property of the loop gain `Aol*beta` at its 0 dB crossing, and the closed-loop response `Aol/(1+Aol*beta)` is a different function with a different phase — "180 + phase at unity gain" off that curve gives a number that looks like a phase margin, moves in roughly the right direction, and is not one. So the closed-loop pass reports peaking (a real, honest indicator, since a closed-loop peak is what low margin looks like from outside) and the margin comes from the loop measurement. The break is made at the amplifier input because that is a low-impedance-drives-high-impedance point, where inserting a series source does not disturb the loading the loop actually sees; the input source is zeroed so the only excitation is the injected one. Gain margin is `NaN` for a one- or two-pole loop, which approaches -180° asymptotically without reaching it — that is the honest answer, not a large finite number. Pin roles are matched by *name* (`+`/`IN+`/`INP`, `-`/`IN-`/`INN`, `OUT`/`VOUT`/...) because `Pin.kind` distinguishes input from output but not `+` from `-`, and that distinction is the entire content of "negative feedback"; an unmatched component raises naming the pins actually present rather than guessing. Parts *around* the stage that carry no model go through the same pre-isolation stand-in pass, with the amplifier excluded because it gets a macromodel instead. Both `modelUnmodelledParts = false` flags restore the older cut-at-the-boundary behaviour. **`180 + phase at crossover` is a phase margin only if the break opened the loop, and that is now checked rather than assumed.** Breaking at the inverting input opens the only feedback path a plain amplifier has, and for those the answer is exact — a follower and a gain-of-2 both measure 90° against the single-pole model. A Sallen-Key has *two*: its first capacitor returns to the **output**, and that positive path stays closed across the break, so the measured ratio is not a loop transmission at all — its phase starts near +79° instead of 0 and climbs through +180 while |T| is still above 0 dB, and the naive arithmetic reported **450°**, which is not a margin and which satisfies every `minPhaseMargin` a design could state. A stability claim that cannot fail is worse than no claim, so three signatures are tested — the low-frequency phase is not within 30° of 0 or 180, more than one 0 dB crossing, or a resulting margin outside (-180, 180] — and both margins come back `NaN` with a `KindLoopBreakInvalid` issue saying which. `NaN` reads as *notEvaluated* downstream, deliberately not a failure: the circuit may well be fine, it is this measurement that cannot say, and the closed-loop peaking still measured alongside remains a real indicator. **`checkInjectionPoint` refuses to sweep a stage whose input is inside its own loop.** Every `.ac` proc here measures by hanging an ideal source on the input net, and an ideal source *holds* that node — right at an input, catastrophic at a node the feedback returns to. A Wien bridge returns its positive feedback straight to `IN+`, so driving there shorted the bridge out and the tool reported `f_hi_3db` of **289 kHz** for a circuit that does everything it does at 1.59 kHz, with the claim **passing** at exit 0. The test is a conjunction and both halves are needed: the driven net is one of the amplifier's own input pins' nets, *and* the output reaches it through passives — either alone over-triggers, since an inverting amplifier's input net reaches the output through `Rin`+`Rf` but is not an op-amp pin, and a non-inverting amplifier's input *is* `IN+` but nothing feeds back to it. That walk additionally refuses to traverse a rail, the same rule `isolate` applies: the TS808's `vout` genuinely does reach `vamp` through the 47 uF-bypassed 4.5 V bias rail, which is an AC ground and not feedback. A stated `gbw` annotation on the amplifier beats the substituted macromodel's 1 MHz default, which matters more than it sounds — on the 39.8 dB RIAA stage the default cost 0.7 dB at 1 kHz against a 10 MHz NE5534, seven times that network's accuracy budget, and it would have been reported as the circuit's gain rather than the model's. Separately, `detachDrivers` removes anything already driving the net a sweep is about to drive: once a *preceding* stage is stood up as a macromodel instead of cut away, its output is a VCVS, and putting the stimulus across a VCVS output is two ideal sources on one node — ngspice answers with a singular matrix, which surfaced as `key not found: frequency`, an error about a missing vector three steps from the cause. Only stiff drivers are removed, so a stage fed through a coupling capacitor or a series resistor is untouched.

Conventions these analyses read from `attrs`, none of which change a core type: `Net.attrs["voltage"]` (nominal rail volts), `Component.attrs["esr"]`/`["esl"]` (capacitor parasitics, SI base units) and `["package"]` (case size, for the parasitic defaults table).

### `spice/xspice` submodule

`src/nimcir/spice/xspice/` authors **XSPICE code models** — behavioural device models compiled into a `.cm` shared object that ngspice `dlopen`s and instantiates as an `A` device. This is how a part whose behaviour is not expressible with R/C/L/D/Q/M/V/I gets simulated. `src/nimcir/spice/xspice.nim` is the hub and exports only what needs no external toolchain (`spec`, `ifs`, `instance`); `mif`, `accessors`, `dsl` and `build` are opt-in per-import, the same rule `spice.nim` applies to `spice/ngspice`.

**Prerequisite:** producing a `.cm` needs a **configured ngspice source tree** at `$NGSPICE_SRC` (`./configure --enable-xspice --enable-cider`). Distro `-devel` packages ship only `sharedspice.h`; `cmpp`, `dlmain.c`, `dstring.c` and the MIF headers exist only in the source.

- **Why a Nim DSL beats the C workflow.** ngspice's `cmpp -mod` is *not* a C preprocessor — it is a lex/yacc translator (`src/xspice/cmpp/mod_yacc.y`) that rewrites `PARAM(gain)` into `mif_private->param[i]->element[0].rvalue`, taking `i` from declaration order in `ifspec.ifs` and the union member from the declared type. So `PARAM`/`INPUT`/`OUTPUT`/`PARTIAL` do not exist as C macros and cannot be `importc`'d; they must be reproduced. Upstream that leaves `ifspec.ifs` and `cfunc.mod` as two hand-maintained files nothing cross-checks. Here one `codeModel` block produces both, so an accessor is resolved against the ports that will actually be emitted — a misspelled port name is a Nim compile error, not a wrong-index read. Verified: the C emitted from `accessors.nim` is byte-identical to cmpp's own output.
- **`spec.nim`** — the format-agnostic data model (`ModelSpec`, `PortSpec`, `ParamSpec`, `StateVarSpec`, `Bound`) plus `validate`. **Declaration order in the `seq`s *is* the `conn[i]`/`param[i]` index**, for both the renderer and the accessor rewriter; that shared ordering is the submodule's central invariant. Enum prefixes are `xp*`/`xd*`/`xt*`, not `pt*`, to avoid colliding with `netlist/types.nim`'s `ptPassive`.
- **`ifs.nim`** — renders a `ModelSpec` as `ifspec.ifs`, one row per repeated table block (legal; ngspice's own `d_dff` does it) rather than aligned multi-column, which removes all alignment logic. An empty `Description:` is *omitted*, because cmpp lexes `""` as zero elements and rejects the table.
- **`mif.nim` / `private/mifshim.h`** — the FFI. Every struct is `{.importc, header.}` so the C compiler resolves each offset from the same header ngspice was built with; hand-declaring `Mif_Port_Data_t`'s twenty fields would put everything after the first mismatch at the wrong offset with no diagnostic. C enumerator values are laundered through a `{.emit.}` TYPESECTION rather than hard-coded, so a reordered enum is a compile error. Note `Mif_Value_t` has exactly six members and **no digital one** — digital ports go through `pvalue` as an opaque `Digital_t*`.
- **`accessors.nim`** — `template`s returning `untyped`, never `proc`s, so `output(outp) = x` stays an ordinary assignment. `PARTIAL(o,i)`/`AC_GAIN(o,i)`: **both** indices are *connection* indices (cmpp resolves each with `valid_subid(..., CONN)`), and direction is checked accepting the required direction **or `inout`**. It also carries the **analog-state** helpers -- `analogAlloc`/`analogVar`/`analogIntegrate`/`setPermBkpt`/`setTempBkpt` -- the continuous-time counterparts of `eventAlloc`/`eventVar` and the third shape a code model comes in, after memoryless and event-driven. ngspice rotates those buffers per accepted timepoint and **rolls them back when it rejects one**, which is what makes them the only correct home for a value a rejected timestep has to be able to un-decide; `stateVar` (STATIC_VAR) is not rolled back, which makes it right for a latched enable and wrong for a switching cycle's turn-off time. `analogIntegrate` integrates with the simulator's own method -- adding `integrand * tstep` by hand would be forward Euler whatever the rest of the deck is being solved with -- and refuses outside `.tran`, since at an operating point there is no interval. `setPermBkpt` is not optional for anything with edges: between them the interesting nodes are smooth, so truncation-error control steps straight over a clock edge nothing told it about. `examples/xspice_integrator.nim` is the worked example.
- **`dsl.nim`** — the `codeModel` macro. Rewrites the `eval:` body's `param(x)`/`input(x)`/`partial(o,i)`/... into indexed accessor calls, mirroring cmpp's yacc pass but name-aware. Unlike `netlist/dsl.nim` (where an unknown `key = value` silently becomes an `attrs` entry), an unknown name here is a hard compile error — there is no open-ended bag for it to mean anything. Two expansion modes: normally it emits the `{.exportc, cdecl, raises: [].}` entry point; under `-d:xspiceGenIfs` it emits an `ifspec.ifs` writer and imports **no FFI at all**, so interface generation works with no ngspice headers. A supplied `default =` implies `nullAllowed`, because cmpp rejects `Default_Value` together with `Null_Allowed: no`.
- **`build.nim`** — `buildCodeModel(source, outPath)` runs the whole pipeline: `-d:xspiceGenIfs` pass → `cmpp -ifs` → `cmpp -lst` → compile `ifspec.c`/`dlmain.c`/`dstring.c` → `nim c --app:lib` linking them. Two non-obvious requirements: **`src/misc/dstring.c` must be linked in** (`dlmain.c` calls `ds_free`, which neither the ngspice binary nor `libngspice.so` exports), and **the tree's configure flags must match the installed simulator's** — `devdefs.h` has `#ifdef CIDER`/`#ifdef KLU` members *inside* `SPICEdev` right before `DEVinstSize`, and `ifspec.c` uses designated initializers, so a mismatch shifts every later slot and ngspice segfaults in its own device loop with no message. `checkAbi` catches what it can; CIDER is not reported by `ngspice -v` and so can only be warned about. Nothing links `libngspice`: the `cm_*` helpers resolve to `dlmain.c`'s wrappers, which forward through a `coreitf` table ngspice fills at dlopen.
- **`cmpath.nim`** — `deckSafeCmPath`. ngspice **case-folds the lines it pre-parses**, including `pre_codemodel`'s argument, so a `.cm` whose absolute path contains any uppercase character can never be loaded from a deck (it reports `No such file or directory` for the folded name; quoting does not help, the quotes become part of the filename). Returns an all-lowercase symlink when needed. This does *not* affect `write <rawfile>` in `spice/ngspice.nim`, which the control interpreter handles later from unfolded text.
- **`instance.nim`** — `addCodeModelInstance(nl, designator, spec, bindings, params)`. An `A` line is **not positional**: a differential port (`vd`/`id`/`gd`/`hd`) takes *two* nodes, a vector port is bracketed `[a b c]` with no nesting, and an unconnected port is the literal `null` — allowed for a whole connection (including a whole vector) but **rejected inside** a bracket. All verified against `src/xspice/mif/mif_inp2.c`. A `PortBinding` (`wire(n)`, `wire(pos, neg)`, `wire([a, b, c])`, `nullPort()`) says only *which nets*; the port's declared type and `vector` flag decide how they group, and `checkBinding` rejects a wrong node count, a partial differential element, an out-of-range `Vector_Bounds`, and a `vnam` port (which names a voltage *source*, not a net). **Pins stay real** — `name[0]`, `name[1]`, … for vectors and `name.p`/`name.n` for differential — so graph walks and ERC-style analysis see actual nets rather than an opaque string. The rendered port text is handed to the writer via `attrs["xspice.ports"]`.
- **Where the `A` line is emitted**: `formats/spice.nim`'s `formatDeviceLine` has one branch honouring `attrs["xspice.ports"]`, the same verbatim-passthrough approach it already uses for `.MODEL` cards. `prefixByDeviceKind` maps `"code_model" -> 'A'` and is therefore **deliberately not a pure inverse** of `deviceKindByPrefix` — `'A'` must never appear in the *forward* map, because an `A` line routed through the positional reader invents nets literally named `%v(in)`. Writing works; reading an `A` line back into ports does not, and cannot without the model's `.ifs` (with `%type` omitted the node count per port is unknowable from the deck alone), so it falls back to generic `pin1..pinN`.
- **Reaching a design**: `addCodeModelInstance` takes a `cmPath`, recorded as `attrs["xspice.cm"]` (dotted, so the registry never validates it), and `collectCodeModels(nl)` gathers them recursively. `run` unions that with its explicit argument, which is why **no analysis call site changed** — and an attribute rather than a `Netlist` field because the netlist reaching ngspice is never the one the design built, but a fragment from `clone` → `flatten` → `expandPinModels` → `isolate`, and `attrs` rides through all four for free. Before this, `codemodels` was passed by none of the eight `run` call sites, so a design containing an `A` device could be authored and never verified: `hasDeviceModel` is true for a code-model component, so `isolate` cheerfully absorbed it into a fragment that then died on `unable to find definition of model` — an error about a model name, three steps from a missing file path.
- **`-d:xspiceSpecOnly`** emits the `ModelSpec` const without the `{.exportc.}` entry point. The entry point is FFI against ngspice's MIF headers, which live only in a configured *source* tree, so importing a model merely to instantiate it would make every design on the machine depend on that tree. `nimcir check` passes it; only `buildCodeModel` ever wants the implementation. `findToolchain` also falls back to a configured tree under the cache directory when `$NGSPICE_SRC` is unset — forgetting the variable did not fail loudly, it made a design quietly report `not evaluated` for the one part the tree was fetched for.
- **Runner integration**: `spice/ngspice.run(nl, cards, codemodels)` emits `pre_codemodel <path>` as the first lines of its synthesized `.control` block. `pre_codemodel`, not `codemodel`, because an `A` device must resolve while the netlist is *parsed*, before the control block runs.
- **Digital / event-driven models** work and are covered end-to-end (`examples/xspice_dff.nim`, a rising-edge D flip-flop). The execution model differs from analog: no `partial`, no matrix loading — the model is called on an input *event*, reads `inputState`, and schedules an output with `outputState` + `outputDelay`. Two obligations an analog model does not have: **`outputChanged(port) = false`** must be set when the output did *not* change, or every input event emits a redundant output event; and previous-timepoint state must live in **`eventAlloc`/`eventVar`**, never a Nim global (ngspice rotates those buffers per accepted timepoint and rolls them back on rejection, and a global would additionally be shared across every instance in the deck). `load(port) = ...` is declared once under `init`. Because `outputState`/`outputStrength`/`outputChanged` convert between Nim enums and ngspice's ints, the DSL rewrites *assignment* to them into setter calls rather than pretending they are lvalues.
- **Digital vs analog field selection**: cmpp picks the `Mif_Value_t` member from `Allowed_Types[0]` (not `Default_Type`), so `accessors.nim` does too. `validate` rejects a port mixing digital and analog allowed types, which is what makes the two equivalent in practice.
- **Not yet exercised**: user-defined node types, `cm_event_queue` self-scheduling, and `.ac` readback from a code model (the rawfile parser now handles `Flags: complex`, but no Nim-authored model has set `acGain` and had the result read back). A whole mixed-signal circuit — analog sources, `adc_bridge`, a Nim code model, `dac_bridge` — *can* now be built entirely through `netlist/graph` and simulated; `tests/test_xspice_digital.nim` does exactly that.
