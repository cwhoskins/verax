# Designs and templates

A design is an ordinary `.nim` file using `nimcir/contract/dsl` that ends with `quit(verifyMain(d))`, so `nim c -r --path:./src designs/foo.nim` is the same check `./bin/nimcir check designs/foo.nim` runs, without the wrapper (~1.1 s cold, ~0.7 s warm). This is the primary loop. `nimble verify` checks every design here and every file under `templates/`.

Exit codes are graded: `0` clean, `1` a claim failed, `2` structural problem, `3` a claim nothing could check, `4` a requested capability is unavailable here, `5` the design did not compile (only `nimcir check` produces `5`, and it is separate on purpose — told only "it failed", a reader edits the circuit to fix a syntax error). Flags, forwarded to the design binary: `--offline`, `--caps=op,dc,ac,tran`, `--verbose`, `--strict`.

## The designs

`ts808_drive` (single-supply overdrive), `sensor_node` (LDO + I2C), `aa_filter` (4th-order Sallen-Key), `charge_pump` (Dickson doubler, whose `settled_rail` claim found a 403 mV edge spike across COUT's ESR and ESL where a hand-run with ideal capacitors reported 5.1 mV of droop), `wien_osc` (oscillator -- kicked into life with an `.ic`, then measured for rate, swing and distortion by the `oscillator` role), `riaa_preamp` (stereo, instancing `lib/riaa.nim` twice, and the first design to claim a **two-subject** quantity: a `channel_match` role binds the two `gain_stage` instances with `roleRef` and claims `gain_delta_max_db <= 0.5 dB` across the audio band — two copies of one `subckt` measure exactly 0 dB apart, and a 1% feedback-resistor error on one channel moves it to 67 mdB) and `lt8640a_buck` (the datasheet reference design, simulated through **two** Nim-authored XSPICE code models -- `lib/lt8640a_avg.nim` for the rail voltage and `lib/lt8640a_sw.nim`, peak current mode at fifty timepoints a cycle, for the ripple -- with `spice/transform.selectSimModel` picking by what is being asked, and the first design to claim a **current**: `current_path` reads L1's 905 mA triangle against the 879 mA the design equations fix, and its 49% of the part's own stated saturation current -- now stated as one `switching_regulator` instance covering the way up, the settled ripple, the inductor current, a 1 A **load step** measuring 21.3 mV of droop and 27 us of recovery, and 70.1 dB of **ripple rejection** at 100 kHz by the tone method, which is the only method that reaches it: an `.ac` sweep through an XSPICE code model returns exactly zero output, because a code model contributes to the AC matrix only if it sets `AC_GAIN`) and `carrier` and `sensor_head` (each a **module when imported and a program when checked**, split by `when isMainModule`: a board states what is plugged into it for the bench, and `asSubcircuit` drops the connectors so those assumptions cannot leak into a system) and `system_sensor_rig` (both boards wired through an explicit cable — the design that found an 8.71 ohm anti-resonance neither board has on its own, on a sensor head that passed its own check by 30x) and `param_filter` (two Sallen-Key sections a decade apart, both built by `lib/filters.sallenKeyLP(fc, r, q)` — no component value appears in the design file, so the claims check the design equations rather than checking that somebody did the arithmetic twice), `divider_net` (a voltage divider and a current divider both stated as a **total impedance and a ratio**, and the three-resistor network that replaces the voltage divider's bottom leg with the current divider -- both taps must read the same 2.5 V, which is the substitutability property measured rather than asserted, and the split itself is read at a sense node two levels down inside the instance because both legs return to the same ground and nothing in the parent netlist witnesses it; the two taps are additionally **swept** rather than sampled -- `source_sweep` measures the ratio as a slope over the whole input range, which a wrong network with a compensating error would still pass at one bias, and `load_sweep` measures 18.75 kohm of output resistance at both taps, which is the half of substitutability no node voltage witnesses) and `i2c_eeprom` (a dummy MCU and an M24C64-U EEPROM holding an actual **conversation** -- two Nim-authored event-driven code models on a shared open-drain bus, reading the 128-bit unique ID out of the identification page, writing to the memory array, acknowledge-polling through the part's real 5 ms write cycle and reading back, with the controller's verdict pin carried out through a `dac_bridge` so the outcome is a `settled_v` claim like any other; SDA and SCL are **real analog nets** with pull-ups, bus capacitance and a `bidi_bridge` at each line, so the `i2c` role's claims have resistors to find) and `adj_regulator` (two LM317 rails sized from the datasheet equations in `lib/adjreg.nim` -- the part is a *value* carrying its reference, ADJ current, range, dropout, minimum load and thermal resistance, and for simulation a `SimReplacement.build` swaps it for the **loop** it closes, an error amplifier holding the reference between OUT and ADJ plus a current source for the ADJ pin, so ngspice solves the divider in the netlist and nothing in the design file is compared against itself: drop the `iAdj*rAdj` term and the 5 V rail measures 5.036 V and misses its 0.5% band; the loop now closes through a **floating series pass element** fed from the IN net, so both the input current and the ripple rejection fall out of it rather than being declared, and two `linear_regulator` roles claim a load step, line regulation of 0.0107 %/V against the datasheet's 0.01 %/V typical, and 62.9 dB of rejection at 120 Hz **by both methods at once** -- a `.tran` tone and an `.ac` sweep, two solvers agreeing to 0.002 dB). The **`xbar_*` family** is the first *product* here rather than a circuit demonstrating one feature: an Ethernet-controlled 4x4 50-ohm RF crossbar powered from PoE or USB-C, split into five chunk designs (`xbar_poe`, `xbar_usbc`, `xbar_power`, `xbar_rf`, `xbar_control`) each a module-and-program like `carrier`, and one system (`xbar_switch`) that instances all five through `asSubcircuit` and drives both inlets at once. What it demonstrates: (1) the **`safe_default` role** (`lib/xbar_parts.nim`, the second role written outside the library after `i2c_transaction`) -- one `dc_voltage <= fraction*rail` claim per line, checking that the ADG904 enables sit low at power-up held by `controlPulldowns`; a *reversed* OR mux is caught the other way, collapsing `vsys`/`v3v3` so the `power_rail` claims fail. With the ADG904 now a real absorptive `rf_switch` model (`lib/adg904.nim`), the claim finally *means* what it says -- enable low ⇒ every RF port sitting in its internal 50 ohm -- rather than passing because `expandPinModels` grounds an unmodelled pin. `xbar_rf.nim`'s bench also routes RIN1 → m1 → ROUT1 (EN1/EN5 driven) and checks the routed path carries a tone while the unselected midplane rails stay at ground. (2) The **cannot-check list is a deliverable**: `xbar_switch.nim`'s header carries it. Two entries closed while this family was live -- coupled inductors (§26, `spice/models/magnetics` + a `dc_path_exists` barrier claim on the flyback `T1` and the PoE common-mode choke) and the switch device model (§26, `spice/models/switch`) -- and what is left is stated precisely: transmission lines / S-parameters, rail sequencing, a logic-state quantity, `esd_clamp`, and a two-port AC transfer for the choke's rejection. (3) A whole-system `.op` carrying **both** the LT8640A switching code model and the 48 V PoE rectifier bridge does not converge, so `equipXbarPower(d, prefix, withBuckModel = false)` swaps in `buildIdealBuck` (an ideal source on SW) for the system while the chunk bench keeps the real model; and the switcher's steady-state claims (ripple, PSRR, load step) are declined even in the chunk bench because its input, fed through the OR diodes rather than a stiff source, collapses the switching model's timestep -- `lt8640a_buck` exercises those against a stiff 12 V input instead. Shared parts and subcircuits live in `designs/lib/`, which `nimble verify` does **not** pick up because `listFiles` is not recursive — they are compiled as dependencies of the designs that import them. A file that imports an XSPICE code model for its `ModelSpec` needs `-d:xspiceSpecOnly`, which `nimcir check` passes for a design and which `tests/test_xspice_i2c_eeprom.nim.cfg` -- a per-file Nim config, and the reason `.gitignore` re-includes `/tests/*.nim.cfg` -- passes for the one test that does; without it the compiler tries to build the model's FFI against ngspice headers it has no reason to need.

## Seeing what was actually simulated

`NIMCIR_KEEP_DECKS=<dir> ./bin/nimcir check <design>` copies every deck handed to ngspice into `<dir>`. The fragments are derived, not authored, so this is the only way to check a surprising number against the circuit that produced it. **`--keep-runs=<dir>` (or `$NIMCIR_KEEP_RUNS`) keeps the *results* too** -- per simulation, `run000.cir`, `run000.raw` and `run000.log`, plus `run000.svg` and its `run000.json` scene of the derived fragment, plus an `index.txt` naming each run's analysis, netlist, plot and point count, so `run001` can be identified as the PDN sweep of `vdd` without opening it. The deck is not copied there but *written* there, so it is the one that ran and re-running it in place reproduces its rawfile; the rawfile is ngspice's own ASCII format, so `load run001.raw` in ngspice brings the whole curve back. `--save-currents` adds device terminal currents (`@r1[i]`) to what is saved, which is the one category ngspice does not save by default -- `.op`/`.tran`/`.dc` only, see `src/nimcir/spice/CLAUDE.md`. Neither flag can move a measured number, which `tests/test_spice_keep.nim` pins.
